# @forge/gates

The verification plane: independent gates that decide whether a Worker's ticket may move forward. G1 (claims, receipts, test integrity, project checks) is implemented; G2 to G6 and blast radius are not.

## Why it exists

Agents overclaim. A Worker's own summary ("I ran the tests, I edited X") is untrusted, and the Worker can also make a suite green by weakening it. The Director therefore needs checks that run outside the Worker's process and read only evidence the Worker cannot forge: the git diff, HMAC-chained tool receipts written by the hook, and the project's own commands re-run by the server. Without them a ticket reaches Review on a false claim, a deleted test or a loosened assertion. Gates are the independent half of the governing rule: Workers self-report, separate processes verify (d-0001). Design: `docs/design/verification-plane.md` §2.

## What it does

Public API (`src/index.ts`):

- `createG1Gate(deps: G1Deps): Gate` returns a core `Gate` named `G1`. It pairs the pure `buildG1Gate` (domain, `runCommand` required) with the real spawner; the domain never imports an adapter.
- `detectProjectAt(root)` reads the names in a repository root and its `package.json` (size-capped, never run) and returns `{ ecosystems, checks }`: ecosystem ids from the registry's marker files, and suggested checks (node: the `lint`, `typecheck`, `test`, `build`, `format:check` scripts run with pnpm, yarn or npm by lockfile; go, rust and python: fixed commands). A suggestion for the new-project form only: nothing is executed, an unreadable folder gives an empty result.
- `createScriptGateRunner({ worktrees, env, passEnv?, runCommand? })` is the core `ScriptGateRunner` for pipeline script gates and the tester's red proof (d-0074). Before running anything it reads the diff: a change to a path matching `guardPaths`, to the script the command starts (a relative first token such as `./scripts/x.sh`) or to the script a known interpreter (`node`, `python`, `bash`, `pwsh`, ...) is given fails the gate closed without running it, and so does a `cwd` outside the worktree. It then runs the command with the G1 environment allowlist. `expect: 'pass'`: exit 0 is `passed`, non-zero `failed`. `expect: 'fail'` (red proof): non-zero is `passed`, exit 0 is `failed` ("the new tests already pass"). A timeout or a command that cannot start is `error` either way.
- `createWorktreePreparer({ worktrees, env, runCommand?, now?, cacheDir?, cacheBudgetBytes? (a number or a function read at every store; the server passes the `engine.setup_cache_gb` setting), trackStore?, log? })` is the core `WorktreePreparer` (d-0180): `plan(path, config)` returns the owner's `setup` (even `[]`) or defaults detected from the worktree (and the repository top for a subfolder project); `prepare(path, plan, { baseSha, onStep? })` runs the steps with a scrubbed env plus the step's `env` and `pass_env`, project tool folders (`path`) first on PATH once they exist, skips when the stored record's key (sha256 of the steps and the bytes of their `inputs` files) matches, stops at the first failure and returns it as `{ ok: false, step, command, exit_code, timed_out, tail <= 4 KB, inputs_changed_by_worker }`, records created top-level paths and tool folders on success; an empty plan runs and stores nothing; `skip(path, plan)` stores a `skipped` record. With `cacheDir` (`<dataHome>/cache`, wired in `apps/server`) steps reuse work (4.3a): `cache_env` points the tool's download cache at `<cacheDir>/downloads/<folder>` for that step only (`adapters/step-cache.ts`), and a step with `cache_outputs` runs an optional `toolchain` probe, computes `computeStepCacheKey` (command, folder, `inputs` bytes, toolchain output, OS, CPU, outputs), restores the folders by copy from `<cacheDir>/setup/<key>/` and skips the command (record step `restored: true`), or runs and stores them in the background (`adapters/setup-cache.ts`: temp folder then rename, LRU eviction to a 5 GB budget). Any cache fault runs the step normally and is logged; with no `cacheDir` nothing changes. G1 and the script gate runner read that record (`worktrees.readPrep`, optional) and put its tool folders first on PATH and allow running from them (`trustedDirs`), so `pytest` is the project's own.
- `detectSetup({ projectEntries, repoEntries? })` picks default steps from the recipe table `domain/ecosystems/setup-recipes.ts` (d-0176: one row per tool, lockfile rows before bare-manifest rows, project folder before repository top; `.gitmodules` at the repository top; covers node (pnpm, yarn, bun, npm), python (uv, poetry, pipenv, pip), go, rust, dotnet, ruby, php; none for Maven/Gradle/CMake or a repo with no manifest). `detectProjectAt(root, repoRoot?)` now also returns `setup`. Adding an ecosystem is one row. Rows carry `cache_env` per tool (not Cargo); `cache_outputs` + `toolchain` only for npm, yarn classic, bun (`node_modules`) and composer (`vendor`); Python rows (`setup-recipes-python.ts`) never have outputs (virtual environments are not relocatable), and pnpm, Yarn Berry, .NET `obj/` and Bundler are download-cache only or nothing.
- `runShellCommand(req)` is the default command runner (`G1Deps.runCommand` seam).
- `createFileReportStore(dataDir)` is the core `ReportStore` on disk: `<dataDir>/runs/<runId>/gates/<name>.md`, written under a temp name and linked into place (atomic), never overwriting (a taken name gets `-2`, `-3`, ...), run id and name checked against a strict pattern. The engine names a report `<gate>-<head sha>`. `createStorageToolCallLister(storage)` is G1's `listToolCalls` over the stored `tool_call` run events. It leaves out only a call a restart cut off: a read-only tool (`Read`, `Glob`, `Grep`, `LS`) with no result that is followed by a later `hook_liveness` registration, and only as many registrations as the run row's `generation` accounts for (a run that never resumed excuses nothing). A cut-off `Edit`, `Write`, `Bash` or `PowerShell` call may have run, so its receipt stays owed and G1 fails on the missing receipt. It also leaves out a call Claude Code rejected in its own validation: an error result whose text starts with `<tool_use_error>` (an Edit of a file not read yet) never reached PreToolUse, so no receipt exists and none is owed; a success, or a failure that only quotes the tag after other output (a shell that ran), still owes one. `createStorageEarlierRuns(storage)` is G1's `earlierRunIds`: the ticket's runs that started before the one being gated.
- Types: `ScriptGateDeps`, `G1Deps`, `ToolCallRef`, `CommandRequest`, `CommandResult`, `RunCommand`.

`G1Deps`: `receipts: ReceiptLog`, `worktrees: Pick<WorktreeManager,'diff'>`, `listToolCalls(runId)`, `runSecrets(runId, generation): Promise<HmacKey | null>`, `env`, and optional `earlierRunIds(run)` (a rework run reuses the ticket's branch, so those runs' receipts count once their own chains verify under their own secrets: they cover the changed files they edited with no claim needed, and back `edited` and `read` claims; `ran_tests` and `added_test` need the run's own evidence; the chain that gates the verdict stays the run's own. An earlier run whose chain is forged or whose secret is gone gives no cover and the claims finding names it), `passEnv` (extra env names for project commands), `runCommand`, `commandTimeoutMs` (default 10 min), `ignoreToolCall`, `now`.

G1 runs six checks and folds them into one `GateVerdict` (`failed` if any finding, else `error` if a check could not run, else `passed`; `report` is markdown, one section per check):

1. **chain**: `verifyGenerations` over the run's receipts, one segment per secret generation (d-0100): a run resumed after a server restart (d-0092) has one `resumed` receipt per resume, linking to the last receipt before it and signed with the new generation's secret. G1 asks `runSecrets(runId, g)` for every generation `1..N` (N = the larger of the run row's `generation` and the generations the chain records), verifies each segment under its own secret and the links between them, and requires the chain's generation count to equal the run's, so a cut-out segment or a missing `resumed` link is a finding ("Receipt chain broken at index i" or "Run reached generation R but its receipt chain records G"). Every tool-call run event must have a decision receipt whose `id` equals the event's `call_id` (hook `tool_use_id` equals ACP `toolCallId`, d-0057). A key too weak to verify with is `error`, never `passed`. A missing secret of any generation (for example a run past the registry's retirement, or a wiped secret store) is `failed` with the finding "Receipt chain unverifiable: the run secret of generation N is gone; re-running the ticket.": an `error` would park the ticket and unparking would hit the same missing secret for ever, while a failed gate sends it to rework, which starts a fresh run with a fresh secret.
2. **claims**: each `finish` claim needs evidence, else a finding quoting it.
   - `edited P`: allowed `edit`/`write` decision with a `mutation_committed` effect on P, and P is in the diff. The decision may come from an earlier run of the ticket whose chain verified (rework); `read` accepts those too, `ran_tests` and `added_test` do not. Coverage: a changed file with no `edited` claim is still covered when a verified earlier run has a committed edit receipt for it and this run did not edit it itself (a fresh edit always needs its own claim); the report says which run covered which file (`domain/claim-coverage.ts`, `domain/earlier-runs.ts`). An earlier run is set aside with a structured reason (`secret_gone` or `chain_broken`); when the only record of a file's edit is a `secret_gone` run (its unverified receipts name the file but never cover it), the finding says in plain words that the run's proof is gone and tells the Worker to re-apply the file through its edit/write tool and claim it, with `file` set; when every finding of the gate is such a finding, the verdict carries `provenanceOnly: true` so the engine can rework and then hold for the owner (`provenance_hold`, F-D3). A `chain_broken` run, an unsupported claim or any other failure is never `provenanceOnly`.
   - `read P`: allowed decision with a `read_completed` effect on P or on a folder containing P (`containsPath`: `.` and the worktree root contain everything; `src` does not contain `srcs/`). The effect state is the test, not a tool name, because only a `risk: read` tool ends there (`Read`, `Grep`, `Glob`, any harness). `failed_no_effect` never backs. The report says "backed by a search over <folder>". Earlier verified runs count.
   - `ran_tests`: allowed `shell` decision (effect `mutation_committed`, or `uncertain` for a run that failed; the report notes when only a failed run backs the claim) with a segment that starts with the command of ANY test-role check (`checks` with `role: test`). Match rule: split the resource on `;`, `&&`, `||`, lower-case and collapse whitespace, ignore leading `NAME=value`; the segment must equal the command or continue it after a space, must not be piped, and must not carry `--help`, `-h` or `--version`. So `echo pnpm test` and `git commit -m "pnpm test"` do not count. No test-role check (or an empty command, which never matches) means the claim is unsupported.
   - `added_test N`: an added line of a test file (by the active ecosystems' test patterns, or a file whose changed lines carry a test marker such as Rust `#[cfg(test)]`) declares a test (`it(`, `def test_x`, `func TestX`, `fn x`, `@DisplayName`, `TEST(S, N)`, ...; per-ecosystem regexes) and its title or name contains N, or N ends with the declared title at a separator boundary (`\s`, `::`, `.`, `/`, `#`, `>`, `›`; whitespace collapsed, case kept) so a runner's group-qualified name (`shelf add rejects x`, `TestAdd::test_x`) matches. The title needs two words or 12 characters. Comments and strings do not count.
   - Paths are folded (slashes, case, `./`, worktree prefix) before comparison.
   - Coverage: a non-empty diff with no claims is a finding ("finish carried no claims for N changed files"); every changed file except lockfiles (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`, `bun.lockb`, `Cargo.lock`, `poetry.lock`) and deletions must be named by an `edited` claim, else one finding lists them.
3. **test-diff**: deleted test files, test files renamed to non-test paths, added skip/ignore/focus markers of the active ecosystems (node `.skip`/`.only`/`xit(`; python `@pytest.mark.skip`/`xfail`; go `t.Skip`; rust `#[ignore]`; jvm `@Disabled`/`@Ignore`; dotnet `[Ignore]`/`Skip =`; ruby `xit`/`pending`; php `markTestSkipped`; cmake `DISABLED_`), more removed assertion lines than added (per-ecosystem assertion regexes), and, for node, `expect(X).strong` re-added as `expect(X).toBeDefined/toBeTruthy/...`. It fails closed: a test file git printed as `Binary files ... differ` (what a Worker-written `.gitattributes -diff` produces), or a `diff --git` header the parser cannot read, is a finding.
4. **gate-config**: any change to a gate configuration file of an active ecosystem (node: `vitest.config.*`, `eslint.config.*`, `tsconfig*.json`, `.npmrc`, ...; python: `pyproject.toml`, `setup.cfg`, `tox.ini`, `pytest.ini`, `conftest.py`, `mypy.ini`, `ruff.toml`, ...; go: `.golangci.*`; rust: `rustfmt.toml`, `clippy.toml`, `.cargo/config.toml`; jvm: Checkstyle, Spotless, Detekt, PMD files; dotnet: `Directory.Build.props`, `.editorconfig`, `*.runsettings`; ruby: `.rubocop.yml`, `.rspec`, `Rakefile`; php: `phpunit.xml`, `phpcs.xml`, `phpstan.neon`; cmake: `CMakePresets.json`, `CTestTestfile.cmake`, `.clang-tidy`), a project `gate_rules.config_globs` entry, or a file that steers every stack (`.gitattributes`, `Makefile`, `justfile`). Dependency manifests (`go.mod`, `Cargo.toml`, `pom.xml`, `Gemfile`, `composer.json`) are deliberately not guarded; any added or modified `*.cmd|*.bat|*.exe|*.ps1|*.com` anywhere in the diff; or a `package.json` script (or its `pre`/`post` hook) named by a check command. A file in the worktree that a check command runs by path is guarded too (`domain/check-scripts.ts`): the first word of a command when it is a path or `gradlew`/`gradlew.bat`/`mvnw`/`mvnw.cmd` (`./scripts/test.sh`, `bin/test`), any word that has a path separator or a script extension (`sh|bash|zsh|ps1|bat|cmd|mjs|cjs|js|ts|py|rb|php|pl`; `node scripts/lint.mjs`, `python scripts/check.py`, `bash ci/run.sh`; the value of `--flag=value` counts), with the check's `cwd` and a `cd <dir> &&` prefix honoured. Editing, adding or deleting one is a finding (this is also what makes an exact-match interpreter check on the Express lane safe to run unattended: the script it names cannot be changed by the Worker without a finding), since a Worker could otherwise turn it into `exit 0` and G1 would re-run the edited script. **Greenfield exception (d-0173):** while the project has no `checks` configured, an _added_ (status `A`) config file is allowed and the report says which files and why ("no project checks are configured yet, so there is nothing to loosen"); modified, deleted or renamed config, an added `.gitattributes`, executables and guarded scripts still fail, and with checks configured an added config file fails as before. Every finding carries the `file` it is about, and the G1 verdict sets `configOnly: true` when gate-config is the only check that did not pass and no check errored, so the engine can hold the ticket for the owner instead of reworking it (absent means unknown, never config-only). The script name is parsed from the invocation: flags and the values of `--filter`, `-F`, `--dir`, `-C`, `--prefix`, `--workspace`, `--cwd` are skipped (`-w` is read both ways, as npm and pnpm differ), then `run <name>` or a bare `<name>`.
5. **conflict-markers** (`domain/conflict-markers.ts`): any line the ticket adds that starts `<<<<<<< ` or `>>>>>>> ` fails G1, in any text file of any language (the check reads the diff, not an ecosystem), with the `file` set. A bare `=======` passes (common in documents), markers already in the base are not in the diff, removed marker lines pass, binary files are skipped. Forge merges the base into a ticket's branch and may leave a clash in the files for the Worker; this is what stops a resolver that quit early from merging, and the engine reads the finding to send the ticket back as a conflict, not a failed check.
6. **project-checks**: every entry of the project's `checks` list in list order, whatever its role (test, lint, typecheck, build, format, custom), in the worktree or its `cwd`, each with a timeout, last 4 KB of output in the report and the last 1500 characters in the finding message (the rework prompt must say why). The finding's `check` is `project:<name>`. Every check runs even after a failure. A role the project did not configure is absent from the report, never skipped or passed. An empty command or a `cwd` outside the worktree is a finding and nothing runs (fail closed).

Which ecosystems' rules apply (`domain/gate-rules.ts`): the project's `ecosystems` if it names any Forge knows; otherwise the ones detected from the diff's paths and the check commands' first words; if nothing is detected, all of them (so detection can only narrow the guard when it is sure). Data lives one file per ecosystem in `domain/ecosystems/` (node, python, go, rust, jvm, dotnet, ruby, php, cmake) plus `common.ts` for files that blind every gate. A project's `gate_rules` (`config_globs`, `test_globs`, `skip_patterns`, `replace`) adds to that data, or replaces a non-empty list when `replace` is set; `.gitattributes`, `Makefile` and `justfile` stay guarded either way.

- The environment is an allowlist (`PATH`, `PATHEXT`, `SystemRoot`, `ComSpec`, `TEMP`, `HOME`, `USERPROFILE`, `APPDATA`, ... see `shared/env.ts`) plus `G1Deps.passEnv`; `CI=1` and `NoDefaultCurrentDirectoryInExePath=1` are forced. `ANTHROPIC_API_KEY`, `GH_TOKEN` and `FORGE_*` never reach the child.
- The command's first token is resolved to an absolute executable through PATH and PATHEXT only, never the cwd, and refused (the check is `error`) if it is not found or lies inside the worktree. cmd.exe would otherwise run a Worker-committed `pnpm.cmd` from the cwd.

G1 also fails any change outside the project folder (`scope` check): the worktree manager reports such
paths as `../x` for a project scoped to a subfolder of a repository (d-0124).

## Why this approach

- Evidence over assertion: claims are matched to HMAC-chained receipts and git's own diff; nothing the Worker writes is trusted.
- Every side effect is injected (receipt log, secret, spawner, clock, env), so the gate is tested with in-memory fakes and real receipts built by `@forge/tools`.
- Project commands are repo-owner config strings from `.forge/project.yaml`, often with pipes or `&&`, so they run through the platform shell (`shell: true`) with the first token pre-resolved (see check 5). They are never Worker input. On timeout the whole tree is killed (`taskkill /T /F` on Windows, process group elsewhere).
- Heuristics are deterministic and simple on purpose; a cleverer gate that sometimes guesses is worse than one that explains each finding.
- Rejected: pushing logic into the engine (it must stay IO-free, d-0058). Decisions: d-0001, d-0015, d-0033, d-0052, d-0095 (checks by role and per-ecosystem rules; supersedes d-0034).

## Requirements

- Node 24; layer rule: imports `@forge/core` and `@forge/tools` only (d-0052).
- `G1Deps.runSecrets(runId, generation)` must return that generation's receipt secret, which the server keeps in the SecretStore until the run is retired (d-0100); the server keeps a successful run's secrets until its ticket has left the gates.
- `ProjectConfig.checks`, `ecosystems` and optional `gate_rules` from the project settings (the old `profile` + `commands` form is converted by `@forge/core` when settings are read).
- Tests: `npx vitest run packages/gates`. `command-runner.test.ts` spawns real `node` processes (30 s per-case timeout for full-suite load).
- The diff handed to G1 must come from a `WorktreeManager.diff` that passes `--text` and `-c core.quotePath=false` (`@forge/git` does).
- Setup steps run the project's own tools (`pnpm`, `uv`, `cargo`, `git`, ...) with network and install scripts, outside the Worker's tool policy: they must be on the server's PATH. Setup output folders and the record live in the worktree and `.forge-prep/` (`@forge/git`).
- Heavy tests: `worktree-preparer-cache.heavy.test.ts` runs a node script as a fake package manager and proves a second worktree is restored with the command not run. `worktree-preparer.heavy.test.ts` (root `vitest.config.ts` heavy project) runs a real `npm ci` offline on a fixture with a `file:` dependency, a second prepare (no command) and a lockfile edit (reinstall); it skips itself where `npm` is not on PATH.
- Coverage floor 80% lines (root `vitest.config.ts`).

## Extending

A new gate is a new `create<Gx>Gate(deps): Gate` in `src/domain/` over injected ports; reuse `CheckOutcome` and `renderReport`. A new G1 check is a function returning `CheckOutcome`, added to the list in `domain/g1-gate.ts`. A different process runner implements `RunCommand`.

## Limits

- Heuristics: the removed-assertion count is per file and ignores moves between files; matcher weakening only sees `expect(X).matcher` on the same subject text; `assert` counts any line containing the word. A cleverly rewritten weakening passes.
- `package.json` scripts are matched by key on changed lines, not by parsing the `scripts` object, so a same-named key elsewhere also trips it. Only scripts invoked as `npm|pnpm|yarn|bun [run] <name>` are known; a direct `vitest run` command has no script to guard.
- Ecosystem rules are regex and glob heuristics per language, not parsers: a Ruby `skip` or a Python `@pytest.mark.skipif` is flagged by its text, a test silenced by another mechanism (a build-file exclude, a runtime flag) is not. Rust test modules are recognised by changed lines (`#[cfg(test)]`, `#[test]`, `#[ignore]`), so an edit inside an untouched module is judged by its path only. Onboarding detection from repo root files is not built; detection uses the diff and the check commands.
- Truncating the tail of the chain is not detectable from the chain alone (the run record's final hash covers that, not G1).
- Receipt resources are lower-cased and the shell resource is cut at 200 characters by policy, so a test command longer than that cannot match.
- Forge's own MCP tools are expected to carry hook receipts; if a harness does not hook them, pass `ignoreToolCall`.
- Path comparison is case-insensitive (Windows); two files differing only by case are not told apart.
- Script gates: the guard looks at paths only (a script that sources another file the Worker changed is not caught), and the interpreter list is fixed; a command led by anything else is guarded only by the owner's `guardPaths`.
- Setup cache: Cargo has no `cache_env` on purpose: a Forge-owned `CARGO_HOME` would hide the owner's `config.toml`, registry credentials and installed tools, so crates stay in the owner's own `CARGO_HOME`; the copy cache is per recipe-marked folder, so an npm workspace whose nested `node_modules` differ is not restored fully until the owner lists them; the settings view and a clear-cache action come in 4.3b.
- Setup: input globs are file names or a pattern in the last path segment (no `**`, no pattern in a folder name), so a sub-package manifest in a workspace does not change the key; the default python recipes call `python` (not `python3`) and `requirements.txt` only; install scripts run with the server's user rights until the sandbox (d-0161).
- G2 to G6 and blast radius: none yet. Red-before-green order (d-0015) is not checked.
- Residual risk: project checks execute Worker-written code (tests, scripts) as the server's Windows user. The env allowlist and the executable resolution narrow what leaks and what can be swapped, but same-user files and DPAPI blobs (`forge secret wrap`) are reachable by that code. Real isolation needs the container/WSL lane (d-0005); until then a passing G1 is evidence about behaviour, not a sandbox.
- Command resolution pins only the first token of a command line; later segments (`a && b`) are resolved by cmd.exe with `NoDefaultCurrentDirectoryInExePath=1`, and any added `*.cmd|*.bat|*.exe|*.ps1|*.com` is a finding. Shell builtins (`cd`, `echo`, `set`, ...) and `NAME=value` prefixes pass through unresolved.
- Earlier-run evidence needs the earlier run's secret, which the server keeps for every ended run until its ticket is done or cancelled (d-0178); a run whose secret is gone anyway (a ticket from before that rule, a wiped store) covers nothing, so its files need a fresh edit receipt from the rework run (re-apply them through the edit/write tool); that is what the finding asks for, and the owner can vouch if it cannot be done.
- Earlier-run receipts are not tied to a commit: an `edited` claim backed only by an earlier run's edit passes if the path is in the current diff, even if a later run changed that file again. The rework run must re-run tests itself for `ran_tests`.
- Coverage: deleted files cannot be backed by an edit receipt, so they are exempt from the `edited` claim requirement (test deletions are still caught by test-diff). Files a Worker generates through the shell and leaves untracked need an `edited` claim too.
- With `--text` a real binary file appears in the patch as text; the parser only inspects test and config paths, so this costs size, not correctness.
