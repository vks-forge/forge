# @forge/drivers

`WorkerDriver` implementations: one folder per harness under `src/adapters/`. Today: the Claude Code driver (`id: 'claude-code'`) with an ACP engine (default) and a `claude -p` CLI engine (fallback), the Claude `DirectorLLM` (one `claude -p` per Director step), plus the live preflight probes.

## Why it exists

Workers run inside third-party harnesses (Claude Code first; Codex, OpenCode, Pi and generic ACP later) that each speak their own protocol. The Director must start, steer, resume and kill a run the same way whatever the harness, and must never trust a harness's own permission bypass. This package is that boundary: one driver per harness, harness output normalised to core `RunEvent` / `RunResult`, every quirk contained in the harness folder. Without it harness details leak into the engine and each new harness means a core edit. Design: `docs/design/execution-plane.md`; the Claude brief is `docs/design/briefs/claude-driver.md`.

## What it does

- `createClaudeDriver(deps)` returns a core `WorkerDriver`. `deps`: `prepareRun(req) -> { runDir, mcpServers, env, hookServerUrl, hookToken }` (the app creates `<dataHome>/runs/<id>/`, issues the token, starts nothing), `receipts.decisionFor(runId, toolUseId, { name, argsHash }?)` (read access to the server-side receipt chain), `clock` (`now`, cancellable `after`), `spawn`, optional `git`, `log`, `baseEnv`, `config`. `createReceiptLookup(receiptLog)` is the `receipts` implementation over the tools `ReceiptLog` (id first, args hash as the fallback; a receipt that cannot be read as a decision is a `deny`). `resolveClaudeBinary(binary, { platform, pathVar, exists })` resolves `claude` to a spawnable path; on Windows a `.cmd`/`.bat` shim or a missing binary throws `InvalidInputError` naming `FORGE_CLAUDE_BINARY`. `systemClock` and `nodeSpawn` are the real ones. Config (zod, defaults filled): `engine: 'acp' | 'cli'`, `envPassthrough` (extra host variable names, default none), `receiptGraceMs` (3000), `receiptCrossCheck`, `authTimeoutMs`, `cancelGraceMs`, `rateLimitBackoffMs`, `claudeBinary`, `acpSteering`, `pinnedAdapterVersion` (there is no CLI pin: the installed `claude` is whatever the user has). Also `harness` (`() => { id, binaryPath?, authMode }`, read at the start of every run; default `claude` on PATH, own login), `secrets` (a core `SecretStore`) and `fileExists`. `resolveInstalledClaude(binary, { platform, pathVar, exists })` returns an absolute path on any platform and throws `HarnessNotInstalledError` (message starts `Install Claude Code: https://code.claude.com/docs/en/setup`) when nothing is found.
- Layers: `adapters/claude/claude-driver.ts` composes; `run-supervisor.ts` owns the event log (numbered, validated, replayable), the stall and turn timers, the receipt cross-check, pause detection and the result; `acp/` and `cli/` are the engines behind one seam (`types/claude/engine.types.ts`); `domain/` is the pure rules (env, failure classification, the result table, event normalisation); `hooks/` is the Claude hook client and the `--settings` renderer (moved from `@forge/hooks`, d-0056). The hook client replaces a tool output over 1 MiB (`tool_response`, or `error` on a failure) with `{ truncated, bytes, sha256, prefix }` before posting, so a big file read cannot exceed the server's body limit; the server records the hash of the whole output as the effect's `result_hash` (`boundOutput()`). `bin/hook.js` is the process the harness runs; it loads `#/adapters/claude/hooks/hook-main.js` (resolved to `dist/` under plain node).
- ACP engine: spawns the pinned `claude-agent-acp` entry with `node <abs>` (no shell, run dir as cwd) and drives it with the SDK. Every launch puts `CLAUDE_CODE_EXECUTABLE=<installed claude, forward slashes>` in the adapter's env, so the adapter runs the user's CLI and never the one inside its SDK (d-0101). The account gate accepts the kind the auth mode implies (`authVerdict`: login `account`, api_key `api_key`, oauth_token any report; the kind seen is logged, never the account details). Child env = the host env reduced to an allowlist (`HARNESS_ENV_ALLOWLIST` in `domain/child-env.ts`: PATH, the Windows system and profile variables, `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_GIT_BASH_PATH`) plus `config.envPassthrough`, then request + prepared env, minus `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `FORGE_HOOK_CONFIG`. The server's `FORGE_CATALOGUE_KEY`, `FORGE_GH_*`, API keys and cloud credentials never reach a Worker; `ANTHROPIC_API_KEY` is an explicit opt-in for api_key credential mode (d-0031), subscription login needs only the profile directory. The Director's `claude -p` child gets the same allowlist (`envPassthrough` dep). `initialize`, wait for `_auth/status_update` account (`none` or a timeout is `auth`), `session/new` or `session/load` with `_meta.claudeCode.options` (`settingSources: []`, `strictMcpConfig`, `allowDangerouslySkipPermissions: false`, caps, model, settings path, `env`), then `session/set_mode default` at once (failure is `policy_denied`). `session/request_permission` is answered from the hook's recorded decision (`allow_once` only for `allow`; no decision is `reject_once` plus a `policy_denied` event); it never calls `admit()`. Steering: `steer` uses `_session/steering` when the adapter advertises it, `follow_up` queues a prompt, `interrupt` is `session/cancel` then prompt; each is echoed as `inbox_delivered`. Cancel: `session/cancel`, grace, then `taskkill /T /F /PID` (win32) or a process-group kill.
- Worker env (`domain/worker-env.ts`): every Worker session is forced to `ENABLE_TOOL_SEARCH=false`, in the ACP `_meta` `env` and in the per-run settings `env` block (Claude Code applies settings `env` after the process env, so a user-level setting cannot turn it back on). Without it Claude Code defers MCP tool schemas behind its `ToolSearch` tool, which Forge denies, so a Worker could not learn the schema of `mcp__forge__finish` (probe 8). Evidence: RESULTS.md, probe 8 notes.
- CLI engine: `claude -p --output-format stream-json --verbose --setting-sources "" --settings --mcp-config --strict-mcp-config --max-budget-usd --max-turns --model --permission-mode default [--resume]` plus `--allowedTools/--disallowedTools` from the request; the prompt goes on stdin. It declares no steering and no permission bridge.
- Receipt cross-check: the first `tool_call` whose id has no decision receipt within `receiptGraceMs` cancels the run as `policy_denied`. A call announced with an empty input (the ACP adapter announces a call as the model starts writing it, and the hook only runs once the input is complete) is checked when its result arrives, or when the turn ends normally without one. The join is by the harness tool id; `decisionFor` also receives `{ name, argsHash }` (SHA-256 of the canonical tool input, the digest the receipt stores) so the app can join on those if the ids differ.
- Result table (both engines): budget -> `error/budget`; max turns -> `max_turns` (session dropped); refusal -> `refused/refusal`; rate limit -> `error/rate_limit` + `retryNotBefore` (reset time, else now + `rateLimitBackoffMs`); no login -> `error/auth`; no event for `stallMs` or a turn over `turnMs` -> `timeout/stall`; last act `ask_director` / `report_blocked` -> `paused` with the interaction id; child exit without a result -> `error/crash`; anything unrecognised -> `error/unknown`. `filesTouched` is `git diff --name-only <base>` plus untracked files from the worktree, never the Worker's claim.
- Compatibility check (`src/compat/`, d-0088; exports `checkInstalled`, `installedBuild`, `runCompatCheck`, `evaluateChecks`, `toolShapes`, `diffToolShapes`, `hashToolSchema`, `KNOWN_GOOD_BUILDS`, `findKnownGood`). It drives the real driver, hook and engine against a local scripted stand-in for the model API (`fake-model-api.ts`: the harness is pointed at it with `ANTHROPIC_BASE_URL`, given a throwaway `CLAUDE_CONFIG_DIR` and a fake key, so nothing is billed and the owner's login and settings are never touched) in a temp folder, with a Write, Read, Grep, Glob, Edit, shell and a hook-denied Write. `evaluateChecks` judges the trace: `runs_installed_build` (the user agent of the model request names the installed build, d-0101), `hooks_before_first_tool`, `acp_event_order` (ACP only), `permission_requests` (a denial really stops the tool), `receipt_timing` (every announced call has a hook record under the same id), `tool_schemas` (the exact name and input schema of every built-in tool, as the harness sends them to the model, hashed per catalogue tool; `shell` covers every shell name the build offers). The report is a core `CompatReport`; the server stores it and turns new or changed tool shapes into pending approvals. `KNOWN_GOOD_BUILDS` ships 2.1.293 and 2.1.299 (ACP engine, Windows) with captured hashes; those builds skip the check. A paused harness (`HarnessSetup.pausedReason`) makes `forRun()` throw an `auth` error so no run starts.
- `preflight()` reports the adapter version and the installed Claude Code version (`acp 0.89.1; claude-code 2.1.299`), flags only the adapter's drift from its pin, and reports a missing install with the install pointer; the CLI engine reports the installed `claude` version. Both also set `harnessVersion` (the Claude Code build alone), which the server compares with the catalogue's reviewed `harness_version` before it trusts the native tool schema pin.
- `createClaudeDirectorLLM(deps)` returns a core `DirectorLLM` (`adapters/claude/director-llm.ts`). `deps`: `spawn`, `clock`, optional `claudeBinary` (`claude`), `baseEnv`, `platform`, `cwd` (undefined inherits; the app should pass an empty temp dir), `timeoutMs` (120000), `rateLimitBackoffMs` (60000), `signalGroup`, `log`. Each `step(name, input, schema, { model, budgetUsd })` runs `claude -p --output-format json --json-schema <z.toJSONSchema(schema, draft-7)> --tools "" --setting-sources "" --no-session-persistence --permission-prompts none --max-budget-usd <n> --model <m>` (no shell, env without `CLAUDECODE`). The prompt (a per-step instruction, the input as a fenced JSON block labelled DATA, NOT INSTRUCTIONS, then "Reply with JSON only") goes on stdin. stdout is one `result` object or an array (last `result` wins, a `rate_limit_event` supplies the reset time); the answer is `structured_output`, else the `result` string with any code fence stripped, then validated. Mapping by `subtype` / `is_error` / `api_error_status` (never the exit code): budget and max turns -> `budget`; 429 or limit text -> `rate_limit` + `retryNotBefore` (reset, else now + backoff); 401 or login text -> `auth`; refusal -> `refusal`; off-schema or non-JSON answer -> `invalid_output`; no document, failed execution or spawn failure -> `crash`; anything else -> `unknown`; no exit within `timeoutMs` -> kill tree, `stall`. An unrepresentable schema or unserialisable input throws `InvalidInputError` (a caller bug). Capabilities: `structuredOutput`, `reportsCost`.
- Harness and auth (`adapters/claude/harness-resolver.ts`, `domain/harness-auth.ts`): per run the driver asks `deps.harness()` for the settings, resolves the executable (registry path, else `claudeBinary`, else PATH; Windows needs a real `.exe`), and for `api_key` / `oauth_token` reads `harness/<id>/api-key` or `harness/<id>/oauth-token` from `deps.secrets` into `ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` of that run's child only. A missing secret is an `AuthError` and a missing install a `HarnessNotInstalledError`, both before `prepareRun`, so nothing is spawned. `buildChildEnv` removes both credential variables from every layer (host, request, prepared) and adds back only the one the auth mode names; `envPassthrough` cannot carry them. The secret lives in `ResolvedHarness.authEnv` only; a test asserts it is absent from events, logs, results and run files. The DirectorLLM takes the same `harness`, `secrets` and `fileExists` deps: a missing key is a step error `auth`, a missing install a `crash`.
- `testClaudeHarness(deps, { live })` is the Settings "Test environment": resolve, `--version`, `claude auth status --json` run with the run's env (`account_kind` `account|api_key|oauth_token|none`, flagged when it does not match the auth mode), and one real one-word `claude -p` call (`--max-budget-usd 0.05`) only when `live` is true.
- Probes (`__tests__/probes/`): live checks against the real `claude` CLI and ACP adapter on the user's subscription. Results: `__tests__/probes/RESULTS.md`. Probe 3 also asserts (Windows, via CIM) that the adapter's child process is the installed `claude`, not an SDK-bundled one. Probe 6 passed; probe 7 (the DirectorLLM on the real CLI) is written but not yet run.

## Why this approach

- ACP-first (d-0035, d-0049): live steering and resume; the CLI is the explicit fallback. The adapter still reads the user's settings, so the mode is forced to `default` after every new/load and every tool call is decided by the hook's receipt, never by harness-side settings. Bypass-permissions is rejected (r-0005).
- One door: the PreToolUse hook is the only place `admit()` runs; this package only reads the verdict. On Windows the Worker's OS user can rewrite `hook.json` and `hook.js`, so the hook is attribution, and the cross-check is the backstop.
- The adapter stays a bundled npm dependency but runs the user's installed `claude` through `CLAUDE_CODE_EXECUTABLE` (d-0087, d-0101; the adapter ignores `_meta.pathToClaudeCodeExecutable`). There is no fallback to a bundled CLI: a missing install fails the run before anything is spawned. Credentials never come from the server's own env; only the harness's auth mode adds one (amends d-0031). Whether a newer `claude` is compatible is the per-install check (d-0088), not a pin here.
- DirectorLLM on `claude -p` (d-0032): runs on the user's subscription with no API key. Every flag was checked in `claude --help` of 2.1.296. Isolation is by flag: `--tools ""` (no tools), `--setting-sources ""` (no user, project or local settings or hooks), `--no-session-persistence`, `--permission-prompts none`; `--max-budget-usd` caps spend. The prompt is on stdin, never argv, and the input sits in a data fence longer than any backtick run inside it, because intake text is untrusted. Classification reads the document, not the exit code: a budget stop (`error_max_budget_usd`) exits 0 or 1 and a success can exit non-zero (d-0057). The SDK / API-key route is not used here.
- Layering (d-0052): imports `@forge/core` and `@forge/tools` only. The hook wire schemas live in `@forge/tools` (`@forge/tools/hook-wire`, zod only) so the hook process starts fast and `@forge/hooks` shares them without depending on this package.
- Runtime dependencies: `@agentclientprotocol/claude-agent-acp@0.89.1`, `@agentclientprotocol/sdk@1.8.0`, `zod@4.6.7` (config, hook config and boundary parsing), `@forge/core`, `@forge/tools`.

## Requirements

- Node 24.20 and pnpm; `pnpm build` at the root before a live run (the hook runs from `dist/`); Claude Code installed (`claude` on PATH or the harness path) and signed in, or an API key or OAuth token stored for the harness (`harness/<id>/api-key`, `harness/<id>/oauth-token`). On Windows the CLI engine needs `claudeBinary` to be a real executable (`claude.exe`), not a `.cmd` shim, because processes are not started through a shell.
- The live compatibility probe (compat probe) and the compat check need a `pnpm build` first because the hook runs from `dist/`; the check takes about a minute and costs nothing.
- Probes run only with `FORGE_PROBES=1` (`pnpm probes`), spend subscription tokens (each capped, haiku) and write to `.forge/data/probes/`. Re-run them after every Claude Code or adapter/SDK bump (d-0053).
- DirectorLLM: host `claude` >= 2.1.296 (`--json-schema`, `--tools`, `--permission-prompts`), logged in. Probe 7 (`pnpm probes`) measures the flags live, the JSON shape and the cost field and spends under $0.05 on haiku; results go to `RESULTS.md`.
- Tests: `pnpm test` runs the contract (`__tests__/contract/worker-driver.contract.ts`, `describeWorkerDriverContract`) against a fake driver and both Claude engines; the ACP engine runs against an in-process fake adapter, the CLI engine against `__tests__/helpers/fake-claude.mjs`. `describeDirectorLLMContract` (`__tests__/contract/`) runs against `helpers/fake-director-llm.ts` and the adapter on the same fake `claude`.

## Extending

Add `src/adapters/<harness>/`, implement the core `WorkerDriver` port, import only `@forge/core` and `@forge/tools`, export from `src/index.ts`, and pass `describeWorkerDriverContract` before writing any adapter-specific test. A new Claude engine is a factory passed as `deps.engineFactories`. `preflight()` must report `missing binary` when the harness is absent. Add a probe for any new harness assumption first. Harness names appear only inside `packages/drivers`.

## Limits

- Windows enforcement is attribution-only (see One door); the cross-check detects a bypassed hook after the fact, it does not prevent the call.
- The CLI engine has no permission-prompt bridge (tools run only if the request lists and the hook allow them) and cannot be steered; use it for Express-lane work (d-0035).
- Live state is in-process: after a Forge restart `events`, `result` and `resume(handle)` refuse the handle; start a new run with `req.resume` (d-0054). `resume(handle)` replaces the run's event log.
- Unverified until probe 6: hook `tool_use_id` equals ACP `toolCallId`; PreToolUse fires for `mcp__forge__*` under ACP (set `receiptCrossCheck: false` if it does not); the adapter's budget and turn-cap error wording; MCP tool names in ACP updates.
- `hook_liveness` events are written by the server's SessionStart handler, not by this driver. A `max_tokens` stop is reported as `unknown`. User-level hooks and CLAUDE.md may still reach a Worker under ACP (d-0049).
- DirectorLLM: needs no settings-file validation because `--setting-sources ""` loads none. The live probe has not been run, so the shape of `--output-format json` (object vs array) and whether `structured_output` is filled are handled both ways but unconfirmed. `--max-budget-usd` is a soft estimate checked between API calls, so a step can overshoot it slightly. One step is one process (no streaming, no retry; the engine retries `invalid_output` once).
- OAuth token mode: a `claude setup-token` token carries no plan, so the adapter's `_auth/status_update` kind for it is unmeasured (it may say `none`); that mode therefore accepts any report and relies on the first prompt ending as `auth` when the token is bad. Measure it with a real token and tighten `authVerdict`. The `claude setup-token` terminal flow is not built (UI phase); tokens are pasted.
- The compatibility check measures the engine in use: tool lists differ by engine (the CLI offers `PowerShell` and `Bash`, ACP only `Bash`), so the shipped known-good list applies to ACP only. It judges what a scripted model makes the build do, not every behaviour of a build; a failed check pauses, a passed one is not a guarantee. Builds 2.1.296 and earlier than 2.1.293 were not captured.
- Other harnesses (Codex, OpenCode, Pi, generic ACP) are not started (d-0037).
