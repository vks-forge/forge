# @forge/engine

The Director's engine: tick, dispatch, settle and the model steps, as pure orchestration over ports.

## Why it exists

The Director is the one writer that turns "someone asked for something" into "a Worker ran in a
worktree and the ticket moved". Its guarantee is that no ticket is silently lost and no run is
started twice, and that guarantee only holds if the sequence is decided in one place: intake
becomes a ticket, triage names its lane, dispatch starts a Worker run, the run pump stores the
Worker's events, and when the run ends the ticket moves on or is retried or is handed to a human.
Without this package that logic would sit in `apps/server` (which must only compose) or in `core`
(which must stay types and pure rules), and could not be tested against fakes (d-0058).

Actors: the app (`apps/server`) owns the clock and the HTTP side and calls the engine; the engine
talks to storage, the Worker driver (Claude Code today), the Director's own model (`DirectorLLM`),
git worktrees, project memory and the receipt chain, all through ports.

## What it does

Public API from `src/index.ts`: `createEngine(deps)` (an `Engine`, below), the pure rules `decideLane`, `decideFailure`, `findViolations`, `nextTicketNumber`, `pickNext`, `orderCandidates`, `chooseHarness`, `describeWait`, `requestWake`, `LIVE_LANES` / `isLive`, `loadScorecardInput`, `warnOnBudget`; storage reads for the owner's confirmations `replanImpact(tx, ticket)` (tickets a Re-plan would hold or keep, by the plan-keep rule) and `openDependents`; process-edge helpers so `apps/server` holds no port implementation: `createIdSource()` (random `run-`/`wake-`/`int-` ids and 256-bit base64url run tokens from the OS random source), `createOwnerId()`, `createJsonLogger(write, min?, now?)` (one JSON line per call, never throws, redacts credential-looking field names); `ProjectRuntime` and the engine types.

### Engine methods

- `tick()`: Reconcile, refresh, release lane holds, verify, advance stages, dispatch, then the invariant sweep. Single-flight (a call during a tick returns that tick's `TickReport`). The app calls it every `engine.tick_interval_ms` (30 s safety sweep) and when `deps.onTickRequested` fires. Director card turns run as jobs beside it, so a tick never waits on a model call.
- `requestTick()`: Coalesced "tick soon"; also made by every event that can start work (intake, run events, a settled run, a finished job, an answer, an approval, an edit, a cancel, a merge) and by the one timer (`tick/tick-timer`) for the soonest `not_before` wake, quota pause or hold.
- `ingest(event)`: Stores an intake event (deduped) and maps it (below).
- `createCard(input)`: The create-card form door (below).
- `setCardRelations(cardId, {depends_on, blocks, actor})`: Replaces the card's dependency edges (the set is complete: an edge left out is removed) after the same checks as `createCard`, and writes a `note`.
- `editTicket(ticketId, {body?, priority?, depends_on?}, actor)`: The one ticket edit door (`tick/ticket-edit.ts`; `editTicketTx` inside a caller's transaction): `checkTicketEdit`, then fields and the complete `depends_on` set in one transaction with a plain-words card `note`; `updated`, `ticket_not_found`, `stale` or `refused` with the rule's code. The chat actions `set_ticket_dependencies`, `set_ticket_priority`, `edit_ticket_description` use it; `create_ticket.restores` keeps a restored ticket's priority; the chat context lists `owner_controls` and each ticket's `plan_key`.
- `postCardMessage(cardId, text, author)`: Card chat (below).
- `cardDirector(cardId)`: `thinking` while a reply is queued or running, `error` after a failed reply until the next message, else `idle` (process-local).
- `steerRun(runId, message, author)`: Direct user-to-Worker message (d-0109): no model call, no tick wait, `steer` mode only. Writes the run inbox row and a `user_message` run event in one transaction, calls `driver.steer(handle, text, 'steer', inboxSeq)`, then marks the row delivered. Result `delivered {inboxSeq}`, `not_live` (no live pump here, run not starting/running, or owned by another server) or `unsupported` (driver lacks `steer`, or the session refused with `InvalidInputError`; the message stays undelivered). Any other driver failure throws. Never falls back to `follow_up`: that would change what the person asked for.
- `answerInteraction(id, answer)`: CAS answer, queues the `response_wake`.
- `cancelTicket(id)`: Alias of the one cancel door `cancelFlow()` (also behind `actOnTicket` `cancel` with an optional `reason` and the Director's `cancel_ticket`; history reads "You cancelled it: ..." or "The Director cancelled it: ..."; a ticket others wait on is refused without `cascade`). `cancelled` through `transition()`, cancels the live run and waits up to 10 s for it to stop, then removes the worktree and local branch, closes its open PR and deletes its pushed branch on the host, and writes one card note with the last commit id so the work can be recovered (`tick/workspace-cleanup.ts`, the one helper every no-merge end uses: cancel, a re-plan that replaces tickets, the first-tick sweep, and a retry next tick when a removal failed; d-0179). PR close and remote delete are best effort (a host that is down is logged, a merged PR is left alone) and never forced.
- `interruptRun(runId)`: Shutdown path (`tick/interrupt.ts`): marks a live run `interrupted` with its harness session (`resumable_session`, from the pump's `session_ref`) and `interrupted_at`, flags its pump so no tick settles the stream that ends because of the stop, then `driver.cancel`s the harness. Token, worktree and receipts are kept; a run whose result already arrived settles normally.
- `explainWait(ticketId)` / `explainWaits(ids)`: Why a ticket has not started: one line (`quota: claude-code until 14:20 UTC`, `cap: per-project 1/1`, `deps: PAY-231`) or null; `explainWaits` returns the `TicketWait` (phase, plain line, slot `holders`, `blockers`) of many tickets from one `planDispatch`. Holders are tickets with a live run, a workspace being prepared or a brief being written. A `waiting_human` ticket with no open owner item is `held_by_plan` (its card re-plans) or `stuck` (logged once at `warn`). Read-only, from the same decision dispatch makes.
- `closeCardWork(cardId)`, `reviewOf(ticketId)`: Close a card's work; read the diff stat and gated commit for the ticket page (below).
- `actOnEscalation`, `actOnTicket`, `raiseToolApproval`: Owner actions and the tool-approval door (below).
- Planning doors, `cardPlans`, `cardPlan`: Below.
- `liveRunIds()`, `gateJobsInFlight()`, `directorJobsInFlight()`, `idle()`, `unservableProjects()`: In-flight state: live runs, gate runs and script jobs beside the tick, Director jobs; projects the engine skips for invalid settings.

### Intake, cards and chat

- `ingest` maps `new_request` to a card (`<PROJECT>-C<n>`, type from the payload's `card_type`, default `issue`, checked against the card type registry and its allowed sources; unknown or refused is `ignored`) in phase `grilling` with a `user_message` event and a queued Director reply (`card_created`), and no ticket. Only a type that starts tickets at intake (`pr_issue`, the PR fast path) also makes an `inbox` ticket (`<PROJECT>-<n>`) linked by `card_id` with a `ticket_created` event; its card starts `queued` and no Director turn is queued. `reply` goes to the answer of the one pending question or to a queued steering message for the live run. The engine does not know ticket sources: the app's trigger registry decides which reach `ingest`.
- `createCard` (`tick/card-create.ts`): validates the type (it must take chat) and the dependencies, creates the card in `grilling` with title and description as the first `user_message`, and queues the reply, in one transaction; a repeated `dedupe_key` returns the first card (`duplicate`). Typed refusals, not throws: `project_not_found`, `project_archived`, `invalid_type`, `card_not_found` (a dependency id that is no card), `cross_project_dependency`, `dependency_cycle` with the loop (`findCycle`). No ticket.
- Card chat: `postCardMessage` stores a `user_message` on an open card (`stored` with the event, `not_found`, `closed`) and the owed reply in the durable `card_reply_queue` (same transaction) for the next tick's `card_chat` step (d-0109, d-0134). The step (`tick/card-chat.ts`, before triage) gets the card, its last 30 events, tickets with run state, pending questions, spend against the budget cap, the allowed actions and the project memory slice, as one JSON input the driver fences as data. Its `{reply, actions}` output is parsed against `CardChatOutput`; each action runs only through an existing door (`tick/card-chat-actions.ts`): `create_ticket` through the intake inserter (`tick/ticket-insert.ts`: numbered, `inbox`, linked, triaged the same tick), `steer_run` through `steerRun` on the live run of one of the card's own tickets (author `director`), `change_type` by the PATCH rule, `suggest_close` as a `close_suggested` event only, `cancel_ticket {ticket_id, reason, cascade?}` through `cancelFlow()` (`tick/card-chat-cancel.ts`: only an open ticket of this card; one others wait on is refused naming them unless `cascade`). An executed action writes `director_action` in the same transaction; a refusal (type forbids it, closed card, card still grilling/verifying/awaiting plan approval, ticket of another card, no live Worker, same or unknown type) writes a `note`; the reply is then written as `director_message` with `actions_taken`. Invalid output or a model failure sets `error` and writes a plain `note`; the tick never crashes.
- Card close, review merge, settle guard: `closeCardWork` (called by `PATCH /cards/:id` after a close commits) and the every-tick `sweepClosedCards` cancel the unfinished tickets of a closed card through `transition()`, close their waits, stop live runs and remove worktrees, with one card note; no escalation is raised for a closed card (`raiseEscalation` returns null, backfill and the first look skip it) and a reopened card does not revive cancelled tickets. `actOnTicket` accepts `approve` (tier B, `review`) and `sign_off` (tier C, `needs_signoff`, signer named or the owner): `tick/review-merge` resolves the verify target, asks `decideMerge()` (`domain/decide-merge.ts`, shared with the automatic merge: a failed gate passes only when the owner overruled this run's G1 stage, and the card note names it) and calls `mergeReviewed()` in `verify-merge.ts` (still the only caller of `GitHost.merge`), which merges exactly the gated sha; a moved head merges nothing, sends the ticket back to verifying (event `regate`) and answers `head_moved`; a refusal answers `merge_refused`. Each run settles in isolation (`tick/settle-guard`): a throw is logged with the run id and counted, and a run that fails three ticks in a row is closed as an error and its ticket parked with a failure escalation. The receipt chain is read before the settle transaction (the receipt log shares the writer lock). A ticket filed on a `done` card moves it back to `in_progress` (`resume_work`). Planning writes are stamped with the clock at the write (`stamp()`), after `step_started` was committed before the model call.
- Card phase changes only through `tick/card-phase.ts` (`moveCardTx` runs `transitionCard`, stored with a CAS on `phase_version`); `syncCardWithTickets` (inside `moveTicketTx`) makes the card agree with its tickets both ways: starts a `queued`/`approved` card with its first unfinished ticket past the inbox, completes it with its last live ticket done, reopens a `done` card (`resume_work`, "Reopened" note) when a live ticket is not done (also the path for a new ticket on a done card: `insertInboxTicket` calls it), and keeps the stored `needs_you` flag in step with owner waits (set when every ticket of an in-progress card was cancelled, with a note). `sweepCardPhases` (`tick/card-sweep.ts`, every tick; the first tick checks every card) repairs cards that already disagree. A card is created only by `tick/card-create.ts`. Card history is written by `tick/card-log.ts` inside the transaction of the change it describes (`ticket_state` from `moveTicketTx`, `interaction_opened`, `interaction_answered`); a `ticket_state` event carries a plain `reason` where known (`TicketPlan.reason`: a Worker started, an answer resumed it, a re-plan, card close or owner cancel, an owner override, a lane's pipeline going live, Run as Express, a rework comment) else the parked `blocked_reason`. Forge's publish commit carries `Forge-Ticket` / `Forge-Run` trailers (`commitMessage`).

### Card planning

- Flow (`tick/card-planning.ts`, `planning-*.ts`, d-0130 to d-0150): a card of a planned type (not Discussion, not a fast-path type) in `grilling`, `verifying` or `plan_ready` is planned instead of chatted with. Starting snapshots the effective flow (`flow_json`, cursor, config revision); each turn (a Director job, `tick/director-jobs.ts`) walks the flow from the cursor, one Director call per step, each recorded in one transaction (`step_started`, `step_finished` with files read and config version, the grill state, the cursor), until a step needs the owner or the flow ends. Default flow: `survey` (read rounds), `grill` (one question per turn, options, one recommended, `open_points`, limits per round), `verify` (read rounds, pins HEAD), `enhance` (standard and full lanes; its owner questions are asked one at a time before the plan is written), `write_plan` (versioned plan, decisions and verification filled by the engine, diff from the previous version; the planner answers `decision_checks` for every owner answer, a missing index is retried once, a `conflict` or a non-goal negating an answer is stored as `decision_conflicts` and fails the floor; risks and assumptions merge through `dedupeStatements`, the planner sees `known_risks`), `approve`.
- Reads (`tick/planning-read-step.ts`): `survey` and `verify` answer `read_requests`; round 0 of the survey is shown `repo_files` (up to 400 tracked paths) and findings with no file read while the repo has files are sent back with `previous_error`, then kept with `survey.read_nothing` so the grill says it could not look; the engine runs each through `admit()` (`admitDirectorRead`, `@forge/tools`) and `deps.repoReader` (git-tracked files at HEAD only), under `read_caps`, and calls the step again with `read_results`, two rounds at most. The approval floor (`checkFloor`, facts from other approved cards' plans and git) runs first; only a passing plan with approval mode `director_or_user` reaches the tool-less `approve_plan` step, which sees only the plan, typed findings and floor result. Otherwise the card goes to Needs you with `approve_plan` and `request_changes`.
- Spend: Director step spend counts on the card through `addDirectorSpend` only (a dated `director_spend` ledger row plus cached `director_spend_usd` in the grill state; a failing call and rounds before a failed round still record what the harness reported; `budget_warning` once per level against `effectiveCardBudget`, never a block). A failing step writes a note and leaves its queued turn claimed, retried when the claim goes stale (10 minutes). `planning sweep` (`tick/planning-sweep.ts`) queues the first turn of planned cards with no flow (a converted Discussion) or with queued owner questions but none open and no turn owed, and nudges an unanswered question after 24 hours (never answers it). A planning turn that took an owner chat message always writes a Director event after it: with no question, step or note, a plain `director_message` says the message was kept and nothing ran, and the engine logs a warning.
- Doors (typed `status` results, never throws for a wrong moment): `answerGrill(cardId, {question_id, option_id | text}, author)` (`answered`, `question_not_open` 409, `invalid_answer`); `grillShortcut(cardId, 'use_recommendations' | 'write_plan_now', author)` (`applied`, `phase_mismatch` 409); `approvePlan(cardId, version, author)` (`approved` with `ticket_ids`; cancels only earlier tickets the core keep rule calls replaceable: no run, branch, worktree or open item; `cardPlans` lists `will_cancel` and `not_covered`, the second also blocking the Director's own approval through the floor; idempotent per version; `stale_plan`, `phase_mismatch` 409; `plan_not_found`); `requestPlanChanges(cardId, version, comment, author)` (`requested`, `invalid_comment`, `stale_plan`, `phase_mismatch`); `editPlanTickets(cardId, version, {tickets, order?}, author)` (`edited` with the new owner version, `ticket_has_dependents` 409, `unknown_ticket`, `invalid_order`, `empty_plan`, `stale_plan`, `phase_mismatch`); `startPlanning` (`started`, `phase_mismatch`, `not_plannable`); `retryPlanningStep(cardId, author)` (`retried`, `not_found`, `phase_mismatch` when the card is not stopped on a budget failure); `runAsExpress(ticketId, author)` (`released`, `not_held` 409); reads `cardPlans(cardId)` (versions, current plan, floor computed now until approval, then `floor: null` with `floor_frozen_at`) and `cardPlan(cardId, version)`.
- Approval (`tick/plan-to-tickets.ts`) files the plan's tickets dependencies first (priority urgent 3, high 2, normal 1, low 0; `blocked_by` from the plan keys), moves the card through `transitionCard()`, and gives each ticket `triaged` with the stricter of the plan lane and `preCheckLane` over the ticket's own `body` and files (`tick/plan-ticket-lane.ts`; a raise is written on the card with its reasons; `lane_by_owner`, set by `editPlanTickets` with a `lane`, skips the size raises, Tier C still forces Full; Tier C files make it Tier C); a planned ticket whose lane is not live (`LIVE_LANES` is all three lanes now, so this only holds a lane a later build adds) is parked with wait reason `pipeline_pending` and a lane-hold escalation offering `run_as_express`; the engine releases the hold itself once the lane is live (`tick/lane-hold-release.ts`, before triage).
- Research (d-0143, d-0144, d-0146): `tick/planning-research.ts` (`researchStep`, `runResearch`) is the research flow step and the loop it shares with the grill's research detour (`tick/planning-detour.ts`). The tool-less `research` step answers `research_requests` (at most `director.research.max_rounds`, then it must answer, else a rejected step) or `findings`. `tick/research-run.ts` runs each request in the strictest order: the run's caps (a hit is a "cap reached" row), fetch provenance (`fetchAllowed`: only URLs from this run's search results, the card or the owner's answers), `admitResearch` (`@forge/tools`), then the provider; pages are held in memory with `S<n>` refs and every result is wrapped in an untrusted-content envelope; the owner may allow up to 100 pages a run (d-0171), so `fitResultsToPrompt` keeps at most 400 000 characters of page text in the step's input, newest first, older pages keep their ref but lose text (the stored page is whole). `tick/research-store.ts` is the only writer of the Director's sources and evidence: in the transaction of the finished step it stores pages, checks every quote against the stored text (`checkClaims`, so the model never sets a status), stores claims and logs the `research` card event; a failed or restarted run leaves nothing and reruns from round one with the same numbering. The step runs unless `step_decisions.research = false`; a provider that is off, a project with research off, the per-card run limit or a server that does not answer is a card note, an empty result, and the flow goes on. `write_plan` may name `outside_claims`; `composePlan` attaches the card's evidence and the engine marks each claim supported or unverified; the floor adds one reason per unverified claim, and the approval step sees claims, refs and statuses but never a quote or page text. Card spend counts research calls and the provider's price and only warns; a warning belongs to the cap it was written for, so a changed cap warns again. `EngineDeps.research` is the one provider (absent means none).
- Memory context (d-0168): `tick/memory-context.ts` `buildMemoryContext(ctx, project, { question, rewrite, filter, cardId })` is the one way the six steps that read project memory (triage, planning, card chat, dispatch, `ticket_answer`, `ticket_recover`) get `{ decisions, rejected, note? }`. With `EngineDeps.memoryIndex` it shows pinned decisions (at most `director.memory.pinned_max`) plus the `top_k` most relevant (search actor `director`, scope from core `directorScope()` or the agent slice through `workerScope()`), with the note "Showing N of M active decisions: pinned and most relevant; all rejected approaches are listed"; a project with at most `pinned_max + top_k` active decisions is sent whole with no note, and every rejected approach is always listed (newest first up to `rejected_max`, past that most relevant first, with its own note). Without `memoryIndex` the old `MemorySource.slice` is read unchanged. `tick/memory-rewrite.ts` `rewriteQuestion()` is the `memory_rewrite` step (planning and card chat only; the other four use core `extractTerms` of ticket title and body, no model call): it runs only when something is left out, with `rewrite_budget_usd` and `rewrite_timeout_ms` (the call is raced against the timeout), is cached per (project, sha256 of the question) for the process, drops tags outside the project's vocabulary, falls back to plain keywords on a timeout, invalid answer, budget stop or any error (never throws), counts its cost in the card's Director spend, and leaves a `memory_retrieval` trace entry naming the source (`model`, `cache`, `fallback`). `tick/planning-rejected.ts` `planRejectedHits()` reads the full `MemoryIndex.rejected()` list when a plan is written and adds to `verification.rejected_hits` every rejected approach whose distinctive words (at least 60%, at least two) appear in the plan's goal, scope and tickets, so one the search left out of the prompt still sends the plan to the owner. `loadChatContext` takes the `EngineCtx`. Express keeps its pasted slice through the same function (the golden dispatch fixture is unchanged).
- Director jobs (`tick/director-jobs.ts`, `EngineState.directorJobs`): card turns (`card_chat`, planning) run beside the tick like gate jobs; starting one never awaits it, its end requests a tick, and the next tick collects it (`collectDirectorJobs`: the job's own report, made by `jobCtx`, joins that tick's, so a rejected step is not lost). Keys `card:<id>` / `ticket:<id>`: one job per key. `director.max_concurrent_steps` (1 to 8, default 3) bounds jobs executing at once (`directorSlots`); `runCardChats` claims with `exclude` (cards in flight) and `maxCards` (free slots), owner messages first. A job stamps writes after a model call with the clock now (`liveCtx`); `launchRun` stamps `started_at` and `last_event_at` at spawn, and `moveTicketTx` never sets `updated_at` below `created_at` or the last write. `idle()` waits for jobs; tests use `tickToIdle`. Ticket steps compute in the job and apply in the tick: triage, steer replies and escalation looks return a `DirectorApply` that the collecting tick runs after re-checking the ticket (still in the inbox, run still live, wait still pending), else the answer is dropped; `startTicketStep` needs a free slot and no job on the ticket, and phases that move tickets (triage, escalation sweep, dispatch, setup recheck) skip a ticket with a job in flight. Slots go in phase order: steer replies and escalation looks (a Worker waits), card turns, triage last.

### Dispatch, runs and resume

- Per tick, in order: restart reconcile on the first tick (`tick/restart.ts`, d-0092: a run lost without a shutdown, still `starting`/`running`/`settling`, that had reported a session is recorded `interrupted`; one with none is crash-settled with wake reason `crash`); resume interrupted runs; settle finished runs (skipping interrupted pumps); cancel runs silent for `stall_ms` and settle them as `stall`; expire overdue questions (ticket to `blocked`); deliver steering replies (`steer_reply` step, then `run_inbox`, then `driver.steer`); triage `inbox` tickets (pre-check, `triage` step, lane rule); verify finished work; dispatch ready tickets.
- Resume: interrupted runs are resumed within the scheduler's limits (`pickNext` with global, per-project and per-harness caps and any quota pause, d-0097; one that does not fit stays `interrupted` and the invariant sweep counts it as explained). A resume is done on the same row: generation + 1, a new token (`runTokens.reissue`, the old hash dies), `hook_registered_at` cleared, then `driver.start({ ...req, resume: session, generation })` with a continue prompt (`RESUME_PROMPT`, which also tells the Worker that a call refused as `server_draining` is to be made again). A run that cannot be resumed (no session, a harness that cannot resume, worktree moved, ticket ended, `start` throws, or the resumed harness ends before reporting anything) settles `interrupted -> settled` with family `crash` and a `retry` wake with reason `resume_failed`, so the ticket continues as a new run in the same worktree. Resumes queue at their ticket's priority on the same rotation cursor as new starts and read the schedule without consuming wakes or pauses. A start that fails before the app wrote the chain's `resumed` link gives the generation back (the receipt chain must read 1, 2, 3 without a gap for G1); a written link keeps it. Each run resumes on its own: a throw (a project runtime that cannot be built, a store error) is a tick error `resume <runId>`, the run stays `interrupted` for the next tick and the others still resume; runs of an unservable project are skipped first. The report lists `resumed`, `resumeFailed`, `crashed`.
- Dispatch is two-phase: the tick picks, reserves the slot in `state.briefing` (counted as running by `planDispatch`, ticket not a candidate, In Progress limit included, d-0097) and starts a `brief` job (worktree, preparation, memory, `dispatch_prompt`; no Director slot, so Workers never queue behind planning; `tick/dispatch-brief.ts`); the next tick re-validates the candidate and launches (`tick/dispatch-launch.ts`: wake still due, same writer due, ticket not cancelled, else the brief is dropped and a cancelled ticket's worktree removed). Parks a brief decides are applied by the tick; a failed brief keeps `rejectStep` + `hold('dispatch:<id>')`. Launch writes the worktree, `dispatch_prompt` step, run row and token hash, `driver.start`, ticket `in_progress`. Run start stores the Worker brief (dispatch prompt plus the appended contract, as the driver receives it, through `scrubSecrets`) as the run's first `prompt` event, in the run row's transaction.
- Parks: a `driver.start` that throws `HarnessChangedError` (installed build is not the one whose approvals were loaded, family `policy_denied`) settles the run and parks the ticket with the error's own text (starts `harness_changed:`); `HarnessToolsPendingError` (the loaded build has a tool pending or its check running) parks it as a `harness_build` setup, and `setupFactsFor` reports the pending tool count so it resumes only once every tool is decided. An unregistered harness is a typed `invalid_input` error: the ticket is parked with the reason (`tick/dispatch-park.ts`), never run on another harness. The worktree manager raising `InvalidInputError` (for example a repository with no commit yet, init-only, d-0124) parks it WaitingHuman ("Needs you"); it dispatches normally after the user's first commit.
- Worktree preparation (d-0180, d-0176): `tryStart` and `startChecks` call `ensurePrepared` (`tick/prep-jobs.ts`) right after `worktrees.create`; it asks `runtime.prepare` for a plan (empty or no `prepare` starts at once, no job, no record), runs it as a background job (`state.prepJobs`, a short grace so a warm tree costs no tick) and answers `ready`, `pending` (the ticket keeps its slot, `schedule.ts` counts the job as running, wait reason `prep`: "Getting the workspace ready: Install packages (0:42)") or `failed` (`parkForSetup`: one owner `worktree_setup` escalation with Try again, Start without setup (`skip_setup`, `tick/setup-skip.ts`) and Cancel; saving new setup steps resumes it through `isSetupFixed`). Gate runs and script jobs call the preparer again first (`tick/prep-checks.ts`): a failure after the Worker changed an input file is a failed `setup` gate row (a rework), any other is a fault retried or parked by family. The record's PATH folders go to the Worker (`RunRequest.pathPrepend`) and to gate and script commands.
- Worker contract: the `dispatch_prompt` input carries `worker_contract` (`domain/worker-contract.ts`), and the same rules are appended verbatim to the prompt under `## Rules of this run`: cwd is already the worktree (never `cd`), one shell command per call (compound lines are denied unattended), the project's exact test command (or the several test-role commands, any of which counts), other checks by role (the gates re-run all), the Worker must end with `finish` and a typed claim for every file it edited (G1 fails a finish without; a later `finish` replaces an earlier one), plus a rework note after a failed gate.
- Run settle records status, usage, cost, error family, the files git says changed, the receipt chain's last hash and revokes the token; the worktree is kept for the PR step. A run that hits `max_turns` is never retried: it parks at once with `max_turns: the run used all <n> turns without finishing`, and the failure carries `limit {kind: 'turns', value, source: 'agent'|'forge', fix_href}` (`domain/turn-limit.ts`, `turnLimitFor` in `tick/outcome-escalate`).
- Scheduling (d-0097; `domain/pick-next.ts`, `tick/schedule.ts`, `tick/dispatch.ts`): dispatch reads one plan (waiting tickets, due wakes, live runs, parked harnesses, the tick's settings) and `pickNext` chooses. A ticket whose setup just finished goes first, then due wakes (retry, resume, rework) before new tickets; inside each group projects take turns in id order, starting after the project that got the last slot (`state.schedulerCursor`), so with any slot at all every project with work reaches the front within as many ticks as there are projects; inside a project the highest `priority` goes first, then the lowest ticket number. A candidate is skipped, with a stated reason, when it has unfinished blockers, its harness is parked, or starting it would pass a limit: global (`max_concurrent_global`, default 2), per project (`max_concurrent_per_project`, default 1; a project's own `max_concurrent` can only lower it), per harness (`max_concurrent_per_harness`, `by_id` over `default` 2), or `max_concurrent_by_state.in_progress`. Blocked and parked tickets sit out of the rotation; a ticket held by a failing step (`dispatch:` / `dispatch_prompt:` holds) is removed before the choice.
- Quota waits (`tick/quota.ts`, `domain/harness-choice.ts`): a run ending with the `quota` family (drivers classify "no available quota" and a rejected rate-limit report as `quota`; a plain 429 stays `rate_limit`) parks `run.harness` in `harness_state` until the reset the harness named, else `quota_default_pause_ms` (1 h); the ticket gets a `retry` wake with reason `quota_wait` at that time (not counted by the re-wake cap) and is not parked; every other ticket on that harness waits too. If the project's `harness_fallbacks` (else the company's) lists an installed, unparked harness, the wake is due at once and dispatch runs the ticket there (a session is resumed only on the harness that made it). Expired pauses are cleared by the first dispatch that sees them.
- Many projects (d-0082): every step takes its project's runtime (`runtimeFor`), never a shared one: worktrees, diffs, commits, removal, gates and the git host all go through the ticket's project, and a run row records its `project`. Ticket numbers count per prefix (`nextTicketNumber(ids, prefix)`). Only a `ready` project runs work: intake for an `archived` project is ignored, and tickets of archived or onboarding projects never spend a run slot. The harness is chosen per ticket from the project's effective `default_harness` (`driverFor`); the run keeps its driver (`Pump.driver`) for steering, cancelling and results. One base branch per project (`tick/project-runtime.ts`): `git_host.base_branch` drives the worktree base, diff base and PR target (`baseRef` serves only projects without a host); a runtime whose `config.slug` is another project is refused (tick error, nothing published).
- Settings snapshot (`tick/tick-config.ts`, d-0085): each tick starts with one read of `deps.config` (`company()` plus `project(slug)` for every registered, non-archived project) and every phase reads that snapshot (`ctx.config`), so an edit saved between ticks applies to the next tick as a whole, with no restart, never half inside one. Company dials (limits, retries, models) come from `ctx.config.forge`; project settings (checks, ecosystems, git host, `tier_c_globs`) overlay the `ProjectRuntime.config` the app built and drive triage, tier computation, the Worker contract and the gates. Each run row stores `config_version` (`c<company>:p<project>`); a company save landing between the company and project reads is detected (each project view names the company version it was merged from) and the read repeated, and a read that never settles marks the mismatched projects unservable for that tick. If company settings cannot be read the tick is skipped with a `load config` error and nothing starts. A project whose stored override no longer validates lands in `TickConfig.unservable` (slug to reason), is reported in tick `errors` as `project config <slug>` and through `engine.unservableProjects()` (the server shows `config_error` on `GET /projects`), and is skipped by triage, verify, dispatch and resume while every other project runs as usual. `requestWake` outside a tick reads the current company settings for the re-wake cap.

### Verify, gates and the stage runner

- Verify (`tick/verify*.ts`, up to `max_concurrent_by_state.verifying` tickets per tick), for a `verifying` ticket whose current run succeeded and whose project `deps.project(slug)` resolves: `commitAll` (Forge author); base merged into the branch (`syncBase` then `mergeIn`, `tick/verify-sync.ts`; worktrees are cut from the host's fetched base, `tick/base-sync.ts`): after a clean merge the gates diff from the new base tip, so main's commits are never blamed on the Worker; a clash, or a resolver's left-over markers that fail G1, moves the ticket back to `in_progress` through `conflict_found` with one `merge_conflict:` continuation wake to the writer (files and upstream tickets' titles), at most `MAX_CONFLICT_RESOLVES` (2) times without spending a rework, then a `merge_conflict` failure whose Retry starts a Worker run; `GitHost.push`; `openPr` once (after `findPr` finds no open PR for the branch, so a crash between opening and storing the PR adopts it; the number is stored on the ticket by CAS before any gate runs); then the project's gates as a background job on exactly the pushed commit (`worktrees.head`, stored as `gate_results.head_sha`) with a `GateContext` (claims come from the run's `finish` event). Each report goes through `deps.reports.put` (named `<gate>-<head sha>.txt`, so a re-gate never replaces an earlier report), each verdict is a `gate_results` row.
- Outcomes: all `passed`/`skipped`: the PR head must equal the judged sha, else nothing merges and the new head is gated again (at most 3 re-gates per run, then a park); then `gate_passed` with `tier_actual` (C when the diff touches `tier_c_globs`, else the predicted tier; the diff tier must still equal it at merge); tier A then `merge(squash, judgedSha)` (`HeadMovedError`, `MergeConflictError`, an unmergeable PR or a head without the base tip = re-gate after a merge-in, not a park; `mergeable: null` waits under the rate-limit backoff, never merges blind), `merged` (ticket `done`), worktree removed and branch deleted (failures logged only); tier B/C stop in `review` / `needs_signoff`. Any `failed`: `gate_failed` (rework run with `retry_of`, findings carried by a `continuation` wake into the `dispatch_prompt` input as `wake.gate_findings`), and at the rework cap the ticket parks naming the gate. A gate that cannot run or a git host fault is classified by `ForgeError` family: transient ones retry after the failure-policy backoff (counted by the hourly re-wake cap), the rest park. `TickReport.verified` lists each outcome.
- Gate jobs (`tick/gate-jobs.ts`): gates can run for half an hour, so the tick that publishes starts an in-memory job (keyed by ticket and run, one per key) and returns; the job writes only `gate_results` rows, then calls `requestTick()`; the next tick consumes it and applies the outcome (rework, merge, retry, park) through the usual CAS moves. A restart loses in-flight jobs; with no rows for the run the next tick gates again. Tickets with a job in flight count toward `max_concurrent_by_state.verifying`.
- Stage runner (`tick/stage-*.ts`): a ticket's lane pipeline is snapshotted at its first dispatch (`stage-snapshot.ts`, `ticket_pipelines`: effective list, roles, hash, settings version, routed stages) after `pipelineProblems` is re-run against today's roster; later edits never change a started ticket, a heavier lane re-snapshots at the next boundary. Nothing stores a cursor: core `stageCursor` runs over the `stage_runs` rows (`stage-state.ts`) and answers run a writer, run the red proof, start G1, start checks, wait, or merge (with `hold` when a human stage is open). Writers run while `in_progress` (`dispatch-stage.ts` picks the agent; `launch-run.ts` writes run row and attempt together); a passing writer asks for the next writer by a `stage` wake or moves the ticket to `verifying` (`stage-outcome.ts`, `stage-advance.ts`), and a tester's red proof runs as a background script job (`stage-script-jobs.ts`). While `verifying`, `stage-runner.ts` drives the rest through hooks `verify.ts` supplies (G1 gate job, gate rows, merge door): check agents start by a `stage` wake that dispatch serves under the normal limits (`dispatch-check.ts`: a read-only run in the ticket's worktree, never the assignee, never a resumed session, prompt rendered by `stage-prompt.ts` from typed artifacts with `narrative` stripped, `stage-artifacts.ts`), script gates as jobs (`stage-gates.ts`). A settled check applies its `submit_review` (`stage-outcome.ts`): blocking findings send the work back through `gate_failed` (`stage-send-back.ts`, the same bounded road as a failed G1, restarting at the stage's `rework_to`) or hold the ticket for the owner; no review at all parks it. Routing rules add checks on the plan's files at snapshot and the real diff when verifying starts, never remove. A lane raised while a writer is mid-run adopts the heavier lane's earlier writers instead of running them out of order.
- Full lane: `LIVE_LANES` is all three lanes; held Full tickets resume by themselves (`pipeline_ready`). _Findings route_ (`blockingRoute`, `stage-send-back.ts`): a gate (G1, a script) reworks to the cap and then raises `rework_cap`, never Merge anyway (a script gate set to hold parks as a plain failure), with one exception (d-0173): a G1 verdict that failed on the gate-config guard alone (`configOnly`, `tick/gate-hold.ts`, core `configOnlyFiles`) spends no rework and holds at once with a `config_hold:` decision (one finding per config file; "the Worker changed files that control how its work is checked; review them, then Merge anyway or send it back"; Merge anyway uses the same override recording and merge door, Send back reworks); a verdict marked `provenanceOnly` (only files whose earlier-run proof is gone) reworks first (findings tell the Worker to re-apply the files through its edit/write tool) and, once automatic reworks are spent, holds with a `provenance_hold:` decision through the same `gateHoldFields()` path and Merge anyway door (the write-scope-denies-the-rewrite case is not detected by `blockingRoute`, so such a ticket reaches the hold only after the reworks); any other G1 failure, a verdict without the marker, an `error` verdict or one lost in a restart keeps the rework road; a reviewer or the Director check reworks to the cap and then **holds**; a stage set to hold (the built-in critic, the Director check) holds at once. A hold parks the ticket from verifying with `findings_hold: ...` and one `decision` item at the owner stage (`escalation-finished.ts`); at the cap a reviewer's findings end in `findings_hold` instead of `rework_cap`.
- _Director check_ (`stage-director-check.ts`, `domain/director-check.ts`): a tool-less `ticket_check` step over typed artifacts only (ticket, plan, diff, gate and test reports, findings; **never** `narrative` or `finish_claims`), run as an in-memory job (`ticket:run:stage:cycle`), row kind `director`, restart-safe; the engine computes the files outside the plan, an unmet criterion becomes a high finding and an unclear one a medium finding, `out_of_plan` with unplanned files raises a `scope_drift` decision, and a ticket with no plan entry gets the stage `skipped` (so an owner sign-off); an erroring step is retried by its family and then parks with a failure, never a pass; cost is added to the card's Director spend (a warning only). _Sign-off_ (`stage-sign-off.ts`, `signOffDecision`): the Director records a `director` row and the merge door finishes (tier A merges; tier B through `mergeReviewed(..., 'director')` with a card note); otherwise the owner gets one `sign_off` item (`sign-off-raise.ts`) with the reason the Director declined. Every ticket `passAndMerge` leaves in review or needing sign-off gets that item; `escalation-backfill.ts` raises it (and decisions for `findings_hold:`, `config_hold:`, `provenance_hold:`, `scope_drift:` parks) at start. Tier C sign-off (d-0181): `signOffDecision` lets the Director sign tier C only on a clean floor (checks passed, no critical/high finding, plan check passed, no secrets path from core `findSecretPath()`, no owner override, approval mode not Always ask); the row records `signed_tier`, the door re-checks the secrets path, `transition()` needs `clean_floor`, and the card note reads "The Director signed off tier C change ... Undo: revert merge commit <sha>"; any other tier C waits for the owner with the failing condition as `director_note`.
- _Parallel writers:_ a writer `group` runs members side by side in the ticket worktree; each member (and each agent member of a check group) is its own scheduler candidate (`Candidate.member`, `candidateKey`), started by its own `stage` or rework wake (`stage#member` in the key, `rework-wakes.ts`), so a per-project limit of two starts both and one runs them in turn; a member's settle is kept while a sibling is the ticket's current run (`outcome.ts`), a crashed member is retried by its own stage row, and a rework of a writer group sends every member back.

### Escalations, approvals, agents and pipelines

- Escalations: every owner wait is one interaction: a Worker's question (typed by `tick/outcome-escalate`), a failure (retry cap, rework cap, lane hold, question timeout, ...) or a setup (login, tool approval, changed harness build, read from the run's receipts). Producers (`outcome`, `triage`, `plan-to-tickets`, `verify-outcomes`, `interactions`, `dispatch-park`) call `raiseEscalation` in the transaction that parks the ticket. A wait starts in the Director's stage (`escalated_at` unset, hidden from the owner): `sweepEscalations` runs once per tick (and again after verify), never inside the settle transaction, and gives each its first look: `ticket_answer` (with planning-style read rounds through `admit()`) may answer a Worker alone only when `canAutoAnswer` allows it (confident enough, cited grounds, not Tier C by prediction or planned file, not `always_ask`); `ticket_recover` may retry once per cause (`max_director_retries`) with a note. Any error, parse failure or timeout hands the wait to the owner at once; a lane hold, a timed-out question and every setup skip the look. `ticket_recover` facts carry `last_error` (newest `error` run event, clipped to 300 characters, data like the rest).
- `actOnEscalation(id, body, author)` and `actOnTicket` settle by CAS and act through `transition()` / `transitionCard()`: answer, retry (a rework-cap retry gives exactly one more attempt), cancel (refused with dependents unless `cascade`), run as Express, recheck (`still_broken` otherwise), re-plan (the card goes back to grilling; the not-started tickets of the old plan are held, and cancelled when v(N+1) is approved) and rework. `merge_anyway` and `continue` (owner only, five characters of reason, recorded on the interaction, the card event and the held stage row, which reads passed with `outcome.override`, `escalation-override.ts`), `rework` (also from a hold: held rows fail, no rework spent, comment and findings ride in the continuation wake) and `approve` / `sign_off` on a sign-off item; `actOnTicket` settles the pending item too. `resumeFixedSetups` resumes a fixed setup by itself; `backfillEscalations` gives tickets parked before this release an escalation at start; the invariant sweep reports a waiting or blocked ticket with none.
- Needs-you raises are structured (d-0172): `askOwner()` and `askStepBudget()` write `kind` (`plan_approval`, `director_questions`, `step_budget`), a short `title` and `items` next to the one-line `reason`; a plan the floor stops lists each floor reason as its own item, and the approval step's questions each as an item.
- Tool approvals (d-0175): a Standard or Full Worker's call that hits `ask` is parked for the owner, not dropped. `engine.raiseToolApproval(request)` (`tick/tool-approval-raise.ts`; `ToolApprovalRequest` / `ToolApprovalResult` in `types/approval.types.ts`) is the one door, called by the server's hook wiring: in one transaction it refuses Express, a run that is not active, a ticket not `in_progress` and a closed card (`refused` with the reason, so the hook denies), returns the pending item of the same `approval_key` (`created: false`), refuses more than five pending per run, and otherwise writes a `permission` interaction at the owner's stage through `raiseEscalation` (the exact call, the asking rule, whether "Always" is offered, the Worker's `description` or last text as a clipped "why"), a `permission` run event, card history and a card notify. `tick/approval-park.ts` (`guardApprovals`, called by `settleRun` before the outcome) means a run is never `success` with a call unanswered: a run that raised items and ends success or paused settles as a pause on its oldest pending item (the staged writer does not advance); with every item answered it parks and queues the wake in the same transaction; a failed run has its open items cancelled `by: auto`. The owner acts through `actOnEscalation` (`tick/tool-approval-act.ts`, owner only: Director, engine and automatic actions are refused): `allow_always` first appends a project settings version holding the `approved` rule (CAS, three retries, the version goes on the answer as `settings_version`), then settles; when no item of the run is pending and the ticket is `waiting_human`, one `response_wake` keyed `perm:<run id>` (`tick/approval-wake.ts`) resumes the same session. `dispatch-run` reads that key, takes the run it names as `previous` (so `retry_of` and the session carry over) and hands `wakeDelta` the run's answers (`approvals`), rendered in fixed words by `domain/approval-answers.ts` into the Worker contract (Standard and Full only; `OWNER_WAIT_RULE` also in `RESUME_PROMPT`; the Express brief is byte-identical). A tool approval is not in `QUESTION_KINDS`, so it never expires into Blocked.
- Agents: `tick/run-agent.ts` resolves the agent behind a ticket's next run from the tick's settings (`resolveAgent` for work naming no stage: the agent an earlier run used while still usable, else the implementer; `resolveStageAgent` for a pipeline stage, null when its agent is missing, disabled or archived, which parks the ticket instead of running another agent) and maps its `runs_on` to a harness and model (`modelFor`: `project_default` is the project's harness, `forge_default` the lane model matrix, `harness_default` sends no model, a fallback harness uses its own entry's model). `dispatch-run.ts` starts the run on that harness (unless the scheduler moved it to a fallback), puts the agent's instructions between brief and rules (`tick/agent-prompt.ts`), passes the agent's memory view to the memory source and records `agent_id` and `agent_hash` on the run row. `run-request.ts` takes the agent's budget keys and falls back to `engine.run_budget` for the rest (a `minutes` budget is logged, not enforced: no driver has a wall-clock cap yet). `schedule.ts` and `quota.ts` use the agent's own harness and let a non-empty agent fallback list replace `harness_fallbacks` (quota and harness-down only); a restart resume continues on the run's agent. With built-ins only, an Express run request equals the pre-agent one (`__tests__/tick/express-parity.test.ts`, golden fixture, also through the stage runner).
- Director pipelines: `tick/pipeline-adjust.ts` is the one door for a ticket's pipeline copy after its first snapshot: `adjustTicketPipelineTx` applies ops through core `applyAdjustments`, freezes every stage running or passed in the current cycle (`frozenStages`), stores the definition, hash, new roles and full log in one write and leaves one card note; it never throws for a refused op, so a Director change can never park a ticket (`declineAdjustmentsTx` records ops as dropped when the owner switched `director.pipelines.adjust` off). `ensureSnapshotTx` sets `base_hash`, applies the plan entry's `pipeline.ops` at first dispatch, re-applies the recorded `plan` then `fallback` ops on a lane raise (an op without its anchor is recorded dropped) and calls `maybeProposeTx` (`tick/pipeline-proposals.ts`: history from the project's recent tickets' copies, core `shouldPropose`, one pending `PipelineProposal` with up to three quoted reasons and the lane list with the op applied, skipped when routing changed the base list). `write_plan` gets `pipelines` (lanes, roster, locked ids, compact 90-day scorecards, the `adjust-pipeline` playbook); `composePlan` keeps only ops that hold and lists the rest under the plan's risks, `computeFloor` passes `lighter` so a removal waits for the owner, and a plan edit may drop ops (`drop_pipeline_ops`).
- Fallback ladder: retry (unchanged `decideFailure`; attempts counted per `fallback_slot`), then `tick/agent-fallback.ts` `nextSlotTx` after `rate_limit` retries run out or at once for `model_unavailable` (next usable entry of `[primary, ...runs_on.fallbacks]`, same-harness models count, parked or uninstalled harnesses and a critic's Worker family are skipped; the slot rides on the stage row `outcome.fallback`, a retry wake is queued, `peekAgent` / `chooseWriter` / `startChecks` read it so the run uses that entry's harness and model, and every run records `model` and `fallback_slot`), then `tick/no-agent.ts` parks the ticket as failure `no_agent_available` listing every try (owner-only when the agent says `on_exhausted: pause`), the Director's `tick/escalation-substitute-step.ts` runs the tool-less `pick_substitute` over candidates from `substituteCandidates` with their scorecards and applies a valid pick as a `swap` of cause `fallback` through the door, settling the item with the engine-only action `substitute` (a pick outside the list, a pause, an error, a switch off or no candidate hands the item to the owner, whose Retry restarts at slot 0). `tick/scorecards.ts` `loadScorecardInput` reads scorecard rows in batches (cap 2000 tickets).

### Observability

- Debug trace (d-0163): `EngineDeps.trace` is an optional `TraceSink` (absent means nothing is traced; passed through `emitTrace()` so a failing sink cannot break a tick). The engine emits one `run_event` per normalised event at the single place events enter it (the run pump), a `run` entry for the start request, end result and settle, one `engine` entry per dispatch pick, per rejected Director step (error kind and message) and per step retry, and an `error` entry when a tick phase throws (with its family). Never one entry per idle tick.

## Why this approach

- Inner ring (d-0058): imports `@forge/core` and `@forge/tools` only; every effect is a port. The same code runs on SQLite and the real harness in the app and on in-memory fakes in tests.
- One door for ticket state (code.md rule 6): every change is a plan of events run through `transition()` and stored by CAS on `status_version` (`tick/ticket-moves.ts`). "Park for a human" is one `parked` event (reason becomes `blocked_reason`), not a status write and not a fake `dispatched` + `asked`. A property test pins it.
- A retry is a new run (d-0055): a run with `ended_at` is never reopened; `retry_of` links the chain. A run stopped by a restart is the exception (d-0092): it has no `ended_at` and is resumed on its own row, so one run id carries the whole conversation and its receipts, with `generation` counting the secret generations (d-0100). `interrupted` moves only to `running` (resume) or `settled` (give up); the table is `RUN_TRANSITIONS` in core. A resume that fails falls back to the retry path, keeping the worktree, rather than losing the ticket.
- Failure policy by error family (`domain/failure-policy.ts`, config `engine.retry`): `auth`, `policy_denied`, `refusal`, `budget`, `invalid_input` never retry; `quota` is handled before the table (the table's own answer is a retry at the reset, or after `rate_limit.max_ms`); `rate_limit` waits for the harness's reset time, else exponential backoff (`base_ms * 2^(n-1)`, capped by `max_ms`, up to `max_attempts`); `crash` and `unknown` retry after `delay_ms` up to `max_attempts` (1 each); `stall` retries after `delay_ms` up to `max_attempts` (2). Past a cap the ticket parks in `waiting_human` with the family in `blocked_reason`. At most `rewake_cap.max` (3) recovery wakes per ticket per `window_ms` (1 h), then it parks.
- Only a lane with a runner starts (`domain/live-lanes.ts`, d-0059): all three lanes run their pipelines; a lane a later build adds parks tickets in `waiting_human` with `pipeline_pending: ... goes live in the next update` until live.
- Director steps (`triage`, `dispatch_prompt`, `steer_reply`) use the model matrix and `step_budget_usd`; off-schema output is retried once with `previous_error`, then rejected (logged, held off one tick interval, no state written).
- One merge door (code.md rule 6): `tick/verify-merge.ts` is the only caller of `GitHost.merge`, and only for a ticket in `verifying` with `tier_actual = A` (set only by `gate_passed`) and an open PR. Verify is resumable from stored facts (PR number, `gate_results`, `tier_actual`, `prStatus`). A verify fault no retry fixes (auth, retry cap, no gates) is a `parked` event from `verifying`: `rework_count` is untouched and `parked_from = verifying` makes a human `unparked` return the ticket to `verifying`, so publish, gates and merge re-run on the same run with no new Worker. Gate findings still go through `gate_failed` (rework, or park at the cap, which releases to `planned`).
- Fairness is by project turns, not global priority: a ticket's `priority` ranks it inside its own project only. A global priority would let one project's urgent tickets starve every other project (a property test pins no starvation).
- Alternatives rejected: engine in `apps/server` (breaks "apps compose only"); timers beyond the one wake timer (it uses `deps.clock.after`, so tests move a fake clock).

## Requirements

- Node 24, pnpm. Runtime deps: `@forge/core`, `@forge/tools` (`admit()` and the `director` read grant), `zod`.
- `EngineDeps` (see `src/types/engine.types.ts`): storage, `drivers` (a core `DriverRegistry`), llm, memory, receipts, `reports` (a `ReportStore`), `project(slug, settings)` (the project's `ProjectRuntime`: config, `GitHost` or null, gates, optional `scriptGates` (a `ScriptGateRunner` for script gates and the red proof; absent means a script gate parks the ticket and the proof is skipped), optional `prepare` (a `WorktreePreparer`: installs packages in each new worktree; absent means no setup), `worktrees` of its own clone and `baseRef`; null = unknown or archived project; `settings` is the project's `ProjectConfigView` of this tick so the app can rebuild a runtime whose git host settings changed), clock, `config` (a `ConfigSource`, read once per tick), `ids`, `owner` (this server's name), `catalogueHash`, `repoReader` (a core `RepoReader`: tracked files at HEAD for planning reads), optional `mcpIdentity`, `memoryIndex`, `research`, `trace`, `onTickRequested`, `log`.
- No env, files or processes are touched here (the id source reads only OS entropy). Tests: `pnpm test` (scenarios in `__tests__/scenarios`, pure rules in `__tests__/domain`, the status-write property in `__tests__/property`, including the scheduler's limit, fairness and priority properties); coverage floor 80% lines.

## Extending

- A new planning step kind: add it to `FLOW_STEP_KINDS` and `STEP_NAMES` in `@forge/core` with its output schema, a runner in `tick/planning-steps.ts` (or its own file), and a case in `runKind` of `tick/card-planning.ts`; it then appears in the flow editor's Add step menu (research was added this way).
- A new Director step: add its name and output schema in `@forge/core` (`schemas/steps.ts`), add the model to the matrix, then call `runStep` from the phase that needs it (see `tick/triage.ts`).
- A lane goes live: add it to `LIVE_LANES` (`domain/live-lanes.ts`); triage and plan approval stop holding it and `releaseLaneHolds` lifts holds already raised. The lane rule is in `domain/lane-rules.ts`.
- A new failure family rule: `domain/failure-policy.ts` plus its config in `engine.retry`.
- A new scheduling limit: add it to `PickCaps`, check it in `pickNext`'s `blocker`, name it in `describeWait`, fill it in `tick/schedule.ts` from the settings, and extend the limit property test.
- Never write ticket status elsewhere; add events to `core`'s state machine and plan them through `ticket-moves.ts`.

## Limits

- Director jobs and card chat: only `create_ticket`, `steer_run`, `change_type`, `suggest_close` and `cancel_ticket` are offered to the Director (pause, stop, restart and re-plan of tickets are not; cancel only when the owner asked in that chat turn: a prompt rule, d-0179). `create_ticket` is refused while the card is `grilling`, `verifying` or `plan_ready` (tickets come from the approved plan, d-0141), the ticket type is always `chore` (triage may refine it), and the budget cap never blocks: crossing 80 and 100 percent writes one `budget_warning` card event each (d-0143, `tick/card-budget.ts`, checked after a card reply and after a run settles). Owed chat replies are `card_reply_queue` rows (claimed per tick; claims found at boot are released on the first tick, a claim older than 10 minutes, `STALE_CLAIM_MS`, is taken again), so a restart resumes them; the `thinking`/`error` flags are process-local (`thinking` is mirrored from the queue, set inside the posting transaction, and `deps.projectEvents` is told when it ends). A `card_chat` turn's cost is recorded through `addDirectorSpend` like planning and escalation steps (a failed turn and memory-rewrite calls too; the chat prompt's `spent_usd` is the card total, runs plus Director). Triage and steering steps record no card cost; an escalation or sign-off check on a ticket with no card is recorded with a null card. Planned cards do not use `card_chat`: their turns are planning turns.
- Planning: the flow is walked in the process that claims the turn (a crash mid-step re-runs that step once the claim is stale, losing only that call's spend); `step_budget_usd` (default $2; the claude CLI alone costs about $0.50 a call) caps each planning call, and a step failing with the `budget` family is not retried by the stale claim (it would spend the same money and fail again): the card gets a note, `needs_you` with actions `raise_step_budget` and `retry_step` (kind `step_budget`), and its queued turn is completed; `retryPlanningStep` (`POST /cards/:id/planning/retry`) clears Needs you and resumes at the unfinished step (the ticket-side `ticket_answer` / `ticket_recover` steps hand any failure straight to the owner); chat messages during planning answer the open question or are kept as an owner note, never a second conversation; the Director's lane for a plan ticket is the plan lane raised by `preCheckLane`, `decideLane` is not involved (no triage model call for planned work, d-0141 item 9).
- Process-local by design: live run pumps, step/dispatch holds, queued steering replies, prep jobs, gate jobs, the re-gate counter, verify holds and verify retry backoff (a restart retries at once, the re-wake cap still counts), the rotation cursor (after a restart the first dispatch starts at the first project by id) and script/proof/routing caches (`stageJobs`, `diffRouted`; a restart runs a lost script or proof again, the rows are the truth). After a restart pumps are gone (interrupted runs resume with new pumps, d-0092) and prep jobs reset (the next dispatch reads the worktree's record and prepares only if needed). The requester's hint, type and title are read from the stored intake event, so they survive a restart. A gate job finishing after its ticket was cancelled leaves harmless rows, pruned later.
- A run lost in a crash can only be resumed if the harness had reported its session (stored on the run row as it arrives); one lost before that is crash-settled and retried. A Worker whose result had arrived but was not yet settled is resumed too, and told to continue.
- A running Worker keeps the limits it was started with (budget, stall time); a settings edit reaches runs started on the next tick. The stall scan uses the current `stall_ms`. Run rows predating migration 0010 have no `config_version`. `driver_version` on run rows is the constant `unversioned` until the driver exposes it cheaply.
- Tool approvals: only a writer run in `in_progress` can raise one (a check agent in verification is refused and its call is denied); a Worker pausing on a question while approvals are pending is parked on the oldest approval, the question stays pending; a failed run loses its open items, so the retry asks again if it still needs the call; "once" is bound to the asking run and its resume (`retry_of`), not a later fresh run.
- Ticket numbers come from listing every ticket id (no counter); fine at M0 scale. Priority is set directly on the ticket row (no API to change it yet). A wait reason is computed on request and not stored. Failure attempts count failed runs of the same family for the ticket, with no decay.
- A project with no git host has a runtime (worktrees, base) but its tickets wait in Verifying: nowhere to publish.
- Preparation: a running install cannot be cancelled (a ticket cancelled meanwhile has its tree removed once the job lets go of it, else by the next start's sweep); a preparing ticket holds its slot only while its job runs; a ticket cancelled before its first job has no folder to clean; the tail the owner sees is the preparer's last 4 KB.
- The re-gate publishes the worktree head: a head someone else pushed to the branch is overwritten or the push is refused (the verify fails, retries or parks); the engine never merges a head it did not gate. Gate findings reach the rework prompt through the wake's `reason` text (4,000 chars max).
- Approve and merge reads the gate rows of the ticket's last successful run and its worktree; if the worktree is gone the review facts are null (the merge itself still works from the PR). The G1 report is shown by reference (`report_ref`), not served as a file. A settled run whose ticket was reassigned is not reopened.
- Card history: a ticket without a `card_id` is skipped, not failed; History infers a reason only when none is stored.
- Not in the engine: `apps/server` (HTTP, SSE, clock), in-run escalation signals, the `clarify`, `plan`, `rework_brief` and `epic_summary` steps, `command` intake, `delegated`/`monitor` wakes (consumed and dropped; `continuation` is the gate-failed rework). The git host has no revert yet, so tier C sign-off's one-click revert is a later step.
- Agents: an agent fallback list changes the harness on quota and harness-down only; the scheduler reads the agent the ticket's next stage names (`tick/stage-agent.ts`), not the agent a retry will resume on.
- Stage runner: check runs start through the scheduler's limits, but a check never takes the ticket's `assignee_run_id`, so a late result for work that already went back is recorded and changes nothing. Artifacts are stored only for pipelines that have a check agent (an Express ticket writes only its snapshot and stage rows). The red proof is advisory: it runs the project's `test`-role check, skips with a note when there is none or no runner, and never blocks.
- Memory: the rewrite cache is per process and a rewrite call outliving its timeout is abandoned, so its cost is not counted; the rejected-approach check is a word-overlap heuristic that only adds a reason for the owner to read, it cannot prove a plan repeats an approach; an index that cannot be read fails the step like any other port error (no silent fall back to the old slice mid-run); the note counts decisions inside the agent slice, not the whole project.
