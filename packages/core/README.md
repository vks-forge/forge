# @forge/core

The pure domain layer of Forge: schemas, the ticket state machine, lane triage, ids, branch names, typed errors and the ports every adapter implements.

## Why it exists

The Director engine, the HTTP API, the gates and the Workers' drivers all touch the same tickets, runs and events. If each had its own idea of what a ticket status means, who may move it, or what a run result looks like, a ticket could skip verification, reach Done without the sign-off its tier needs, or loop through automatic rework forever. Core is the one place those rules live. It has no IO, no database and no harness names, so the same rules run identically in the engine, in tests and on replay, and a new storage backend or harness never forces a change here.

## What it does

Public API (`src/index.ts`):

- Data home: `resolveDataHome({ platform, env, homedir })` is the one rule for where Forge keeps its own files, shared by the server and the CLI and pure (it reads nothing from the machine). `FORGE_HOME` (development and tests only) wins over the platform default, which is the only folder a user gets (d-0170) (Windows `%LOCALAPPDATA%\Forge`, macOS `~/Library/Application Support/Forge`, Linux `$XDG_DATA_HOME/forge` or `~/.local/share/forge`); a relative or empty override throws `InvalidInputError`. `dataHomeLayout(home, platform)` names `forge.db`, `secrets/`, `memory/`, `worktrees/`, `runs/`, `backups/`, `logs/`, `server.json` (schema `ServerRecord`: pid, port, startedAt, version, written by the running server for the CLI), `install-token` (the API token) and `server.lock` (single-instance lock) under it (d-0098, d-0093).
- Ids: `makeTicketId`, `parseTicketId`, `TicketId`. Ticket ids are `<PROJECT>-<n>`; the prefix is `[A-Z][A-Z0-9]{0,9}`, numbers are positive with no leading zero. The parser never throws.
- Cards (d-0105 .. d-0107): `Card` (the intake record: `id`, `project`, `type`, `title`, `summary`, `source {kind, ref}`, `created_by {type, id}`, timestamps, optional `closed_reason` and `budget_cap_usd`, and the stored lifecycle `phase`, `phase_version`, `needs_you`, `priority` and `links`), `CardColumn` (`shaping`, `needs_you`, `queued`, `in_progress`, `done`, `closed`; `new` is gone, d-0139), `CardType` (a registry entry as data: `name`, `label`, `icon`, `allowed_sources`, `actions`, `plan_approval` (`director_or_user | user`), `tickets_on_intake` (only `pr_issue` is true), optional `default_lane`) with `BUILTIN_CARD_TYPES` (discussion, plan, issue, pr_issue), `CardEvent` / `NewCardEvent` (history, a union keyed by `kind`: `user_message`, `director_message`, `ticket_created`, `ticket_state`, `interaction_opened`, `interaction_answered`, `type_changed`, `card_closed`, `budget_warning`, `note`) and the card API bodies (`CardListQuery`, `CardSummary`, `CardDetail`, `CardEventsQuery`, `CardPatchBody`). Card ids are `<PROJECT>-C<n>` (`makeCardId`, `parseCardId`, `CardId`): the `C` keeps a card id from ever reading as a ticket id. `Ticket.card_id` and `TicketSummary.card_id` link a ticket to its card. `rollupCardColumn(card, tickets, pendingInteractions)` is the one rule for a card's column (d-0139): Closed (phase `closed` or a reason set), else Needs you (`cardNeedsYou`: the card's own flag, a ticket in `waiting_human` / `review` / `needs_signoff`, or a pending question on one of its tickets), else by phase (`grilling` / `verifying` / `plan_ready` Shaping, `approved` / `queued` Queued, `in_progress`, `done`). Ports `CardRepository` (also `findBySource` for the create dedupe and `updatePhase`, the phase CAS), `CardEventRepository`, `CardTypeRepository`, `CardRelationRepository`, `CardReplyQueueRepository` and `TicketRepository.listByCard` are on `StorageTx`.
- Card flow (d-0128 .. d-0143): `CardPhase` (`grilling`, `verifying`, `plan_ready`, `approved`, `queued`, `in_progress`, `done`, `closed`), `CardPriority` (`low`..`urgent`) and `CardRelation` (`{from, to, kind: 'depends_on'}`; "blocks" is the reverse view). `transitionCard(card, event)` is the one door for the phase: events `start_verifying`, `plan_written`, `regrill` (also from `done`, for a follow-up plan), `approve`, `queue`, `start`, `complete`, `close`, `needs_you_set`, `needs_you_cleared`; a CAS on `phase_version` (`expected_version`), a bump on every accepted event, closed is a dead end, and `approve`, `complete` and `close` clear `needs_you`. `findCycle(existing, added)` is generic over the id type (cards now, tickets later) and returns a closed path (`[a, b, c, a]`) or null. `CardReplyQueueItem` / `NewCardReply` are the durable queue of owed Director replies (`card_created`, `user_message`). `ProjectEventSink` / `QueryKey` is the port the engine uses to say which web queries went stale. `Interaction.card_id` (optional) lets a question belong to a card. `chatActionRefusal(type, kind, phase)` refuses `create_ticket` while the card is grilling, verifying or has a plan awaiting approval.
- Director concurrency (eval fix 5): `DirectorConfig.max_concurrent_steps` (int 1 to 8, `.default(3)` so a stored row from before the field still parses; not project-overridable in the UI) bounds Director steps running at once; `CardReplyQueueRepository.claim(at, staleBefore, options?: CardClaimOptions)` takes `exclude` / `maxCards`, and `releaseClaims()` clears every open claim at boot.
- Card chat (d-0109, d-0112): `CardMessageBody` (`{text 1..8000, author 1..200}`, strict), `CardChatOutput` (`{reply, actions}`, at most five actions; the `card_chat` Director step output), `CardChatAction` (closed union: `create_ticket {title, body, lane?}`, `steer_run {ticket_id, message}`, `change_type {type}`, `suggest_close {reason}`, `cancel_ticket {ticket_id, reason, cascade?}`; not to be confused with the registry action name `CardAction`), `ActionTaken` (`{action, result: done|refused, summary}`), `CardDirectorStatus` (`{state: idle|thinking|error, last_error?}`, the `director` field of `CardDetail`). New card events: `director_message` may carry `actions_taken`, `director_action` (an executed action), `close_suggested`. `allowedChatActions(type)` and `chatActionRefusal(type, kind)` say which actions a card type allows from its registry `actions` (every action needs `chat`; `create_ticket` needs a type that starts tickets; `change_type` needs `convert`; `suggest_close` needs `close`); `openBlockerIds()`, `openDependentIds()` and `canCancelTicket()` (`domain/ticket-blockers.ts`, shared by the scheduler, the ticket detail and the cancel dialog); `checkTypeChange(card, nextType, name)` is the retype rule shared by `PATCH /cards/:id` and the chat. `card_chat` is a fourth Director step (`STEP_NAMES`, `models.director.card_chat`). Ticket edits: `TicketEditBody` (`{body?, priority?, depends_on?}`, at least one) and the pure `checkTicketEdit()` (no self edge, same project, no cancelled target, no loop via `findCycle`, a started ticket keeps its description and takes no new wait); the chat gains `set_ticket_dependencies`, `set_ticket_priority`, `edit_ticket_description` and `create_ticket.restores`.
- Branches: `branchName`, `parseBranchName` for `<type>/<id>-<slug>`. The slug falls back to `untitled` when the title has no ASCII content.
- State machine: `transition(ticket, event)` returns `Result<Ticket, TransitionError>` and never throws. Events carry `at` (keeps it pure) and optional `expected_version` for compare-and-swap. Automatic `gate_failed` rework is capped at two loops, then the ticket goes to `waiting_human` with a reason. `done` from Review or NeedsSignoff is the human approve and merge; tier C needs a non-blank `signer` (whitespace-only is refused), and the reserved signer `director` only with `clean_floor: true` (d-0181; `signOffDecision` and the merge door decide that, `findSecretPath()` names secrets paths: env files, keys, secrets folders). `triaged` raises the lane and never lowers it. `gate_passed` with `hold: true` sends tier A to `review` like B (a pipeline with a human stage). Every verify cycle needs its own `gate_passed`: `verifying`, `gate_failed` and `rework` clear `tier_actual`, so `merged` can never ride on a pass from an earlier cycle. `conflict_found` (verifying only) is the merge-with-main road: it goes back to `in_progress` with `conflict_count + 1` and no rework spent, and at `MAX_CONFLICT_RESOLVES` (2) it parks in `waiting_human` with a `merge conflict:` reason and no `parked_from` (so a release goes to `planned` and a Worker really runs). `MergeConflictError` has family `merge_conflict` (never a policy denial); `FailureCause` and `FAILURE_ACTIONS` gain `merge_conflict` (retry, replan, cancel), `EscalationFailure` an optional `conflict` payload (files, upstream tickets), and `classifyPark` reads a `merge conflict:` reason. `conflictMarkerFiles()` (`domain/conflict-markers.ts`) reads G1's marker findings off a failed verdict. A cleared optional field (`blocked_reason`, `tier_actual`) is emitted as a present-but-undefined key so a storage patch built from the result clears the column.
- Pipelines and the stage runner (S5b, d-0136, d-0151, d-0152): `schemas/pipeline.ts` (`PipelineDefinition` = 2 to 12 `Stage`s: agent, script gate, group, human, locked merge; `LanePipelines`, `ProjectPipelines` with `RoutingRule`s, `PipelineProblem`, `PipelineView`) and `schemas/stage-run.ts` (`StageRun`, `StageOutcome`, `ReviewSubmission` / `Finding`, `StageArtifact`, `TicketPipeline`, `TicketPipelineView`); `ForgeConfig.pipelines` and `ProjectConfigShape.pipelines` hold them in the versioned config rows. Pure domain: `pipelineProblems()` / `routingProblems()` (merge last, G1 once and after the last writer, nobody checks their own work, a reviewer needs a writer before it, groups hold 2 to 4 checks, the only back edge is `rework_to` an earlier writer; property-tested), `BUILTIN_PIPELINES` (Express `implementer, g1, merge`; Standard adds the test-writer with a red proof and a reviewer; Full adds a review group and a human stage), `effectivePipelines()` (tags, hash, `live`, same-family critic warning), `routeStages()` (only adds, before human or merge), `stageCursor()` / `currentCycle()` / `reworkTarget()` (what a ticket's pipeline asks for next, from stage rows alone), `isBlocking()` / `stageInputs()` (narrative stripped for every non-writer) / `adoptLegacy()`, `ticketPipelineView()`, and the pure document edits `setCompanyLane()` etc. (`pipeline-doc.ts`). Ports: `ScriptGateRunner`, and `ticketPipelines` / `stageRuns` / `stageArtifacts` in `StorageTx`. `TicketEvent` `gate_passed` takes `hold: true` (tier A then waits in Review), `WakeKind` has `stage`, `RunEvent` has `review`, and the settled escalation action `pipeline_ready` is the engine's own (never a button). `stageAgent()` replaces the old lane agent: a stage whose agent is disabled or archived gets nothing (the engine parks the ticket).
- Full lane (S5c-A, d-0137, d-0141 item 9, d-0165): `Stage` gains `director_check` (the Director judges finished work against the plan; `on_blocking` defaults to hold) and `sign_off` (`signer: director_or_owner | owner`); a `group` may hold 2 to 4 members that are all checks or all writers (a writer group runs side by side in one worktree: distinct agents, no red proof, write scopes that cannot meet, judged by `scopesOverlap()`). New problem codes `group_mixed`, `writer_scope_overlap`, `writer_group_proof`, `director_check_position` / `_duplicate`, `sign_off_position`, `critic_same_family` (a problem once `PipelineRuleContext.families_available` has two families, else only the warning from `effectivePipelines()`; a critic is any reviewer whose id or name says critic, or a copy of the critic). `BUILTIN_PIPELINES.full` is `test-writer, implementer, g1, review-group [reviewer, critic (hold)], check-plan, sign-off, merge`; saved lists with a `human` stage keep working. Pure rules: `blockingRoute()` (a gate reworks then `rework_cap`, and holds only when its failure is gate configuration alone, `configOnly`, d-0173; `configOnlyFiles()` / `configHoldSummary()` in `domain/config-hold.ts` decide that from the verdicts and fail closed; a gate whose verdict is `provenanceOnly` (every finding a claims finding with a `file`: the proof of the earlier run that edited it is gone, F-D3) reworks while the cap allows and then holds, decided by `provenanceOnlyFiles()` / `provenanceHoldSummary()` in `domain/provenance-hold.ts`; a check reworks to the cap then holds; a hold policy holds at once), `signOffDecision()` (the Director signs only tier A or B within `director.sign_off.max_tier`, with every check passed, the Director check passed and no override; anything else, and always tier C, is the owner), `unplannedFiles()`, `stageCursor()` cursors `run_writers`, `director_check`, `sign_off` (a row with `outcome.override` counts as passed). `transition()` refuses `done` from `needs_signoff` when the signer is the reserved `director` (`DIRECTOR_SIGNER`) and allows `rework` from a ticket held from verifying. `TicketCheckOutput` (the `ticket_check` step, a `pass` that admits an unmet criterion or a critical or high finding is refused), `Finding` (its own file), `StageOutcome` gains `check`, `unplanned`, `signed_by`, `sign_reason`, `override`, `same_family`, `attempts`; `StageView` gains `findings` (capped at 20), `warnings`, `signed_by`, `override`, `scope`, `check`, `unplanned`. Escalations gain the kinds `decision` (`findings_hold`, `config_hold` (G1 failed only on gate configuration files the Worker changed; same four actions as `findings_hold`), `provenance_hold` (G1 failed only because the proof of an earlier run's edits is gone, after the automatic reworks; same four actions; `provenance_hold:` park prefix), `scope_drift`: `DECISION_ACTIONS`) and `sign_off` (`SIGN_OFF_ACTIONS(tier)`) and the actions `merge_anyway` and `continue` (a reason of five characters is required); `classifyPark` reads `findings_hold:`, `config_hold:` and `scope_drift:` reasons as decisions. `GateFinding` has an optional `file` and `GateVerdict` an optional `configOnly`. The `recover-failure` playbook tells the Director's diagnosis to name only the owner's real buttons (Retry, Re-plan, Cancel) and never to ask the owner to edit files. `director.sign_off.max_tier` (`none | A | B`, default B, no `C`; a project may only lower it: `signOffAboveCeiling()`, held to the company's value when merged). `StageRunRepository.get(id)`; stage run kind `director`; artifact kind `check_report`; the `check-against-plan` playbook and `models.director.ticket_check`.
- Overview shapes (d-0162): `StatsRange` also covers `today`, `12m` and `all`, `StatsGroup` / `defaultGroup()` (hour, day, week, month; the default follows the range, `today` groups by hour), `OverviewQuery` refuses an hour group on any range but `today` and `today` on any group but hour, `StatsRangeQuery` (per-project stats and cost) excludes `today`, `OverviewStats` / `OverviewQuery` (the response and the URL query of `GET /stats/overview`), the pure `computeOverviewStats()` that sums every project's tickets, runs, Director spend rows (the `DirectorSpend` ledger rows, x-0017; every spend figure is Workers plus Director with the split: `kpis.spend_worker_usd` / `spend_director_usd`, `spend_by_source`, per-project `director_values` and `director_usd`), G1 verdicts, open cards and needs-action inbox items into KPIs, series per bucket, spend breakdowns by project / harness / lane, a projects table and the newest needs-attention items, `overviewRunsSince()` (the earliest run or Director spend row the server must read; in `overview-range`) and `bucketize()` / `bucketKeyOf()` (UTC day, Monday-week and month buckets, plus hour buckets named by the ISO instant they start, contiguous and covering the window; property-tested). `today` runs from the server's local midnight to now: callers pass `utcOffsetMinutes` (minutes east of UTC, default 0 = UTC midnight) to `computeOverviewStats()`, `overviewRunsSince()`, `statsWindow()` and `bucketize()`, and hour edges follow that offset (a +5:30 zone cuts at :30 UTC). Its change figure compares with yesterday up to the same time of day. `byWaitingThenActivity()` / `attentionOf()` (table order and the Needs attention list) sit in `overview-lists`.
- Home, Cost, Runs and Inbox shapes: `StatsRange` / `StatsRangeQuery` / `SeriesPoint` (dense UTC-day series), `ProjectStats`, `CostReport` (`COST_TOP_N` default page, `COST_PAGE_MAX`, `CostPageQuery`; `by_ticket` / `by_run` are pages and `by_ticket_total` / `by_run_total` count every row), the cost rollups `TicketCost` / `CardCost` with the pure `rollupTicketCost` / `rollupCardCost` (recorded dollars only; a run with no cost is 0 and `recorded: false`), `RunSummary` / `RunListQuery` / `RunListPage` / `RunDetail`, `InboxItem` / `InboxListQuery` / `InboxPage` / `InboxCounts` / `InboxStateRow`, and the pure rules `computeProjectStats`, `computeCostReport` (runs plus `directorSpend[]`: `total_usd` = `worker_usd` + `director_usd`, `per_day_split`, `director_steps_total` / `director_steps_recorded`), `effectiveCardBudget()` / `budgetDefaultFor()` (the one budget answer: the card's own cap, else the project's warning level, else the Forge default, with its `source`; `CardDetail.budget`), `rollupTicketCost(runs, directorUsd)` (`workers_usd`, `director_usd`), `DirectorSpendRepository` on the storage port, `statsWindow`, and the inbox rules (`inboxItemId`, `applyInboxMarks` where a read or archive mark holds only while the item's `updated_at` is not newer than the mark's stamp, `inInboxView`, `inboxCounts`, `markInbox`). Storage gains `runs.list` (`RunListFilter` / `RunListKey`), `inboxStates`, `harnessVersions.listByCompat` and `harnessToolSchemas.listByStatus`.
- First-run and new-project shapes: `SystemInfo` / `FirstRunState` (`GET /system`) and `ProjectInspection` (`POST /projects/inspect`), `FolderListing` / `FolderEntry` (`GET /fs/folders`, the sub-folders of one folder for the folder browser, each with its `modified_at`; empty `path` with null `parent` is the roots view), `FolderPickBody` / `FolderPick` (`POST /fs/pick-folder`, the system folder window: `picked` with a path, `cancelled`, or `unavailable` with a reason), `FolderCreateBody` (`POST /fs/folders`, make one folder) and `FolderRevealBody` / `FolderReveal` (`POST /fs/reveal`, show a folder in the file manager: `opened` or `unavailable`), plus `suggestSlug()` / `suggestPrefix()` (a valid, unused project slug and ticket prefix from a folder name).
- Ticket list shapes: `TicketSummary` (the board card; `state` is the status, `wait` the `TicketWait` (`TicketPhase`, plain `text`, `holders`, `blockers`) from `derivePhase()`, and `needs_you` is true only for phase `waiting_you`: review, sign-off, blocked, or `waiting_human` with an open owner item), `TicketListQuery` (`state[]`, `lane`, `card`, `q`, `sort` `updated|created|cost`, `offset`, `limit` 1..`TICKET_LIST_MAX_LIMIT` default 100, `cursor`), `TicketListPage` (`total`), and the `TicketListKey` / `TicketMatch` / `TicketListFilter` types that `tickets.listByProject` and `tickets.countByProject` page by. `TicketSummary` and `CardSummary` carry an optional `cost_usd` (the server always sets it) and `CardDetail` the `cost` split. Storage gains `runs.costByTicket` / `runs.costByCard` (grouped recorded cost).
- History (Phase 5.1): `HistoryEntry` (`at`, `kind` state/question/answer/run/check/director/setup/merge/plan/note, `actor {type: owner|director|engine|worker, name?}`, a plain-language `title`, optional `detail`, `from`/`to`, `ticket_id`, `links {run_id, interaction_id, stage_id, card_id}`, `waited_ms`), `HistoryPage` (`entries` oldest first, `has_more`, `next_before`) and `HistoryQuery` (`before`, `limit` 1..500). `buildHistory(facts)` merges a ticket's card events, questions, runs, stage runs, wakes and gate results; `buildCardHistory({events})` gives the card's own phases plus one roll-up line per ticket event; `pageHistory(entries, {before, limit})` pages by time and never splits one instant. A move with no stored reason borrows one from the settled question, the wake or the run next to it, and otherwise says only what moved. `commitMessage(subject, {ticketId, runId})` adds the `Forge-Ticket` and `Forge-Run` git trailers.
- `toTicketPatch(next)`: the `TicketPatch` that stores a transitioned ticket with `updateTicketCas`. It drops `id`, `project`, `created_at`, `status_version` (storage owns the version) and the derived `parent` / `blocked_by`, and keeps the explicit clears (also for the nullable engine fields `assignee_run_id`, `branch`, `worktree`, `checkout_run_id`, `epic_id`, `created_by_intake`, `pr_number`, `pr_url`).
- Git host and secrets: `GitHost` (`push`, `openPr`, `findPr` (the open PR for a branch, so a crash between opening and storing a PR adopts it instead of opening a second), `prStatus`, `merge(n, method, expectedHeadSha)`, `closePr`, `deleteBranch`; only the engine's merge step calls `merge`, and the host refuses with `HeadMovedError` when the PR head is not the commit the gates judged), `SecretStore` (`get`, `put`, `delete` (idempotent), `list(prefix)` (sorted); names are namespaced paths matching the `SecretName` schema, lowercase `/`-joined segments such as `github/<connection>/key` that can never address a path outside the store; `assertSecretName` / `assertSecretPrefix` throw `InvalidInputError`) and `ProjectConfig.git_host` (`GitHostConfig`: `local` with `remote_path`, or `github` with owner, repo, `installation_id` and, only when the project has no GitHub connection, `app_id` and `key_secret`; `base_branch` defaults to `main`). `Ticket.pr_number` and `pr_url` link the ticket to its PR.
- Project settings (d-0095): `ProjectConfigShape` / `ProjectConfig` carry `checks: [{name, role: test|lint|typecheck|build|format|custom, command, cwd?}]` (list order is run order; names unique; `command` non-empty; `cwd` relative with no `..`), `ecosystems: string[]` (`node`, `python`, `go`, `rust`, `jvm`, `dotnet`, `ruby`, `php`, `cmake`; empty means the gates detect them) and optional `gate_rules` (`GateRules`: extra `config_globs`, `test_globs`, `skip_patterns`, `replace`). They replace the old `profile` + `commands` (d-0034). `migrateLegacyProjectDoc()` converts a stored or submitted document in the old form (lint, typecheck, test, build in that order; `typecheck` dropped under `generic`; `ts` gives `ecosystems: ['node']`; an unknown profile is rejected); `ProjectConfig` and `ProjectOverride` apply it on parse, so old config versions read as checks without rewriting the database and new writes use the new shape. A legacy override with no command adds no `checks` key, so it cannot blank an inherited list.
- Built-in defaults: `engine.step_budget_usd` is $2 (the claude CLI alone costs about $0.50 per call on opus, so a lower cap makes every planning step fail with the `budget` family); `forge.yaml` and `BUILTIN_FORGE_CONFIG` must agree (a test pins it). Director models: opus for `card_chat`, `card_survey`, `enhance`, `write_plan`, `ticket_recover` and `ticket_check`; sonnet for `triage`, `dispatch_prompt`, `steer_reply`, `verify`, `approve_plan` and the quick turns (eval fix 5; the owner can change each in Director settings).

- Project memory (d-0007, d-0086): `MemoryRecord` (the front matter of a record: `id` like `d-0001`, `kind`, `statement`, `source`, `author` `user|director`, `origin`, `status`, dates, `supersedes`, `superseded_by`, `tags`, `pinned`; open to extra fields), `MemoryRecordWithBody`, `MemoryListEntry`, and the writer inputs `ProposalInput` (confidence at most 0.8) and `DecisionInput`, neither of which carries an author, status or id. - Gate reports: `ReportStore` (`put(runId, name, text)` returns the reference stored in `gate_results.report_ref`); the engine saves every gate report through it.

## Why this approach

- `zod@4.6.7` is the only dependency. Schemas are the source of truth for types, DB rows, HTTP bodies, config and LLM step output; types come from `z.infer`, so nothing is declared twice. Parsing happens at every boundary.
- Result values instead of exceptions for expected failures (`transition`, id parsing), so callers must handle illegal moves. Unexpected failures throw `ForgeError` subclasses; retry, stall and kill decisions read `errorFamily`, not the message.
- One `transition()` for status changes (the single door). It takes an optional version for CAS so racing writers lose atomically in storage.
- Driver-boundary shapes are camelCase; DB rows (`Run`, `Ticket`, `Interaction`) are snake_case.
- `RunRequest` has no `AbortSignal` (not serializable); cancellation goes through `WorkerDriver.cancel`.
- Ports live here, not in the adapters, so adding a harness or database is a new folder elsewhere and never a core edit (d-0016, d-0047).

Where the design docs were silent, the simplest option was taken:

- Tool approvals (d-0175; the engine raises one, and the web draws it in the dock, the Inbox and Settings, Project, Tool approvals): `EscalationKind` gains `permission` with `EscalationPermission` (`schemas/escalation-permission.ts`: `tool`, `action`, the exact `what` up to 2000 characters, `approval_key`, `reason_code`, the Worker's `why` up to 300, `lane`, `always: { offered, rule?, why? }`, `summary`); `EscalationAction` gains `allow_once`, `allow_always`, `deny` (`PERMISSION_ACTIONS`, or `PERMISSION_ACTIONS_NO_ALWAYS` when no narrow rule is offered; `deny` takes an optional note); `EscalationAnswer.settings_version` records the settings version an "always" stored; `NeedsYouKind` gains `tool_approval` (title ``Allow `<what>`?``, items the Worker's reason then the rule); `ToolGrantConfig.approved` (`ApprovedToolRule[]`, exact allow rules with their source) is the project's stored "always" list, parsed again and validated by `@forge/tools`.
- Needs-you items (d-0172): `NeedsYouItem` (`kind`, `title`, `items`, `actions`, `raised_at`, `seq`, optional `ticket_id` and `interaction_id`) is what the dock draws, and `domain/needs-you.ts` decides the list as pure functions: `scanNeedsYou()` (newest-first history says raised, settled or unknown), `raiseItem()` (an old event gets its kind from its actions and a default title), `escalationItem()`, `cardNeedsYouItems()` (the card's raise while it flags itself, then owner escalations; none for a closed card) and `ticketNeedsYouItems()` (owner escalations plus finished work waiting for review or sign-off). `CardDetail.needs_you_detail` carries the card's items.
- `Ticket` gains `rework_count` and optional `blocked_reason`. There is no `needs_you` status; "Needs you" is a view over `waiting_human`.
- Extra events `asked` / `answered` move a ticket between InProgress and WaitingHuman for a Worker question. `parked` (non-blank reason, becomes `blocked_reason`) holds a Planned or InProgress ticket in WaitingHuman when no question exists; `unparked` releases it to Planned (not `answered`, since a parked ticket may never have run). `rework` is the human "changes requested" and is uncapped. `gate_passed` on tier A stays in Verifying and `merged` then finishes it. `cancelled` is allowed from every non-terminal status: inbox, planned, in_progress, blocked, waiting_human, verifying, review and needs_signoff (director-core.md §4 lists all eight as of this change; earlier drafts listed fewer).
- Relation kinds are five (blocks, depends_on, related, supersedes, spawned_from).
- `ErrorFamily` is auth, rate_limit, quota (the account's usage window is used up: the whole harness waits for the reset instead of a short backoff, d-0097), budget, stall, refusal, crash, policy_denied, unknown, invalid_input (execution-plane.md listed different names). `InvalidInputError` used to be an `unknown` subclass; it has its own family now, so code that tested `instanceof UnknownForgeError` for it must test the class or the family instead.
- The Director's planning flow is data (code.md rule 9, d-0146): an ordered, validated step list with two locked steps, so safety rules are code and the rest is editable in Settings; playbooks are config rows, never repo files (d-0141 item 3), so every step can record the config version it used. `RepoReader` is a port so the engine never touches git and the Director sees only the committed tree. See `docs/briefs/s2-director-planning.md`.

## Requirements

- Node 24.20 and pnpm; no native binaries, no env vars, no `.forge/` files, no external services.
- `pnpm build` at the root runs `tsc -b` and produces `dist/`. The `development` export condition resolves `src/` for tests and typecheck.
- Inside the package use the `#/` alias (from `package.json` `imports`); tests also get `#tests/` for `__tests__/helpers`.
- Tests: `pnpm test` at the root (vitest with coverage). Coverage floor is 70% lines on this package.

- `TriggerAdapter` (`types/ports/trigger.types.ts`, types only): one ticket source. `id`, `source` (the `IntakeEvent.source` it owns), `capabilities()` (`{ push, poll }`), `normalise(raw)` (raw source payload to a validated `IntakeEvent` of its own source; deterministic, so a redelivery has the same dedupe key; throws a `ZodError` on junk, never a partial event) and, for polled sources, `poll(since)` (events at or after the cursor; overlap is fine because the engine dedupes). `IntakeEvent` also carries an optional `author` (`{ kind: 'user' | 'github', login? }`) for the GitHub allow-list (d-0112), and the `github_issue` source.

## Extending

- A new harness implements `WorkerDriver` in `packages/drivers/src/adapters/<name>/`; a new database implements `StorageAdapter` in `packages/db/src/adapters/<name>/`. Both import only `@forge/core` and must pass the contract test. If an implementation needs a core change, fix the interface instead.
- A new schema goes in `src/schemas/` with its `z.infer` alias beside it; hand-written types go in `src/types/` as `<name>.types.ts`; export from `src/index.ts`.
- A new ticket source implements `TriggerAdapter` in `packages/triggers/src/adapters/<name>/` and passes `describeTriggerAdapterContract`; it needs no core change unless it needs a new `IntakeSource` value.
- A new ticket event goes in `types/ticket-events.types.ts` and `domain/state-machine.ts`, with property tests.

## Limits

- Lane triage here is only the deterministic pre-check; the LLM triage step is not in core.
- Core defines the `WorkerDriver` and `StorageAdapter` shapes but contains no implementation of either.
- Core defines the `GitHost`, `SecretStore`, `Gate` and `WorktreeManager` shapes only; implementations live in `@forge/git`, `@forge/secrets` and `@forge/gates`.
- A project override cannot clear an optional key (`remote`, `git_host`) back to unset, and project settings cannot override the company-wide `forge` dials; both need a null/tombstone convention not decided yet.
- `IntakeEvent.author` is not stored yet (the `intake_events` table has no column; it arrives with the GitHub Issues adapter and its migration).
- Gate selection and ledger routing by tier are not modelled here.
- The phase moves S2 needs (grill answers, plan versions, approval floor) are events of `transitionCard` only; no content schemas (`GrillQuestion`, `PlanVersion`) exist yet. A card's column has no separate "outsider's issue awaiting approval" input (d-0107 lists them under Needs you); the rollup sees tickets and pending interactions only. A Discussion cannot be marked resolved: closing it with a reason is the only way out of Shaping.
- `GitHost.merge` pins the merge to a head sha, but whether the host can enforce that atomically is the adapter's business (GitHub: the `sha` field; local bare repo: a ref check under the PR lock).
- The approval floor is a pure function over facts the engine gathers; it cannot see a risk the model failed to put in the typed verify findings. Config revision is the company version plus the project version (rises on every save at either scope), not a single stored number.
- Agents: `write_scope` and the tool list are enforced by `admit()` (see `@forge/tools`), but a `minutes` budget is stored and not enforced by any driver, and `inputs` and `output` are stored for the lane pipelines (S5b) and not used yet.
