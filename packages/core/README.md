# @forge/core

The pure domain layer of Forge: schemas, the ticket state machine, lane triage, ids, branch names, typed errors and the ports every adapter implements.

## Why it exists

The Director engine, the HTTP API, the gates and the Workers' drivers all touch the same tickets, runs and events. If each had its own idea of what a ticket status means, who may move it, or what a run result looks like, a ticket could skip verification, reach Done without the sign-off its tier needs, or loop through automatic rework forever. Core is the one place those rules live. It has no IO, no database and no harness names, so the same rules run identically in the engine, in tests and on replay, and a new storage backend or harness never forces a change here.

## What it does

Public API (`src/index.ts`):

- Data home: `resolveDataHome({ platform, env, homedir, bootstrapHome? })` is the one rule for where Forge keeps its own files, shared by the server and the CLI and pure (it reads nothing from the machine). `FORGE_HOME` (development and tests only) wins over the folder named in the bootstrap file `forge-home.json`, which wins over the platform default (Windows `%LOCALAPPDATA%\Forge`, macOS `~/Library/Application Support/Forge`, Linux `$XDG_DATA_HOME/forge` or `~/.local/share/forge`); a relative or empty override throws `InvalidInputError`. `bootstrapFilePath()` says where the bootstrap file lives, `parseBootstrapFile()` (schema `BootstrapHomeFile`) validates its text, `dataHomeLayout(home, platform)` names `forge.db`, `secrets/`, `memory/`, `worktrees/`, `runs/`, `backups/`, `logs/`, `server.json` (schema `ServerRecord`: pid, port, startedAt, version, written by the running server for the CLI), `install-token` (the API token) and `server.lock` (single-instance lock) under it (d-0098, d-0093). Writing the bootstrap file is a later UI feature.
- Ids: `makeTicketId`, `parseTicketId`, `TicketId`. Ticket ids are `<PROJECT>-<n>`; the prefix is `[A-Z][A-Z0-9]{0,9}`, numbers are positive with no leading zero. The parser never throws.
- Cards (d-0105 .. d-0107): `Card` (the intake record: `id`, `project`, `type`, `title`, `summary`, `source {kind, ref}`, `created_by {type, id}`, timestamps, optional `closed_reason` and `budget_cap_usd`, and the stored lifecycle `phase`, `phase_version`, `needs_you`, `priority` and `links`), `CardColumn` (`shaping`, `needs_you`, `queued`, `in_progress`, `done`, `closed`; `new` is gone, d-0139), `CardType` (a registry entry as data: `name`, `label`, `icon`, `allowed_sources`, `actions`, `plan_approval` (`director_or_user | user`), `tickets_on_intake` (only `pr_issue` is true), optional `default_lane`) with `BUILTIN_CARD_TYPES` (discussion, plan, issue, pr_issue), `CardEvent` / `NewCardEvent` (history, a union keyed by `kind`: `user_message`, `director_message`, `ticket_created`, `ticket_state`, `interaction_opened`, `interaction_answered`, `type_changed`, `card_closed`, `budget_warning`, `note`) and the card API bodies (`CardListQuery`, `CardSummary`, `CardDetail`, `CardEventsQuery`, `CardPatchBody`). Card ids are `<PROJECT>-C<n>` (`makeCardId`, `parseCardId`, `CardId`): the `C` keeps a card id from ever reading as a ticket id. `Ticket.card_id` and `TicketSummary.card_id` link a ticket to its card. `rollupCardColumn(card, tickets, pendingInteractions)` is the one rule for a card's column (d-0139): Closed (phase `closed` or a reason set), else Needs you (`cardNeedsYou`: the card's own flag, a ticket in `waiting_human` / `review` / `needs_signoff`, or a pending question on one of its tickets), else by phase (`grilling` / `verifying` / `plan_ready` Shaping, `approved` / `queued` Queued, `in_progress`, `done`). Ports `CardRepository` (also `findBySource` for the create dedupe and `updatePhase`, the phase CAS), `CardEventRepository`, `CardTypeRepository`, `CardRelationRepository`, `CardReplyQueueRepository` and `TicketRepository.listByCard` are on `StorageTx`.
- Card flow (d-0128 .. d-0143): `CardPhase` (`grilling`, `verifying`, `plan_ready`, `approved`, `queued`, `in_progress`, `done`, `closed`), `CardPriority` (`low`..`urgent`) and `CardRelation` (`{from, to, kind: 'depends_on'}`; "blocks" is the reverse view). `transitionCard(card, event)` is the one door for the phase: events `start_verifying`, `plan_written`, `regrill`, `approve`, `queue`, `start`, `complete`, `close`, `needs_you_set`, `needs_you_cleared`; a CAS on `phase_version` (`expected_version`), a bump on every accepted event, closed is a dead end, and `approve`, `complete` and `close` clear `needs_you`. `findCycle(existing, added)` is generic over the id type (cards now, tickets later) and returns a closed path (`[a, b, c, a]`) or null. `CardReplyQueueItem` / `NewCardReply` are the durable queue of owed Director replies (`card_created`, `user_message`). `ProjectEventSink` / `QueryKey` is the port the engine uses to say which web queries went stale. `Interaction.card_id` (optional) lets a question belong to a card. `chatActionRefusal(type, kind, phase)` refuses `create_ticket` while the card is grilling, verifying or has a plan awaiting approval.
- Card chat (d-0109, d-0112): `CardMessageBody` (`{text 1..8000, author 1..200}`, strict), `CardChatOutput` (`{reply, actions}`, at most five actions; the `card_chat` Director step output), `CardChatAction` (closed union: `create_ticket {title, body, lane?}`, `steer_run {ticket_id, message}`, `change_type {type}`, `suggest_close {reason}`; not to be confused with the registry action name `CardAction`), `ActionTaken` (`{action, result: done|refused, summary}`), `CardDirectorStatus` (`{state: idle|thinking|error, last_error?}`, the `director` field of `CardDetail`). New card events: `director_message` may carry `actions_taken`, `director_action` (an executed action), `close_suggested`. `allowedChatActions(type)` and `chatActionRefusal(type, kind)` say which actions a card type allows from its registry `actions` (every action needs `chat`; `create_ticket` needs a type that starts tickets; `change_type` needs `convert`; `suggest_close` needs `close`); `checkTypeChange(card, nextType, name)` is the retype rule shared by `PATCH /cards/:id` and the chat. `card_chat` is a fourth Director step (`STEP_NAMES`, `models.director.card_chat`).
- Branches: `branchName`, `parseBranchName` for `<type>/<id>-<slug>`. The slug falls back to `untitled` when the title has no ASCII content.
- State machine: `transition(ticket, event)` returns `Result<Ticket, TransitionError>` and never throws. Events carry `at` (keeps it pure) and optional `expected_version` for compare-and-swap. Automatic `gate_failed` rework is capped at two loops, then the ticket goes to `waiting_human` with a reason. `done` from Review or NeedsSignoff is the human approve and merge; tier C needs a non-blank `signer` (whitespace-only is refused). `triaged` raises the lane and never lowers it. Every verify cycle needs its own `gate_passed`: `verifying`, `gate_failed` and `rework` clear `tier_actual`, so `merged` can never ride on a pass from an earlier cycle. A cleared optional field (`blocked_reason`, `tier_actual`) is emitted as a present-but-undefined key so a storage patch built from the result clears the column.
- Home, Cost, Runs and Inbox shapes: `StatsRange` / `StatsRangeQuery` / `SeriesPoint` (dense UTC-day series), `ProjectStats`, `CostReport` (`COST_TOP_N`), `RunSummary` / `RunListQuery` / `RunListPage` / `RunDetail`, `InboxItem` / `InboxListQuery` / `InboxPage` / `InboxCounts` / `InboxStateRow`, and the pure rules `computeProjectStats`, `computeCostReport`, `statsWindow`, and the inbox rules (`inboxItemId`, `applyInboxMarks` where a read or archive mark holds only while the item's `updated_at` is not newer than the mark's stamp, `inInboxView`, `inboxCounts`, `markInbox`). Storage gains `runs.list` (`RunListFilter` / `RunListKey`), `inboxStates`, `harnessVersions.listByCompat` and `harnessToolSchemas.listByStatus`.
- First-run and new-project shapes: `SystemInfo` / `FirstRunState` (`GET /system`) and `ProjectInspection` (`POST /projects/inspect`), `FolderListing` / `FolderEntry` (`GET /fs/folders`, the sub-folders of one folder for the folder browser, each with its `modified_at`; empty `path` with null `parent` is the roots view), `FolderPickBody` / `FolderPick` (`POST /fs/pick-folder`, the system folder window: `picked` with a path, `cancelled`, or `unavailable` with a reason), `FolderCreateBody` (`POST /fs/folders`, make one folder) and `FolderRevealBody` / `FolderReveal` (`POST /fs/reveal`, show a folder in the file manager: `opened` or `unavailable`), plus `suggestSlug()` / `suggestPrefix()` (a valid, unused project slug and ticket prefix from a folder name).
- Ticket list shapes: `TicketSummary` (the board card; `state` is the status, `needs_you` is true for `NEEDS_YOU_STATUSES`), `TicketListQuery` (`state[]`, `limit` 1..`TICKET_LIST_MAX_LIMIT` default 100, `cursor`), `TicketListPage`, and the `TicketListKey` / `TicketListFilter` types that `tickets.listByProject` pages by.
- `toTicketPatch(next)`: the `TicketPatch` that stores a transitioned ticket with `updateTicketCas`. It drops `id`, `project`, `created_at`, `status_version` (storage owns the version) and the derived `parent` / `blocked_by`, and keeps the explicit clears (also for the nullable engine fields `assignee_run_id`, `branch`, `worktree`, `checkout_run_id`, `epic_id`, `created_by_intake`, `pr_number`, `pr_url`).
- Git host and secrets: `GitHost` (`push`, `openPr`, `findPr` (the open PR for a branch, so a crash between opening and storing a PR adopts it instead of opening a second), `prStatus`, `merge(n, method, expectedHeadSha)`, `closePr`, `deleteBranch`; only the engine's merge step calls `merge`, and the host refuses with `HeadMovedError` when the PR head is not the commit the gates judged), `SecretStore` (`get`, `put`, `delete` (idempotent), `list(prefix)` (sorted); names are namespaced paths matching the `SecretName` schema, lowercase `/`-joined segments such as `github/<connection>/key` that can never address a path outside the store; `assertSecretName` / `assertSecretPrefix` throw `InvalidInputError`) and `ProjectConfig.git_host` (`GitHostConfig`: `local` with `remote_path`, or `github` with owner, repo, `installation_id` and, only when the project has no GitHub connection, `app_id` and `key_secret`; `base_branch` defaults to `main`). `Ticket.pr_number` and `pr_url` link the ticket to its PR.
- Project settings (d-0095): `ProjectConfigShape` / `ProjectConfig` carry `checks: [{name, role: test|lint|typecheck|build|format|custom, command, cwd?}]` (list order is run order; names unique; `command` non-empty; `cwd` relative with no `..`), `ecosystems: string[]` (`node`, `python`, `go`, `rust`, `jvm`, `dotnet`, `ruby`, `php`, `cmake`; empty means the gates detect them) and optional `gate_rules` (`GateRules`: extra `config_globs`, `test_globs`, `skip_patterns`, `replace`). They replace the old `profile` + `commands` (d-0034). `migrateLegacyProjectDoc()` converts a stored or submitted document in the old form (lint, typecheck, test, build in that order; `typecheck` dropped under `generic`; `ts` gives `ecosystems: ['node']`; an unknown profile is rejected); `ProjectConfig` and `ProjectOverride` apply it on parse, so old config versions read as checks without rewriting the database and new writes use the new shape. A legacy override with no command adds no `checks` key, so it cannot blank an inherited list.
- Versioned settings (d-0085): `ConfigSource` port (`company()`, `project(slug)`, `history(scope, project?)`, `append({scope, project?, doc, author, reason, expectedVersion})`; `append` is compare-and-swap and throws `ConfigVersionConflictError` when the scope is not at `expectedVersion`). Stored documents are overrides: `CompanyOverride` (strict deep-partial of `ForgeConfig`) and `ProjectConfigView.warnings` (optional: what reading an old-format stored document left out; `legacyProjectDocWarnings()` / `migrateLegacyProjectDocWithWarnings()` compute it), `ProjectOverride` (strict deep-partial of `ProjectSettings`, which is `ProjectConfig` without `slug` and `prefix`), derived by `deepPartial()`. `mergeConfig(defaults, company, project)` layers built-ins, company, project (objects merge, arrays and scalars replace) and validates the result as `EffectiveConfig = { forge, project }`, throwing `InvalidInputError` otherwise; `mergeCompany` is the company-only form. `BUILTIN_CONFIG` holds the defaults that equal `.forge/config/forge.yaml` today (a test pins it) plus generic project settings.
- Many projects (d-0082, d-0094): `Project` (the `projects` row) now carries `local_path` (the clone Worker worktrees are cut from), `connection_id`, `repo_full_name` (`owner/name`), `status` (`ProjectStatus`: `onboarding`, `ready`, `archived`; default `ready`) and `ecosystems` (default `[]`). `Project.tier_c_globs` is **deprecated**: settings own the tier-C paths since B3b, the column is stored and never read. `GithubConnection` (`GithubConnectionStatus`, `GithubConnectionId`) is one GitHub App in one org or account: id (a lowercase slug, also a secret-name segment), account, `app_id`, optional `app_slug`, `key_secret_name` (where the private key sits in the SecretStore; the key is never part of this shape), status, `created_at`. `Run.project` names the project of the run's ticket. `DriverRegistry` (`get(harnessId)` or null, `ids()`) is the port the engine uses to pick a ticket's harness; core still names no harness.
- Project memory (d-0007, d-0086): `MemoryRecord` (the front matter of a record: `id` like `d-0001`, `kind`, `statement`, `source`, `author` `user|director`, `origin`, `status`, dates, `supersedes`, `superseded_by`, `tags`, `pinned`; open to extra fields), `MemoryRecordWithBody`, `MemoryListEntry`, and the writer inputs `ProposalInput` (confidence at most 0.8) and `DecisionInput`, neither of which carries an author, status or id. Ports (types only): `MemorySource.slice(slug)` (what triage and dispatch read), `MemoryReader` (`list`, `get`), `MemoryWriter` (`propose`, `decide`, `approve`, `reject`, `supersede`, `appendOutcome`, each one commit returning `{ id, commit }`) and `ProjectMemory` (`init`, `reader`, `writer`). `MemoryRecordNotFoundError` and `MemoryRecordStateError` (family `invalid_input`) tell "no such record" from "already answered". The implementation is `@forge/memory`.
- Gate reports: `ReportStore` (`put(runId, name, text)` returns the reference stored in `gate_results.report_ref`); the engine saves every gate report through it.
- Gates: the `Gate` port (`name`, `run(ctx)`), `GateContext` (ticket, run, project config, worktree path, base sha, the Worker's claims) and `GateVerdict` (status, findings, report). Gates that need the receipt log get it injected at construction; core holds no receipt types. `Claim` (the typed assertions a Worker makes in `finish`) lives here so the MCP tool and the gates share it.
- `WorktreeManager.diff(path, baseSha)` returns `WorktreeDiff`: per-file status (A/M/D/R, with `oldPath` for renames) and the unified patch, covering committed, uncommitted and untracked changes.
- Lane triage: `preCheckLane`, `maxLane`. Deterministic first step: touched paths against tier-C globs, predicted file count (Express allows at most 3), body length (at most 2000 chars) and ticket type (`ci` counts as infra). A tier-C glob hit forces Full.
- Schemas and inferred types: `Ticket`, `Lane`, `Tier`, `TicketType`, `TicketStatus`, `TicketRelationKind`, `TicketRelation`, `IntakeEvent`, `StoredIntakeEvent`, `Run` (with `config_version`, `c<company>:p<project>`, validated by `ConfigVersionRef`), `RunStatus`, `RunRequest`, `RunResult`, `RunEvent`, `InteractionKind`, `Interaction`, `WakeRequest`, `RunInboxMessage`, `GateResult` (with the nullable `head_sha` the gates judged), `Project` (the `projects` row), `Harness` (the `harnesses` row: kind, optional executable path, `HarnessAuthMode` `login|api_key|oauth_token`, last test status), `HarnessSecretKind` and `harnessSecretName(id, kind)` (`harness/<id>/api-key` or `harness/<id>/oauth-token`, one place for the server and the driver), `ProjectConfig` (the project.yaml, including `tier_c_globs`, default `.forge/**`, `.claude/**`, `.github/**`), `DriverCapabilities`, `Sha256Hex`. `Preflight.harnessVersion` is the harness build alone (not the adapter), for the catalogue's reviewed-version check.
- Scheduling data (d-0097, d-0080): `Ticket.priority` (integer, default 0, higher starts first inside its project; rows without one read as 0), `HarnessState` and the `HarnessStateRepository` port (`get`, `upsert`, `clear`, `list`: a harness parked until `paused_until` with a plain-language `reason`, set when a run ends out of quota), and the layered Worker limits of `engine`: `max_concurrent_global` (default 2), `max_concurrent_per_project` (1), `max_concurrent_per_harness` (`{default: 2, by_id}`), plus `quota_default_pause_ms` (1 h), `shutdown_drain_ms` (10 s: how long a graceful stop waits for running tool calls to record their effect before runs are interrupted; 0 = do not wait) and `harness_fallbacks` (installed harnesses to try, in order, when a ticket's own is out of quota; empty means wait). A project's settings may add `max_concurrent` (lowers its own cap, never raises the company's) and its own `harness_fallbacks`. Stored company documents that still say `engine.global_slots` are read as `max_concurrent_global` (`migrateLegacyCompanyDoc`, applied by `CompanyOverride`).
- Harness compatibility (d-0088): `HarnessStatus` gains `paused` (the installed build failed its check; `Harness.status_note` says why in plain words), `CompatReport` (kind, version, `checks` of `CompatCheckId` with `pass|fail|skipped`, captured tool shapes, one-sentence `summary`), `HarnessVersion` (`kind`, `version`, `compat` `pass|fail|pending`, optional report), `HarnessToolSchema` (`harness_kind`, `version`, `tool`, `schema_hash`, `status` `approved|pending|denied`, `decided_by`, `decided_at`, `decision_reason`), and the storage repositories `harnessVersions` and `harnessToolSchemas` (`StorageTx`). `ProjectConfig` gains optional `tool_grants` (`ToolGrantConfig`: `allow`, `deny`, `rules`, the shape of a tool `Grant`, parsed again by `@forge/tools` before use), so a project can narrow what its Workers may use.
- Run lifecycle: `RunStatus` is `starting`, `running`, `settling`, `settled`, `interrupted` plus the terminal results. `Run` carries `owner` (the Forge server instance, required) and optional `pid`, `last_event_at`, `final_chain_hash`, `catalogue_hash`, `prompt_hash`, `hook_registered_at`, `retry_of`, and the resume fields `generation` (run secret generation, absent reads as 1), `resumable_session` and `interrupted_at` (d-0092, d-0100); `RunRequest.generation` tells the app which generation's secret to register. `interrupted` is a run a restart found or made: not active and not ended (no `ended_at`), resumed on the same row. `RUN_TRANSITIONS`, `canTransitionRun()` and `assertRunTransition()` (`domain/run-lifecycle.ts`) are the table of allowed moves: starting/running/settling to `interrupted` (shutdown), `interrupted` to `running` (resume) or `settled` (gave up), nothing out of a terminal status; the storage adapters enforce it for moves into and out of `interrupted`. `isRunActive(run)` is the one liveness rule (status `starting` or `running` and no `ended_at`); the hook handler and the MCP server both use it.
- **Resume is a new run row.** Resuming a run creates a new `runs` row whose `retry_of` names the old one; a run that has `ended_at` is never reopened (storage refuses to clear `ended_at` or move an ended run back to `starting` / `running`). `RunResult.status` gains `paused`, which must carry `pauseReason: 'interaction'` and the `interactionId` to answer; the Director resumes it as a new run.
- Run events: besides tool_call, tool_result, text, ask, finish, error and usage, `permission` (`interaction_id?`, `call_id`, `tool`, `decision`), `inbox_delivered` (`inbox_seq`, `mode`), `session` (`session_ref`) and `hook_liveness` (`fingerprint`). `InteractionKind` is `question`, `plan_confirm`, `permission`, `blocked` (a Worker's `report_blocked`). Also `user_message` (`inbox_seq`, `mode`, `author`, `text`): a person's message to a Worker, written by the engine with its inbox row so the live thread shows it before delivery; `inbox_delivered` (written by the driver) pairs with it by `inbox_seq`. `SteerRunBody` (`{message: 1..8000 chars trimmed, author: 1..200}`, strict) is the body of `POST /runs/:id/steer`. The capability to steer live is `steerModes` containing `steer`; there is no separate flag.
- `RunRequest` adds `runId`, `projectId`, `lane`, `promptHash`, `mcpIdentity` (the server name the run's Forge MCP server is registered under). `permissionPolicy` and `tools` are optional: the app derives both from `visibleTools()` over the run's `AdmitContext`, so the request is not a second policy source.
- Errors: `ForgeError` (carries `errorFamily`) and one subclass per family: auth, rate_limit, `QuotaError` (family `quota`, optional `resetAt`), budget, stall, refusal, crash, policy_denied, unknown, `InvalidInputError` (family `invalid_input`: a caller bug such as a rejected patch, a bad constructor argument or a constraint violation; never retried as-is) and `HeadMovedError` (family `invalid_input`: a PR head moved after the gates judged it; the engine answers by gating the new head, not by retrying or parking), `ProjectNotFoundError` (a settings read named a slug that is not a project) and `HarnessChangedError` (family `policy_denied`: the installed harness build is not the one whose tool approvals were loaded; its message starts with `harness_changed:` and is the ticket's park reason). Also `ok`/`err` Result helpers and `globMatch`.
- Glob grammar (`globMatch(glob, path)`): `*` is any run of non-slash characters, `?` one non-slash character, `**` anything including slashes (`**` followed by a slash also matches zero directories); every other character is literal; backslashes in the glob or the path are read as `/`. Matching is case-sensitive by default; tier-C checks pass `ignoreCase` because Windows and macOS file systems are case-insensitive (`.GitHub/workflows/ci.yml` is `.github/...`). A pattern with no slash matches the name at any depth, like gitignore (`*.sql` matches `db/migrations/x.sql`); a pattern containing a slash is anchored to the root (`db/*.sql` does not match `app/db/x.sql`). Runs of `*` and repeated `**` followed by a slash are collapsed before compiling, so a hostile pattern cannot cause catastrophic backtracking. No negation, no character classes, no braces.
- Ports (types only): `WorkerDriver` (`capabilities`, `preflight`, `start`, `resume`, `steer`, `cancel`, `events`, `result`; `steer(handle, message, mode, inboxSeq?)`: the optional `inboxSeq` is the `run_inbox` row being delivered, echoed in the `inbox_delivered` event) and `StorageAdapter` (`transaction`, `close`; the repositories `tickets` (with `listByProject`), `ticketRelations`, `runs`, `runEvents`, `runInbox`, `runTokens`, `intakeEvents`, `interactions`, `wakeRequests`, `gateResults`, `projects`, `harnesses`, `githubConnections` hang off the transaction). **`ticket_relations` is the one source of truth for parent and blocker links**: `Ticket.parent` (first `spawned_from` edge out of the ticket) and `Ticket.blocked_by` (its `depends_on` targets plus the sources of `blocks` edges into it) are derived on every read, are not columns, and are not patchable; `tickets.insert` records a seeded `parent` / `blocked_by` as edges, later changes go through `ticketRelations.add/remove`. `interactions.answer(id, answer, at)` and `expire(id, at)` are compare-and-swap from `pending` (`expire` also waits for `timeout_at`) and return a boolean; `intakeEvents.insertIfNew` returns `{ inserted, event }` with the stored id and `markTicket(id, ticketId)` links it; `wakeRequests` is idempotent on (ticket, reason, key) and counts recent wakes for the re-wake cap. `updateTicketCas(id, expectedVersion, patch)` always sets `status_version` to `expectedVersion + 1`; a patch carrying `status_version` is refused (`TicketPatch` no longer has the field), and a key present with value `undefined` clears an optional column. `RunEventRepository.append(runId, event: NewRunEvent)` takes the event without `seq` and returns the stored event: storage is the only `seq` allocator (0-based, max+1 per run). `RunTokenRepository` (`issue`, `reissue`, `getHash`, `revoke`; `put` is a deprecated alias of `issue`) keeps per-run bearer tokens as SHA-256 hashes only; `issue` throws `PolicyDeniedError` for a run whose token was revoked, and only the explicit `reissue` re-arms it. The per-run HMAC secret is never part of any port or stored.

Layout follows the repo skeleton: `schemas/`, `types/` (`types/ports/` for the two ports), `domain/`, `shared/`, with tests in `__tests__/` mirroring `src/`.

Project onboarding shapes (d-0124): `ProjectInspection` carries `git` (`repo` / `none` / `inside_repo`, repo root, subfolder, commits, dirty, remote) and `snapshot` (files, bytes, `.gitignore`, truncated); `GitSetup` and `ProjectScope` are the register-body choices; `Project` has optional `repo_root` and `subfolder`; `GitHostConfig` has a `local_repo` kind for projects with no remote.

## Why this approach

- `zod@4.6.7` is the only dependency. Schemas are the source of truth for types, DB rows, HTTP bodies, config and LLM step output; types come from `z.infer`, so nothing is declared twice. Parsing happens at every boundary.
- Result values instead of exceptions for expected failures (`transition`, id parsing), so callers must handle illegal moves. Unexpected failures throw `ForgeError` subclasses; retry, stall and kill decisions read `errorFamily`, not the message.
- One `transition()` for status changes (the single door). It takes an optional version for CAS so racing writers lose atomically in storage.
- Driver-boundary shapes are camelCase; DB rows (`Run`, `Ticket`, `Interaction`) are snake_case.
- `RunRequest` has no `AbortSignal` (not serializable); cancellation goes through `WorkerDriver.cancel`.
- Ports live here, not in the adapters, so adding a harness or database is a new folder elsewhere and never a core edit (d-0016, d-0047).

Where the design docs were silent, the simplest option was taken:

- `Ticket` gains `rework_count` and optional `blocked_reason`. There is no `needs_you` status; "Needs you" is a view over `waiting_human`.
- Extra events `asked` / `answered` move a ticket between InProgress and WaitingHuman for a Worker question. `parked` (non-blank reason, becomes `blocked_reason`) holds a Planned or InProgress ticket in WaitingHuman when no question exists; `unparked` releases it to Planned (not `answered`, since a parked ticket may never have run). `rework` is the human "changes requested" and is uncapped. `gate_passed` on tier A stays in Verifying and `merged` then finishes it. `cancelled` is allowed from every non-terminal status: inbox, planned, in_progress, blocked, waiting_human, verifying, review and needs_signoff (director-core.md §4 lists all eight as of this change; earlier drafts listed fewer).
- Relation kinds are five (blocks, depends_on, related, supersedes, spawned_from).
- `ErrorFamily` is auth, rate_limit, quota (the account's usage window is used up: the whole harness waits for the reset instead of a short backoff, d-0097), budget, stall, refusal, crash, policy_denied, unknown, invalid_input (execution-plane.md listed different names). `InvalidInputError` used to be an `unknown` subclass; it has its own family now, so code that tested `instanceof UnknownForgeError` for it must test the class or the family instead.

## Requirements

- Node 24.20 and pnpm; no native binaries, no env vars, no `.forge/` files, no external services.
- `pnpm build` at the root runs `tsc -b` and produces `dist/`. The `development` export condition resolves `src/` for tests and typecheck.
- Inside the package use the `#/` alias (from `package.json` `imports`); tests also get `#tests/` for `__tests__/helpers`.
- Tests: `pnpm test` at the root (vitest with coverage). Coverage floor is 70% lines on this package.

- `TriggerAdapter` (`types/ports/trigger.types.ts`, types only): one ticket source. `id`, `source` (the `IntakeEvent.source` it owns), `capabilities()` (`{ push, poll }`), `normalise(raw)` (raw source payload to a validated `IntakeEvent` of its own source; deterministic, so a redelivery has the same dedupe key; throws a `ZodError` on junk, never a partial event) and, for polled sources, `poll(since)` (events at or after the cursor; overlap is fine because the engine dedupes). `IntakeEvent` also carries an optional `author` (`{ kind: 'user' | 'github', login? }`) for the GitHub allow-list (d-0112), and the `github_issue` source.

## Extending

- A new harness implements `WorkerDriver` in `packages/drivers/src/adapters/<name>/`; a new database implements `StorageAdapter` in `packages/db/src/adapters/<name>/`. Both import only `@forge/core` and must pass the contract test. If an implementation needs a core change, fix the interface instead.
- A new schema goes in `src/schemas/` with its `z.infer` alias beside it; hand-written types go in `src/types/` as `<name>.types.ts`; export from `src/index.ts`.
- A new ticket source implements `TriggerAdapter` in `packages/triggers/src/adapters/<name>/` and passes `describeTriggerAdapterContract`; it needs no core change unless it needs a new `IntakeSource` value.
- A new ticket event goes in `types/ticket-events.types.ts` and `domain/state-machine.ts`, with property tests.

## Limits

- Lane triage here is only the deterministic pre-check; the LLM triage step is not in core.
- Core defines the `WorkerDriver` and `StorageAdapter` shapes but contains no implementation of either.
- Core defines the `GitHost`, `SecretStore`, `Gate` and `WorktreeManager` shapes only; implementations live in `@forge/git`, `@forge/secrets` and `@forge/gates`.
- A project override cannot clear an optional key (`remote`, `git_host`) back to unset, and project settings cannot override the company-wide `forge` dials; both need a null/tombstone convention not decided yet.
- `IntakeEvent.author` is not stored yet (the `intake_events` table has no column; it arrives with the GitHub Issues adapter and its migration).
- Gate selection and ledger routing by tier are not modelled here.
- The phase moves S2 needs (grill answers, plan versions, approval floor) are events of `transitionCard` only; no content schemas (`GrillQuestion`, `PlanVersion`) exist yet. A card's column has no separate "outsider's issue awaiting approval" input (d-0107 lists them under Needs you); the rollup sees tickets and pending interactions only. A Discussion cannot be marked resolved: closing it with a reason is the only way out of Shaping.
- `GitHost.merge` pins the merge to a head sha, but whether the host can enforce that atomically is the adapter's business (GitHub: the `sha` field; local bare repo: a ref check under the PR lock).
