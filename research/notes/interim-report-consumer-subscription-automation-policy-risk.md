# Interim report: consumer-subscription-automation-policy-risk

**Locus question:** If heavy agentic workloads route through flat-rate consumer subscriptions via automation harnesses to beat per-token API costs, what are the vendor ToS, rate-limiting, and account-suspension risks at software-factory scale?
**Flavor:** convergent

## What the corpus already said

The width corpus answers the dollar-economics half of Pillar 6 thoroughly but is silent on compliance/viability. [[claude-subscription-vs-api-which-is-cheaper-in-2026-real-math-teamorouter]] (a vendor blog) models subscription-vs-API cost crossover purely on session/weekly usage caps, concluding "CI/CD, background agents, and multi-seat teams exceed subscription session/weekly caps and are economically forced onto metered API billing" — but frames this as a *capacity* constraint, not a *policy/enforcement* risk. It never mentions Terms of Service, account suspension, or automation legitimacy; the only "forcing function" it names is the usage cap itself. [[usage-based-ai-pricing-vs-flat-subscriptions-what-the-github-copilot-shift-means]] and [[ai-pricing-models-compared-seats-tokens-outcomes-zuora]] both discuss the GitHub Copilot flat-to-metered pivot as a *margin economics* story (Copilot's per-seat subscription allegedly ran a $20/user/month loss against a $10 fee per the WSJ's Oct 2023 reporting) — again, a vendor-side cost problem, not a user-side compliance problem. None of the three corpus notes mention ToS enforcement, rate-limit detection of automation, or suspension. This is a genuine audited absence: the corpus treats "subscription caps you out eventually" as the only risk, when the sharper risk is that automation of a consumer UI/CLI may be an explicit ToS violation independent of whether you stay under the cap.

## What the new sources say

**[[legal-and-compliance-claude-code-docs]]** — Anthropic's own Claude Code legal/compliance page, the ground-truth primary source. It draws an explicit line between authentication methods, not just usage volume: "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications... Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication." Critically: "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users... Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice." It also states that "advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK" — i.e., the published caps are calibrated for a human in the loop, not a scripted harness, and Anthropic retains unilateral, no-notice enforcement discretion. The carve-out: an end user signing in to the *unmodified* Claude Code binary with their *own* subscription is fine — the violation is specifically about third-party intermediation/resale of credentials, not all automation per se.

**[[anthropic-puts-claude-agents-on-a-meter-across-its-subscriptions-infoworld]]** (InfoWorld, May 14, 2026) documents that this isn't theoretical: Anthropic actually moved against exactly this pattern. In April 2026 Anthropic announced via X that Claude subscriptions "would 'no longer cover usage on third-party tools like OpenClaw,' citing compute capacity restraints." A follow-on policy, announced for June 15, 2026, would have separated "programmatic Claude usage from standard chat subscription limits, introducing a dedicated monthly credit system, billed at API-style rates, for tools including its Agent SDK, GitHub Actions, and third-party frameworks such as OpenClaw." Developer reaction was sharp: senior data scientist Yadesh Salvi wrote "The monthly limit you are providing won't even last a day of serious work," and SRE Advait Patel warned "a runaway agent or a bad prompt can burn through credit fast and then either stop your pipeline or quietly start garnering extra usage" — i.e., the failure mode isn't a clean ban, it's an opaque throttle/overage trap for production automation. Analyst Sanchit Vir Gogia generalized this as an industry pattern: "Over the next 12 to 24 months, enterprises should expect more vendors to create separate consumption pools for agents, premium models, tool use, background tasks, and third party integrations... The direction will not [vary]."

**[[use-the-claude-agent-sdk-with-your-claude-plan-claude-help-center]]** — the single most important finding for calibration purposes. Anthropic's own live Help Center article shows the June 15 metering separation never actually took effect as announced: "Update June 15, 2026: We've paused the previously-announced changes to Claude Agent SDK usage. For now, nothing has changed: Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription limits." A later update (Oct 7, 2026) shows Anthropic chose an *additive* fix instead of a punitive one: "Claude Max and Team plans now include monthly API credits, which cover the Claude Agent SDK, `claude -p`, the Claude API, and Claude Managed Agents. You can still use the Claude Agent SDK, `claude -p`, and third-party apps with your subscription limits." As of the fetch date (Oct 12, 2026), programmatic/automated use of a Claude subscription — including through third-party harnesses like OpenClaw — is tolerated and still draws against subscription limits, with extra credits layered on top rather than a hard wall.

**[[anthropic-bans-third-party-subscription-access-to-claude-sesame-disk]]** — a low-quality secondary aggregator (uncited, contains a corrupted/possibly-injected artifact), flagged low-confidence by the fetcher. Its claim that "Anthropic's backend now identifies when a credential is being used from an unapproved client or IP fingerprint, blocking requests that don't originate from official interfaces" is plausible directionally (consistent with the ToS language on enforcement) but unverified against any primary source — treat as unconfirmed color, not evidence.

**[[usage-policies-openai]]** — OpenAI's general content/safety usage policy (effective Oct 29, 2025) does not address the subscription-vs-API automation distinction at all; it's a content-safety policy, not a billing/access policy. The only generically relevant line is "breaking or circumventing our rules and safeguards may mean you lose access to our systems or experience other penalties" — a boilerplate reservation-of-rights clause, not evidence of a specific automation-harness enforcement regime on the ChatGPT Plus/Pro consumer tier. This is itself a finding: OpenAI's publicly posted usage-policy page is silent on ChatGPT-subscription automation specifically (the fetcher did not locate an OpenAI-side equivalent of Anthropic's "OAuth is for ordinary use, API keys are for programmatic use" language within budget — flagged as an open question below).

## Evidence synthesis

Two things are true simultaneously, and the tension between them is the actual finding. First, Anthropic's written policy is unambiguous and currently in force: subscription OAuth credentials are licensed for "ordinary, individual" human-driven use; any third-party product that "routes requests through Free, Pro, or Max plan credentials on behalf of... users" is explicitly out of bounds, and Anthropic reserves unilateral, no-notice enforcement. This is not a theoretical clause — Anthropic acted on it against OpenClaw-style third-party automation tools in April 2026. Second, Anthropic's actual enforcement trajectory in 2026 has been to retreat from hard bans toward soft metering, and then retreat again from hard metering to additive credit pools. The April ban and the announced June 15 metering split were both walked back or paused; the October 2026 resolution is "keep using subscription credentials for Agent SDK/`claude -p`/third-party apps, plus here's extra API credit on top." That is a materially different risk profile than either "banned" or "ToS-compliant and safe" — it is "formally against the letter of ordinary-use language, informally tolerated and in fact subsidized, with an unreviewable right to flip back to enforcement without notice."

The self-use/third-party-intermediation distinction matters enormously for a software-factory architecture and the corpus has not drawn it. A factory where each of N simulated "employee" agents runs under its own individually-purchased Anthropic account, authenticating as itself through the unmodified Claude Code binary, falls on the "ordinary use by the credential owner" side of Anthropic's own carve-out — risk is capped at hitting usage limits, not account suspension, because nothing is being resold or intermediated. A factory that pools a smaller number of subscriptions behind an orchestration/automation layer that logs in on users' behalf, multiplexes one subscription across many automated workers, or wraps subscription OAuth behind a third-party product is exactly the pattern Anthropic named and already enforced against once (April 2026 OpenClaw action) and reserves the right to re-enforce "without prior notice." The economic case for subscription-over-API (made entirely on caps/dollars in the width corpus) silently assumes the second pattern — many cheap subscriptions multiplexed by automation — is the one that saves money at scale, and that is precisely the pattern with the live policy target on it.

OpenAI's side of this is evidentially thinner in this pass: the fetcher could not, within the 4-source budget, locate an OpenAI-specific equivalent of Anthropic's "OAuth = ordinary use / API key = programmatic use" clause. The general Usage Policies page is a content-safety document, not an access/billing-tier document, and gives no automation-specific guidance. This is a genuine gap, not a finding of permissiveness — absence of a clause is not evidence Open AI tolerates ChatGPT Plus/Pro automation, only that this investigation did not locate the governing language in budget.

## Committed position

A software-factory architecture should not route pooled, multiplexed, or resold consumer-subscription credentials through an automation harness to beat API pricing — that specific pattern (many automated "seats" behind one or few purchased subscriptions, or any orchestration layer that logs in as the end user) is the one Anthropic has both named explicitly in its legal-and-compliance docs ("Anthropic does not permit third-party developers to... route requests through Free, Pro, or Max plan credentials on behalf of their users") and already enforced against once, in April 2026, against OpenClaw-style tools, before partially reversing course in October 2026 toward a subsidized hybrid. The economically-optimal-looking strategy the width corpus implicitly endorses — flat subscriptions multiplexed by automation to dodge per-token API pricing at scale — is the exact strategy sitting on Anthropic's "reserves the right to enforce... without prior notice" trigger, and Anthropic's own 2026 track record shows that trigger has already been pulled once and could be pulled again with no warning, with the practical failure mode being either abrupt loss of access or a silent downgrade to metered credit exhaustion mid-pipeline (per Advait Patel's warning) — both catastrophic for an unattended, always-on factory. The one pattern that is textually safe under Anthropic's own carve-out is: each individual simulated "employee" agent authenticates through the unmodified Claude Code binary with its own, individually-purchased, non-resold subscription, used for "ordinary, individual usage" — in which case the only real risk is hitting the published session/weekly cap, not suspension. Recommended mix: use per-seat individually-owned subscriptions (Pro/Max, one per logical "employee" agent, self-authenticated, never pooled or intermediated) only for bounded, interactive-shaped, human-supervisable workloads (single-session coding tasks, code review, within-cap daily usage) where the per-agent economics favor flat-rate pricing (per the corpus's own crossover math at light-to-moderate usage); route all unattended, 24/7, CI/CD-triggered, multi-agent-orchestrated, or credential-pooled workloads through metered API billing with aggressive prompt caching, because that is both the cheaper option at scale per the corpus's own numbers *and* the only option with no ToS exposure, since the API is the channel Anthropic itself designates for "developers building products or services that interact with Claude's capabilities."

- **Position:** Pool/multiplex/resell consumer-subscription credentials behind an automation harness to beat API costs is a documented, live policy target (not a hypothetical risk) for Anthropic, already enforced once in 2026 and reversible without notice; a software factory should treat API billing as mandatory for any unattended/multi-agent/orchestrated workload, and reserve individually-owned, self-authenticated subscriptions only for bounded, human-supervisable, within-cap interactive tasks per logical agent.
- **Confidence:** medium-high for the Anthropic side (grounded in Anthropic's own legal-and-compliance page plus a documented enforcement-and-reversal cycle from two independent sources, one primary); low for the OpenAI side (no OpenAI-specific automation clause located in this budget — the absence is reported, not resolved).
- **Boundary conditions:** This position holds specifically for *pooled or intermediated* subscription use (one or few subscriptions multiplexed across many automated workers, or any orchestration layer authenticating on a user's behalf) — Anthropic's own carve-out exempts an individual, self-authenticated user running the unmodified Claude Code binary even via automation/scripting (`claude -p` is explicitly still permitted under subscription limits as of Oct 7, 2026). It does not resolve whether a factory running, say, 50 individually-purchased Max subscriptions (one per simulated employee, no intermediation) is "ordinary... individual usage" at that scale — Anthropic's language assumes a human purchaser per account but does not define a headcount ceiling, and this is untested.
- **What would change this position:** (a) a documented case of Anthropic suspending or throttling an account that was self-authenticated (not pooled/resold) purely for running `claude -p` or the Agent SDK at high, non-pooled volume — this would show the "ordinary use" carve-out is narrower in practice than the text suggests; (b) Anthropic reinstating the June-15-style hard metering split with no credit offset, which would collapse the economic case for subscription use at any automation volume; (c) discovery of an explicit OpenAI consumer-ToS clause banning ChatGPT Plus/Pro CLI automation, which would extend this risk finding to the OpenAI side with the same confidence as the Anthropic side.
- **Evidence weight:** 1 primary vendor legal doc (Anthropic, high confidence) + 1 primary vendor policy-reversal doc (Anthropic Help Center, high confidence) + 1 contemporaneous trade-press account of the actual ban/metering/reversal cycle (InfoWorld, corroborated by the primary Help Center doc) support the position; 1 low-quality secondary source offers unverified corroborating color (not counted); 1 OpenAI primary source is inconclusive/silent on the specific question (counts as an open gap, not counter-evidence).

## Open questions

- Does OpenAI have an equivalent "OAuth/session login is for ordinary use; automation requires API keys" clause for ChatGPT Plus/Pro, analogous to Anthropic's Claude Code legal-and-compliance page? Not located within this budget.
- Has Anthropic (or OpenAI) documented or acted on any case of an *individually self-authenticated, non-pooled* subscription being suspended purely for automation volume, as distinct from the April 2026 third-party-intermediation (OpenClaw) action? This is the boundary case that determines whether the "one subscription per agent" mitigation is actually safe at 50-5,000-agent factory scale.
- What specifically triggered the April 2026 enforcement action — was it detected via IP/client fingerprinting (per the low-confidence sesamedisk claim) or self-reported/contractual? This matters for whether a factory could evade detection vs. whether evasion itself would constitute an additional ToS breach.
