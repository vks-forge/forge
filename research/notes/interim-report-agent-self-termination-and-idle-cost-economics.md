# Interim report: agent-self-termination-and-idle-cost-economics

**Locus question:** Beyond infra-level VM idle-shutdown (which vendors are explicit is NOT an agent-logic decision), what decision rule should an agent itself use to conclude "clean scan, no issues, self-archive" — distinguished from a silently-failed scan — and what does idle-vs-always-on actually cost at 100-agent fleet scale?

**Flavor:** convergent

## What the corpus already said

The width sweep converged on four sources that, read together, establish the infra layer cleanly but leave the agent-logic layer almost entirely unaddressed — which is itself the load-bearing finding for this locus.

[[idle-shutdown-gemini-enterprise-agent-platform-google-cloud-documentation]] documents Google Cloud's Workbench idle-shutdown: a VM auto-shuts-down after a configurable inactivity window (default 180 min, 10–1440 min range, or any integer-second value via `idle-timeout-seconds`), but "activity" is defined narrowly as kernel activity on `127.0.0.1:8080/api/{sessions,terminals,kernels}` — "CPU usage alone does NOT reset the timer." Critically, "scheduled executions still run on schedule even while the instance is in a shut-down state," meaning the platform treats shutdown as dormant/resumable, not destroyed.

[[manage-hosted-agent-sessions-microsoft-foundry-microsoft-learn]] shows Azure Foundry's hosted-agent sessions follow the identical pattern at a shorter default: idle timeout configurable 120–3600 seconds (2–60 min), default 900 seconds (15 min), after which "the platform deprovisions compute and saves state until the session is referenced again." The note also surfaces a genuine gap: stopping a session "uses the same shutdown sequence as any container teardown... with NO dedicated 'session stopped' code path," and the docs explicitly warn a session a caller stops itself "isn't guaranteed to restart on its own even when its work was left in progress for recovery."

[[ai-agent-development-costs-why-sandbox-billing-breaks-blaxel]] (vendor content, treat product claims skeptically but the cited benchmarks are useful) reframes the cost problem: online-serving workloads spend 61% of in-execution time idle while consuming 48% of energy in those intervals; real infrastructure audits show utilization below 20%; GCP Cloud Run enforces a 1-minute minimum billing period per instance regardless of actual use.

[[build-long-running-ai-agents-that-pause-resume-and-never-lose-context-with-adk-g]] is the one source that gets closest to agent-logic (not just VM-logic) dormancy: Google ADK's event-driven dormancy pattern lets an agent instance scale to zero while an explicit state machine (`START/WELCOME_SENT/.../COMPLETED`) persists in `DatabaseSessionService`, and an external webhook wakes it via `state_delta`. It also documents "golden evaluation" tests that simulate 48-hour idle gaps and assert the agent does not hallucinate skipped steps on resume.

## What the new sources say

No new sources were fetched. Source budget for this locus was explicitly scoped to 2 and flagged as "mostly a synthesis task" by the loci analyst; on inspection, all four pre-assigned corpus notes directly bear on the question and no genuine blocking gap exists that 1–2 fetches would resolve. The real gap — a published decision rule or benchmark number for agent-level "clean scan, self-archive" logic, and an exact $-at-100-agents idle-vs-always-on figure — is not a retrievable fact missing from my search; it is an absence in the literature itself (see below), which no amount of additional fetching within this budget would fill. Spending the 2-source budget on generic searches ("agent health check decision rule," "AI agent silent failure detection") would likely surface only generic SRE/observability content already implicit in the corpus (e.g., heartbeat/liveness patterns), not a purpose-built "agent self-archive" rule — so I am treating this as the audited absence itself rather than chasing it further.

## Evidence synthesis

The four corpus sources converge tightly on one point: every vendor mechanism described (Workbench idle-shutdown, Foundry session idle-timeout, Blaxel's 15-second-to-standby sandbox suspension, ADK's scale-to-zero dormancy) is a **liveness/activity-absence trigger**, not a **task-outcome trigger**. They all answer "has anyone/anything touched this process recently?" — none of them answer "did the scan I just ran actually complete and find nothing, or did it silently die?" That distinction is the crux of Pillar 6's "quietly self-terminate... if it finds no issues" ask, and it is structurally outside the scope of every source in this corpus. The Foundry note is the most useful because it names the failure mode directly: a stopped/idle session "isn't guaranteed to restart on its own even when its work was left in progress for recovery" — i.e., the platform's own infra-level suspend mechanism cannot distinguish a clean exit from an interrupted one, which is exactly the ambiguity an agent-level decision rule has to resolve on its own.

The ADK source is the strongest positive analog even though it isn't about health checks: its state-machine pattern (explicit named states, atomically written via tool calls, durably persisted before dormancy) is the correct *shape* of the fix. Applied to a health-check agent, the equivalent would be: the scan's completion state (and its outcome) must be written to durable storage as an explicit, atomically-committed value *before* the agent is allowed to go dormant/terminate — never inferred after the fact from "the process stopped running." The ADK golden-eval pattern (simulate a 48-hour idle gap, assert no hallucinated/skipped steps) is directly reusable as a test pattern for self-archival logic: simulate a scan that completes clean, one that errors mid-way, and one that is killed by an infra timeout mid-scan, and assert the agent only self-archives quietly in the first case.

On cost: the Blaxel figures establish the *mechanism* of waste (minimum billing windows, 61%/48% idle time/energy split, <20% utilization) but the corpus contains no vendor or analyst figure translating this into a concrete dollar number "at 100-agent fleet scale." This is a genuine, flagged absence — not a search failure. What the corpus does support is a cost-shape argument: if a fleet of 100 scheduled health-check agents each run on infra with a 1-minute Cloud-Run-style minimum billing floor, poll/check cadence dominates cost far more than compute-per-check does, because the minimum-billing floor is paid per invocation regardless of how trivial the check is. A fleet of health-check agents that self-terminate within the infra's resumable-dormancy window (Workbench 180 min default / Foundry 15 min default / Blaxel's 15-second standby trigger) pays only for active execution seconds plus storage, not idle compute — but the same fleet polling actively (never going dormant) pays the full minimum-billing floor on every cycle. The multiplier between these two regimes scales linearly with fleet size and inversely with check interval, but no source quantifies the actual ratio or a dollar figure; stating one would be fabrication.

## Committed position

The agent-level decision rule the corpus evidence points to is this: an agent must write an explicit, durably-persisted **outcome token** — not merely a liveness signal — before it is permitted to self-archive, and that token must distinguish three states, not two: `CLEAN` (scan ran to completion, no issues found), `ISSUE_FOUND` (scan ran to completion, surfaced something — escalate to human), and `INCOMPLETE/UNKNOWN` (the most recent outcome token's timestamp is older than the scan's own expected-runtime budget, or no token was written at all for this cycle). The default behavior for `INCOMPLETE/UNKNOWN` must be to escalate (ping a human) or retry-with-backoff, never to self-terminate — because every infra mechanism in this corpus (Workbench's kernel-activity-only timer, Foundry's teardown-path-equals-any-container-teardown, Blaxel's standby-on-network-inactivity) is explicit that dormancy/suspension by itself provides zero information about task outcome; the Foundry docs say this most directly by warning that a self-stopped session "isn't guaranteed to restart on its own." Operationally this means: (1) write the outcome token atomically as the last tool call of the scan, modeled on ADK's `state_delta` pattern, before any dormancy/termination call; (2) a supervisory layer (not the agent itself) checks "was a fresh CLEAN or ISSUE_FOUND token written within [scan interval + grace period]?" and only escalates on missing/stale tokens — this supervisory check must live outside the agent being evaluated, since an agent cannot be trusted to self-report its own silent failure; (3) treat "quietly self-terminate" as applying only to the `CLEAN` case, and require golden-eval-style tests (per the ADK pattern) that explicitly simulate a mid-scan kill and assert the supervisor — not the agent — escalates. On cost, the honest framing is directional with a named mechanism, not a dollar figure: idle-vs-always-on economics at fleet scale are dominated not by compute-seconds but by per-invocation minimum-billing floors (e.g., Cloud Run's 1-minute minimum) multiplied by check frequency and fleet size, so the single highest-leverage lever for a 100-agent fleet is lengthening the gap between scheduled wake cycles and/or batching multiple agents' checks into shared invocations, rather than optimizing per-check compute efficiency.

- **Position:** Self-archival must be gated on an explicit three-state outcome token (CLEAN / ISSUE_FOUND / INCOMPLETE-UNKNOWN) written durably by the agent and verified by an external supervisor — never on the mere absence of activity — and at fleet scale the dominant idle-cost lever is per-invocation minimum-billing floors × check frequency × fleet size, not per-check compute.
- **Confidence:** medium-high on the decision-rule architecture (strongly implied by convergent, consistent gaps across 3 independent vendor docs plus one positive design analog; no source contradicts it), low on any specific cost multiplier or dollar figure (none exists in corpus; my framing is a mechanism-level inference, not a measured number).
- **Boundary conditions:** The decision-rule argument holds for scheduled/periodic health-check-style agents where "clean" is a well-defined terminal state (DB health check, log scan, lint pass). It does not directly transfer to agents with open-ended or partial-completion semantics (e.g., a long-running refactor agent), where "clean" vs "incomplete" is not binary and the three-state token would need richer semantics. The cost argument holds specifically for infra billed with per-invocation minimums or coarse timeout granularity (Cloud Run, Azure Functions Flex Consumption); it weakens for infra with true per-second/per-GB-second billing and sub-second standby transitions (Blaxel's 15-second/25ms figures), where compute-seconds matter more than invocation count.
- **What would change this position:** A vendor or benchmark source documenting a built-in "task-outcome-aware" dormancy primitive (i.e., infra that itself verifies scan completion before suspending, rather than treating suspension as a pure liveness/activity question) would undercut the claim that this must be built as a separate agent-level/supervisor-level layer. On cost, a single credible source with a measured $-at-fleet-scale figure (e.g., a case study quantifying N agents × check interval × billing model) would let me replace the mechanism-level claim with a quantified one and should be sought in a follow-up fetch if this locus is revisited with a larger budget.
- **Evidence weight:** 3 vendor/platform docs (Google Workbench, Azure Foundry, Blaxel) converge on "infra dormancy = liveness-based, not outcome-based" — no contradicting source. 1 vendor tutorial (Google ADK) provides the only positive design analog (explicit state tokens + golden-eval testing) and is consistent with, not contradictory to, the other three. 0 sources address agent-level "clean vs. silently-failed" decision logic directly, and 0 sources provide a fleet-scale dollar figure — both are audited absences, not search failures, given the tiny source budget and the nature of the gap.
