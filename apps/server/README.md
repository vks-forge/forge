# @forge/server

The Forge server process: wires config and adapters into the Director engine, runs its tick, hosts the hook ingress and serves a small HTTP and SSE API on 127.0.0.1.

## Why it exists

Forge turns requests into merged changes: the Director engine triages an intake event, dispatches a Worker in a git worktree, and verifies and merges what comes back. Something has to be the running process that holds the tick clock, opens the database, starts the Worker harness, answers the Worker's hook calls with signed receipts, and lets a person or the CLI see and steer tickets. Without it the packages are libraries and nothing runs a ticket. It also holds the one secret that must never be on disk: each run's HMAC key for its receipt chain (d-0054). This app is composition only (code.md rule 1): it picks adapters from config, hands them to the engine and the routes, and holds no business rules.

Actors: the Director (the engine), Workers (Claude Code today, through the Claude driver), the user or CLI (HTTP), and the per-run `forge-mcp` process (`apps/mcp`), which shares the SQLite file.

## What it does

- Ticket sources: `POST /intake` reads the body's `source`, finds the registered `TriggerAdapter` for it (`services/trigger-registry.ts`; chat from `@forge/triggers` is always on, `ExternalPorts.triggers` adds others), lets that adapter validate the body into an `IntakeEvent`, then calls `engine.ingest`. A source nobody registered, or one that cannot be pushed to, is `400 unknown_trigger_source`; a body the adapter rejects is `400` with the zod issues; the answer stays `202` plus the engine's result. Polled adapters are called on an interval (`ExternalPorts.triggerPollMs`, default 60 s) by `services/trigger-poller.ts` with an in-memory cursor per adapter; the poller creates no timer when none is registered and stops first at shutdown.
- `src/main.ts` (entry, no logic) calls `runServer`. `src/config/` is the only code that reads `process.env` and the data-home bootstrap file (`data-home.ts`; `entrypoints.ts` is the one resolver for the MCP server and the hook script; `paths.ts` keeps config paths in the checkout apart from data paths in the data home). `src/services/assemble.ts` is the composition root. `src/routes/` holds the endpoints, `src/services/http/` the in-repo router, body reader, SSE and bind guard.
- Startup: validate env, resolve the data home (`FORGE_HOME`, else `forge-home.json`, else `%LOCALAPPDATA%\Forge`), take the single-instance lock `<dataHome>/server.lock` (another live server: exit 1 naming its pid; a dead owner's lock is taken over), read or create the install token, open SQLite at `<dataHome>/forge.db` and run migrations (the server owns them; migration 0013 seeds the tool catalogue as database version 1, there is no catalogue signing), load the project registry (every non-archived project in the database gets its runtime, below), start the Worker driver's preflight and observe the installed harness build (native tools are allowed only through approved schema rows for that build, B7), build memory, the report store, the driver registry, the G1 gate per project (claims also count receipts of the ticket's earlier runs, so a rework run can claim edits a previous run made), the hook handler and the engine, then bind, write `<dataHome>/server.json` (`{pid, port, startedAt, version}`) and start the tick.
- Run preparation (`prepareRun`): the engine issues the run token (hash in the database); the app registers the same raw token with a fresh HMAC secret for the run's generation (`req.generation`, default 1; the secret is stored in the SecretStore as `run/<runId>/secret-g<generation>` for the life of the run, d-0100), creates `<dataHome>/runs/<runId>/`, and returns the `forge` MCP entry (`node apps/mcp/dist/main.js` with `FORGE_RUN_ID`, `FORGE_RUN_TOKEN`, `FORGE_DB_PATH`) and the hook base URL. The Claude driver writes `hook.json`, `settings.json` and `mcp.json` there. A resume after a restart (d-0092) runs `prepareRun` again with generation 2 or more: a new secret, a `resumed` receipt linking the chain to the previous generation (signed with the new secret), and the new URL, port and token in the rewritten `hook.json`.
- Tick: every `engine.tick_interval_ms`, plus a coalesced immediate tick on intake, answered interactions, run events and the first `SessionStart` of a run.
- HTTP, loopback only (any other `FORGE_HOST` is refused with `BindRefusedError`), every route needs `Authorization: Bearer <install token>` or a browser session cookie (below) except `GET /health`, `POST /runs/:id/hook`, `GET /auth/open`, `POST /auth/proof` and `POST /auth/logout`, no CORS (JSON replies carry `Cross-Origin-Resource-Policy: same-origin`), 1 MiB JSON bodies (hook route 2 MiB: the hook client caps a tool output at 1 MiB), the `Host` header must be a loopback name on the server's own port (else `403 bad_host`), the API answers at the bare paths and also under `/api/*` (the prefix is stripped; the browser always uses `/api`), keep-alive 65 s (above what pooled clients reuse):
  - `POST /auth/sse-ticket`: `{run_id}` or `{project: <slug>}` -> `{ticket, expires_in_s: 60}`, a signed ticket for `GET /runs/:id/events?ticket=` of that run only, or for `GET /projects/:slug/events?ticket=` of that project only; neither kind opens the other (see Why this approach).
  - `POST /admin/shutdown`: `202 {status:'stopping'}`, then the same graceful shutdown as SIGTERM (what `forge stop` calls).
  - `POST /intake`: a core `IntakeEvent`; `202` with the engine's result. A `new_request` first becomes a card (d-0105): the result is `card_created` with `cardId` (a `grilling` card, no ticket, a Director reply queued; payload `card_type`, default `issue`), `ticket_created` with `ticketId` and `cardId` only for a type that starts tickets at intake (`pr_issue`, the PR fast path), or `ignored` for an unknown type or a source the type does not accept.
  - `GET /tickets/:id`: ticket (with `priority`), runs, gate results, pending interactions, `cost` (`{total_usd, by_run[{run_id, usd, status, started_at, recorded}]}`, oldest run first, `recorded: false` = the run reported no cost and counts 0), and `wait_reason` (`quota: claude-code until 14:20 UTC`, `cap: per-project 1/1`, `deps: PAY-231`, `retry: backing off until 14:20 UTC`, or null), computed by the engine's scheduler (`engine.explainWait`) so it matches what dispatch does; `404` unknown.
  - `GET /projects/:slug/tickets`: `{items, total, nextCursor}`, one project's tickets as board cards (`TicketSummary`: `id`, `title`, `state`, `lane`, `type`, `tier_predicted`, `project`, `card_id` (the parent card, when it has one), `priority`, `rework_count`, `needs_you` (true in `waiting_human`, `review`, `needs_signoff`), optional `blocked_reason`, `run_id`, `run_status`, `pr_url`, `created_at`, `updated_at`), newest `updated_at` first with `id` as tie-break. Query: `state` (repeatable or comma list of ticket statuses), `limit` (default 100, 1..500, `400` outside), `cursor` (opaque, from `nextCursor`, which is `null` on the last page; `400 invalid_cursor` for anything else). Also (the Tickets page): `lane`, `card` (a card id), `q` (case-insensitive substring of id or title, max 100), `sort` (`updated` default, `created`, `cost` = recorded run cost, highest first), `offset` (any sort); `total` is the number of tickets matching the filters; `nextCursor` is only given when paging by cursor (`sort=updated`, no `offset`), and a `cursor` with `offset` or another sort is `400 invalid_query`. Every row also carries `cost_usd` (recorded run cost, 0 when none) and `card_title`. `404 project_not_found` for an unregistered slug, `400` for a bad parameter, `401` without the token. Archived projects stay listable.
  - Cards (`routes/cards.ts`, `routes/card-patch.ts`, d-0105 .. d-0107): `GET /projects/:slug/cards?column&type&limit&cursor` is `{items, nextCursor}` of `CardSummary` (the card row with `project` as the slug, the rolled-up `column`, `ticket_count`, `tickets_done`), newest `updated_at` first; the column is computed per request by core's `rollupCardColumn`, so the `column` filter scans the project's cards and pages by an opaque cursor over (`updated_at`, `id`) (limit default 50, 1..200). `GET /cards/:id` is `CardDetail` (the summary plus `tickets` as `TicketSummary` with `card_id`, `pending_interactions`, and `cost`: `{director_usd, tickets_usd, total_usd, by_ticket[{ticket_id, title, usd}]}`; every `CardSummary`, list included, carries `cost_usd` = that total, the list from one grouped read per page); `GET /cards/:id/events?limit&cursor` is `{items, nextCursor}` of history oldest first by `seq`; `GET /card-types` is `{types}`, the registry in display order. Every card read also carries `phase`, `needs_you` (the overlay: the card's own flag, a waiting ticket or a pending question), `phase_version`, `priority`, `links`, `depends_on` and `blocks`, and `column` follows d-0139 (`shaping`, `needs_you`, `queued`, `in_progress`, `done`, `closed`). `PATCH /cards/:id` takes `{type?, closed_reason?}` (strict, at least one): a type change writes `type_changed`, a close writes `card_closed`, moves the card to `closed` and its phase to `closed` through `transitionCard`, both with the actor `user:owner`, and it answers `200` with `CardDetail`; the column itself cannot be patched. `404 card_not_found` / `project_not_found`, `400 invalid_card_id` (ids look like `FG-C12`), `invalid_cursor`, `unknown_card_type`, `409 card_closed` (a closed card takes no change), `409 card_type_source` (the type does not accept the card's source).
  - `POST /projects/:slug/cards` (`routes/card-create.ts`, d-0128, d-0138): the create-card form. Body (strict): `title` (4..120), `description` (>= 20), `type` (`plan|discussion|issue`, default `plan`), `priority` (`low|normal|high|urgent`, default `normal`), `depends_on[]` and `blocks[]` (card ids, up to 50), `links[]` (http(s) URLs, up to 20), `dedupe_key`. `201 {card}` (a `CardSummary`: the card row plus `column`, `needs_you`, `depends_on`, `blocks`, `ticket_count`, `tickets_done`) in phase `grilling`, no ticket, a Director reply queued; the same `dedupe_key` again is `200` with the first card. Errors (`{error: {code, message, issues?, cycle?}}`): `400 invalid_request` (with `issues`), `404 project_not_found`, `404 card_not_found` (an unknown dependency), `400 cross_project_dependency`, `409 dependency_cycle` with `error.cycle` (a closed path of card ids, e.g. `["DCP-C4","DCP-C3","DCP-C4"]`), `409 project_archived`, `503 server_draining`.
  - Planning fields on card reads (d-0130, d-0132): every `CardSummary` (list and detail) carries `open_points` (the grill's open-point count while the card is `grilling` or `verifying`, else null) and `plan_version` (the newest plan version, else null), read from the card's planning state in `services/card-view.ts`. The plan, grill and approval routes call the engine's planning doors (`answerGrill`, `grillShortcut`, `approvePlan`, `requestPlanChanges`, `editPlanTickets`, `startPlanning`, `runAsExpress`, `cardPlans`, `cardPlan`); `assemble.ts` wires the git `RepoReader` the planning steps read the code with.
  - `PUT /cards/:id/relations` (`routes/card-relations.ts`): `{depends_on: CardId[], blocks: CardId[]}` is the card's complete dependency set; `200 {card}`, the same errors as above plus `400 invalid_card_id`, `409 card_closed`.
  - Planning (`routes/card-plan.ts`, bodies in `schemas/plan-api.ts`, d-0130 .. d-0133): each route calls one engine door as author `owner` and maps its closed outcome through `services/plan-refusal.ts`. `GET /cards/:id/plan` is `{versions, current, floor}`; `GET /cards/:id/plan/:version` is `{plan}` (`404 plan_not_found`). `POST /cards/:id/grill/answer {question_id, option_id | text}` (exactly one) and `POST /cards/:id/grill/shortcut {kind: use_recommendations | write_plan_now}` answer `200 {card}`. `POST /cards/:id/plan/approve {version}` is `200 {card, ticket_ids}`; `POST /cards/:id/plan/request-changes {version, comment >= 5 chars}` is `200 {card}`; `PATCH /cards/:id/plan/:version/tickets {tickets: {key, title?, priority?, removed?}[], order?}` is `200 {plan}` (the new owner version); `POST /cards/:id/start-planning` is `200 {card}`; `POST /cards/:id/planning/retry` (re-queues a planning step that stopped on its budget, `409 phase_mismatch` when the card is not stopped so) is `200 {card}`; `POST /tickets/:id/run-as-express` is `200 {ticket_id}`. Errors: `409 question_not_open | stale_plan | phase_mismatch | not_plannable | not_held | ticket_has_dependents` (the last carries `key` and `dependents` in the error body), `400 invalid_request | invalid_card_id | invalid_ticket_id | invalid_version | invalid_answer | invalid_comment | unknown_ticket (key) | invalid_order | empty_plan`, `404 card_not_found | plan_not_found | ticket_not_found`. The routes write no storage themselves; the engine's writes go through the tracked storage, so the project stream announces them.
  - `GET /projects/:slug/events` (`routes/project-events.ts`, d-0132): SSE, invalidate-only. The install token or `?ticket=` from `POST /auth/sse-ticket {project}`. Each message is `event: invalidate` with `data: {"keys":[["cards","<slug>"],["card","DCP-C1"],["tickets","<slug>"],["inbox","<slug>"]]}` (TanStack query keys; only the stale ones are listed), a `: heartbeat` comment every 25 s (`http.projectHeartbeatMs` shortens it in tests), `retry: 2000`, no replay (a reconnecting client refetches everything). `404 project_not_found` before the stream starts. Emitted after any committed write to cards, card events, card phase, relations, the reply queue, tickets, questions or inbox marks of that project.
  - `POST /interactions/:id/answer`: `{answer}`; compare-and-swap; `409` when not pending, `404` unknown.
  - `GET /cards/:id/events` windows (for the chat UI poll): `?after=<seq>` is events with a greater `seq`, oldest first; `?order=desc&limit=N` is the newest N, newest first; `?before=<seq>` (implies `desc`) is the newest N below it ("load older"); `after` and `before` may be combined and `order=asc` forces oldest first. Every item carries its `seq`. The opaque `cursor` still continues a page in its own order (pass the same `order`) and cannot be combined with `after` or `before` (400).
  - `POST /cards/:id/messages` (`routes/card-messages.ts`, d-0109): `{text (1..8000 chars), author (1..200)}`, strict; the user talks to the card's Director. `202 {event}` with the stored `user_message`; the reply (and anything the Director did) arrives later as `director_message`, `director_action`, `note` and `close_suggested` events on `GET /cards/:id/events`. `GET /cards/:id` and the PATCH answer carry `director: {state: idle|thinking|error, last_error?}` for a typing state. Errors: 400 bad body or id, 404 `card_not_found`, 409 `card_closed`, 503 `server_draining` (the 503 is written directly, not thrown).
  - `POST /runs/:id/steer`: `{message (1..8000 chars), author}`; a person messages a running Worker directly (d-0109; the run is the primary address, its thread is `GET /runs/:id/events`). `200 {run_id, inbox_seq, mode: 'steer', status: 'delivered'}` once the engine stored it (inbox row and `user_message` event, so open streams show it at once) and the driver took it. `400` bad body, `404 run_not_found`, `409 run_not_live` (ended, interrupted or another server's), `409 steer_unsupported` (the harness does not declare live `steer`), `503 server_draining` (shutdown began; answered before anything is stored). `author` is stored on the inbox row and event as the audit trail. Same guard as every write (token or browser session; cookie writes need `Origin`).
  - `GET /stats/overview?range=today|7d|30d|90d|12m|all&group=hour|day|week|month&projects=a,b&archived=0|1` (defaults 30d, grouping follows the range, all open projects; `400` on a bad range, group or flag, on `group=hour` without `range=today` and on `range=today` with any other group; `today` is the server's local calendar day from midnight to now in hourly buckets, using the server's UTC offset at request time, with the change figure against yesterday up to the same time of day; the per-project `stats` and `cost` endpoints do not accept `today`): `OverviewStats` across projects from core's `computeOverviewStats`, read per project by `services/overview-source`. `projects` names slugs (an archived one is included whatever `archived` says); unregistered slugs are ignored and listed in `unknown`. Spend is only recorded `cost_usd` with `cost_coverage`; nothing is stored or priced.
  - `GET /projects/:slug/stats?range=7d|30d|90d` (default 30d; `400` otherwise): `ProjectStats` for Home, computed on request from tickets, runs and gate results: `tickets_by_state` (every status), `throughput` (done per UTC day, a dense `{date, value}` series), `lead_time` (created to done, `median_ms` / `p90_ms`, null when none), `rework_rate`, `gate_pass_rate` (G1, skipped verdicts excluded; `rate` null on no data), `runs_per_day`, `active_workers`, `spend_per_day` and `cost_coverage` (`runs_with_cost` of `runs_total`). `GET /projects/:slug/cost?range=&ticket_limit&ticket_offset&run_limit&run_offset`: `CostReport` with `total_usd`, `per_day`, `by_ticket` and `by_run` (pages of the ranked tables, default the top 50, limit 1..100 each, `400` outside; `by_ticket_total` and `by_run_total` count every row of the window), `by_harness`, `by_model` (tokens only), `tokens` and `budgets` (`run_max_usd`, `step_budget_usd` from settings, `period_usd` always null). Only recorded `cost_usd` is summed; nothing is priced or invented.
  - Inbox (`routes/inbox.ts`, d-0116): `GET /projects/:slug/inbox?view=needs_action|unread|all|archived&limit&cursor` is `InboxPage` (`InboxItem`: `id` `<kind>:<source id>`, `kind`, `title`, `detail`, `ticket_id`, `run_id`, `needs_action`, `updated_at`, `read`, `archived`), derived on every request from open interactions, tickets in `review` / `needs_signoff` / `waiting_human`, failed gates, interrupted runs, parked harnesses, failed harness builds, pending tool approvals and pending memory proposals. Harness build and tool items cover only each harness kind's current build (the installed one, else the newest checked); older builds' rows stay in storage but are not listed, and a tool approval is dated by its build's `checked_at`. `GET .../inbox/counts` is `InboxCounts` for the sidebar badge. `POST .../inbox/:itemId/read|unread|archive|unarchive` (url-encode the id) stores the mark and answers the updated item; an item whose source changed after a mark is unread and unarchived again. `404 inbox_item_not_found` for an item not in the inbox now, `404 project_not_found`, `400` for a bad view, limit or cursor.
  - Runs (`routes/runs.ts`): `GET /projects/:slug/runs` and `GET /runs` (all projects) are `RunListPage` of `RunSummary` (ticket id and title, project, harness, status incl. `interrupted`, `started_at`, `ended_at`, `duration_ms`, `generation`, `paused_harness` while its harness is parked for quota, `cost_usd` and `tokens` when recorded), newest first; query `status` (repeatable or comma list), `limit` (default 50, 1..200), `cursor`. `GET /runs/:id` is `RunDetail` (summary plus `cwd`, `session_ref`, `tokens_by_model`, `gates`); `404 run_not_found`.
  - `GET /runs/:id/events`: SSE; the install token or `?ticket=`. `id:` is the event `seq`, `event:` its type. Replays after `Last-Event-ID` (or `?after=`), then follows by polling storage (so events written by the MCP process show up), heartbeat comment every 15 s, an `end` event and close once the run has ended and everything was sent; a reconnect after that (cursor at the last event of an ended run) gets `204`, which makes `EventSource` stop.
  - `POST /runs/:id/hook`: the harness hook. `Authorization: Bearer <run token>`; always `200` with the handler's verdict (deny included); the handler fails closed.
  - `GET /harnesses` (each row also carries `paused_until` and `pause_reason` while the harness is parked for quota; the top-level `paused` lists every active pause, registered or not), `PUT /harnesses/:id` `{kind:'claude', binary_path?, auth_mode:'login'|'api_key'|'oauth_token'}`, `PUT /harnesses/:id/secret` `{kind:'api_key'|'oauth_token', value}`, `POST /harnesses/:id/test[?live=1]`: the installed harness, how it signs in, and its Test environment (see Why this approach). JSON only, the same loopback and `Host` guard.
  - `GET /harnesses/:id/compat` (installed build, `compat` `pass|fail|pending|unknown`, the latest `report`, the background `job` state), `POST /harnesses/:id/compat/run` (202 with the job state; one check at a time), `GET /harnesses/:id/tools` (`{version, tools:[{tool, schema_hash, status, decided_by, decided_at, decision_reason}]}` of the installed build), `POST /harnesses/:id/tools/:tool/approve` and `/deny` `{author, reason}` (404 for a tool the build did not offer). A saved harness stays `paused` through an edit; only a passing check lifts it.
  - `GET /settings/catalogue`, `GET /settings/catalogue/history`, `PUT /settings/catalogue` `{doc:{entries:[...]}, author, reason, expectedVersion}`: the versioned tool catalogue (409 on a stale version, 400 for a document that would leave no usable tool).
  - `GET /projects`: `{projects}`, every registered project (archived ones too) with `id`, `slug`, `prefix`, `local_path`, `connection_id`, `repo_full_name`, `status`, `ecosystems`, `repo_origin`, `memory_repo` (the deprecated tier-C column is not shown), plus `config_error` (the reason) on a project the engine skips because its stored settings no longer validate.
  - `POST /projects`: registers an existing local clone. Body (strict): `slug`, `prefix` (1-10 uppercase), `local_path` (absolute), optional `base_branch`, either `git_host` (the settings shape: `local` with `remote_path`, or `github`) or `connection_id` + `repo_full_name` (`owner/name`) + `installation_id` (never both, never neither), optional `settings` (`checks`, `ecosystems`, `gate_rules`, `default_harness`, `remote`; the old `profile` + `commands` pair is still accepted and stored converted to `checks`), `author`, optional `reason`. It checks, in this order and with nothing saved on any failure: body shape (400 `invalid_request`), absolute path (400 `invalid_local_path`), a folder inside Forge's own data home or worktree folder, by plain path or after resolving links (400 `path_in_data_home`), unique slug / ticket prefix / folder (409 `project_exists`, `prefix_in_use`, `path_in_use`; this is a fast refusal, and the same check is made again inside the one transaction that saves the row, so two creates racing for the same slug, prefix or folder give one `201` and one `409`), the connection exists and is active (404 `connection_not_found`, 409 `connection_disabled`), the folder is the root of a git repository with the base branch (400 `not_a_directory`, `not_a_repository`, `not_repository_root`, `base_branch_missing`), the settings are valid (400 `invalid_settings`) and a runtime can be built from them (400 `project_not_servable`). Then it saves the row (id = slug, status `ready`; before the project's memory repository and settings version are created), the first project settings version (the body's `author` and `reason`) and starts serving it: `201 {project, settings_version}`; no restart. Settings versions cannot be deleted, so a failure after the row was saved deletes the row again and a retry of the same request appends on top of the versions the slug already has (`settings_version` can then be above 1) instead of failing with a conflict.
  - `POST /projects/inspect` (dry run, `routes/project-inspect.ts`): body (strict) `{local_path, base_branch?}`. Runs the same folder checks as `POST /projects`, in the same order and with the same codes (`assertProjectFolder` is shared): 400 `invalid_local_path`, `path_in_data_home`, `not_a_directory`, `not_a_repository`, `not_repository_root`, `base_branch_missing` (also for a repository with no commits when no base branch was named), 409 `path_in_use` for a folder another project already holds. Then `200 ProjectInspection` (core schema): `local_path`, `current_branch` (null when detached), `base_branch` (the one asked for, else the checked-out one), `branches` (local, alphabetical, at most 50) and `branches_truncated`, `ecosystems` and suggested `checks` found at the repository root by `@forge/gates` `detectProjectAt` (file names and the root `package.json` scripts only; nothing is run), and `suggested_slug` / `suggested_prefix` that no registered project uses. It creates, writes and fetches nothing.
  - `GET /system` (`routes/system.ts`): `SystemInfo` (core schema) `{service:'forge', version, data_home, first_run:{complete, project_count, harness_ok}}`. `first_run.complete` is derived, not stored: true once any project row exists (archived ones count), because registering a project is what first-run setup produces, so there is no flag to fall out of step and a fresh data home shows the wizard again by itself; `harness_ok` is true when a harness row has status `ok`. No token, key or credential; needs the install token like every route but `/health`.
  - `POST /fs/pick-folder` (`routes/folder-pick.ts`, `services/folder-picker/`): opens the OS folder window on the machine Forge runs on and answers `FolderPick` (core schema): `{status:'picked', path}`, `{status:'cancelled'}` or `{status:'unavailable', reason}` (a normal 200, so the page falls back to its own browser). Body `{start?}` (strict) is the folder to open in, used only if absolute and existing. POST so it passes the token and Origin checks like every action. One module per OS chosen by a `Record<NodeJS.Platform, ...>` table, all started with `execFile` (no shell): Windows runs `powershell.exe -STA` with an encoded script that compiles an `IFileOpenDialog` (pick-folders) via `Add-Type`, owned by a hidden top-most form so it comes to the front, falling back to `FolderBrowserDialog` (the start folder travels in `FORGE_PICK_START`, not in the script); macOS runs `osascript` `choose folder` (exit 1 with "User canceled" is cancelled); Linux and other Unix try `zenity` then `kdialog` (exit 1 cancelled; neither installed, or no `DISPLAY`/`WAYLAND_DISPLAY`, is unavailable). Result text is cleaned (no newline or trailing slash, roots kept). Ten-minute limit then the window is killed (answered as cancelled); a second request while a window is open is 409 `picker_busy`. The picker is injected as `RouteDeps.folderPicker` (absent reads as unavailable), so tests use a fake and no test opens a window.
  - `GET /fs/folders?path=<absolute>` (`routes/folders.ts`, `services/folder-listing.ts`): the folder browser behind "Choose a folder" in the add-project dialog (a browser page cannot learn a folder's absolute path from a file picker). `FolderListing` (core schema) `{path, parent, entries:[{name, path, is_repo, modified_at}], truncated}`; `modified_at` is the folder's ISO modified time (null on the roots view) so the page can sort by date. No `path` is the roots view (`path` empty, `parent` null): the home folder first, then each drive that exists (Windows, probed A to Z) or `/`. With a `path`: sub-folders only (never files), case-insensitive alphabetical, hidden names (leading `.`), `$Recycle.Bin` and `System Volume Information` left out, unreadable entries skipped, at most 500 (`truncated` says more exist); `is_repo` is a `.git` stat, no git is run; `parent` is the folder above, null at a drive or `/` root. Errors: 400 `invalid_path` (not absolute), 400 `not_a_directory` (a file), 404 `folder_not_found`, 403 `folder_not_readable`. Read-only, names only, needs the install token like every route but `/health`.
  - `POST /fs/folders` (`routes/folders.ts`, `services/folder-create.ts`): body (strict) `{parent, name}` makes one folder and answers `201` with its `FolderEntry`. The name is checked: not empty or over 120 characters, no `\ / : * ? " < > |` or control characters, not `.` or `..`, no Windows reserved name (`CON`, `NUL`, `COM1`…), no leading space and no trailing space or dot (400 `invalid_folder_name`); `parent` must be absolute (400 `invalid_path`), exist (404 `folder_not_found`) and be a folder (400 `not_a_directory`); an existing name is 409 `folder_exists`, a read-only parent 403 `folder_not_writable`. One level only, never over something that exists; rename and delete do not exist.
  - `POST /fs/reveal` (`routes/folders.ts`, `services/folder-reveal.ts`): body (strict) `{path}` shows an existing absolute folder in the OS file manager and answers `FolderReveal` (core schema) `{status:'opened'}` or `{status:'unavailable', reason}` (a normal 200). One program per platform from a `Record<NodeJS.Platform, string>` table (`explorer.exe`, `open`, `xdg-open`), started with `execFile` (the path is one argument, no shell); Explorer exits 1 after opening, so only a missing program is a failure there. The revealer is injected as `RouteDeps.folderRevealer` (absent reads as unavailable), so no test opens a window. POST so it passes the token and Origin checks: a page on another site must not be able to open windows.
  - `DELETE /projects/:slug` (`routes/project-delete.ts`, d-0127): body `{confirm}` must equal the slug. In one transaction it checks that no run of the project is `starting`, `running` or `settling`, then `projects.purge(slug)` removes the project row and its tickets, relations, intake events, wakes, runs and their events, inbox, tokens, gates, interactions and receipts, cards and card events and inbox marks (settings versions stay: they are append-only, and a re-added slug continues them). Then the registry stops serving it and `<data home>/memory/<slug>` and `<data home>/worktrees/<slug>` are removed with retries (`services/project-files.ts`). The project's own `local_path` folder is never touched. `200 {deleted, leftovers?}` (`leftovers` lists a Forge folder that stayed locked), `400 confirm_mismatch` (or `invalid_request` for a missing body), `404 project_not_found`, `409 project_busy`. Git worktree entries Forge registered in the project's repository are not pruned (`git worktree prune` there clears them).
  - `PATCH /projects/:slug` (`services/project-status.ts`): `{status: 'archived' | 'ready'}` is the only change. `archived` keeps the row, the registry stops serving the project and intake for it is ignored. `ready` unarchives it (d-0157): the project's folder must still exist and its runtime must build (the registry serves it again at once), otherwise `409 project_not_servable` with the reason and the project stays archived; unarchiving a project that is not archived is a no-op. `200 {project}`, `404` unknown, `400` for any other body. `GET /projects` lists archived projects too, with `status`.
  - Project memory (`routes/memory.ts`; the owner answers what the Director proposed, nothing here creates a record): `GET /projects/:slug/memory` is `{records}` (pending proposals, then decisions, then rejected; each `id`, `kind`, `status`, `statement`, `tags`); `GET /projects/:slug/memory/:id` is `{record}` with every front matter field and `body`; `POST /projects/:slug/memory/proposals/:id/approve` `{author}` and `POST .../reject` `{author, reason}` (bodies strict, both fields non-empty) answer `200 {record, commit}` where `commit` is the sha in the project's memory repository. `404` for an unknown project (`project_not_found`) or record (`memory_record_not_found`), `409 not_a_pending_proposal` when it was already answered, `400` for a bad body. `POST /projects` also creates the project's memory repository (`500` and nothing saved if that fails); at startup every served project without one gets it, and a failure is logged, not fatal.
  - `GET /github/connections`: `{connections}` (id, account, `app_id`, `app_slug`, `key_secret_name`, status, `created_at`); never any key.
  - `POST /github/connections`: `{account, app_id, app_slug?, private_key_pem}`. The PEM goes to the secret store as `github/<id>/key` (id = slug of the account, `-2`, `-3` when taken) and is never echoed, logged or stored in the database; a body that is not a PEM key is refused with 400; if the row cannot be saved the key is removed again. `201 {connection}`.
  - `POST /auth/open-code` (install token only, a session is refused): `{code, expires_in_s: 60}`, a single-use sign-in code. `GET /auth/open?code=` (open; the code is the credential): spends the code and answers `302 /` with `Set-Cookie: forge_session=...; HttpOnly; SameSite=Strict; Path=/; Max-Age=604800`; a wrong, used or expired code gets a plain `401` HTML page (`run forge open`) and no cookie. `POST /auth/logout` is open (a person with an expired cookie must still be able to clear it): it always answers `204` with the clearing `Set-Cookie` and drops the session when the cookie names a live one; a cookie request still needs the matching `Origin`. `POST /auth/proof` (open, Host-checked) takes `{nonce}` (16 to 200 characters) and answers `{proof}`, the hex `HMAC-SHA256(install token, nonce)`; the token is never returned, and the CLI uses it to check a port really is this server before it sends the token. `POST /auth/sse-ticket` works with the cookie too.
  - The built web UI (`apps/web/dist/web`, found next to this app, never from the working directory; absent until `pnpm --filter @forge/web build`, then the server logs a warning and serves the API alone) is served at `/` and its files (root files such as `/favicon.ico`, `/site.webmanifest` and the crest PNGs are static files answered before the auth guard, with their own content types, so the icon loads on the sign-in page); a browser navigation (`GET`, `Accept: text/html`, no `Authorization`) to any path outside `/api` gets `index.html`, even where an API route has the same name. `/assets/*` are `immutable` for a year, `index.html` is `no-store`; every page has a CSP (`default-src 'none'`; scripts: self plus the hash of the one inline theme script; connect, fonts, images: self; `frame-ancestors 'none'`), `X-Content-Type-Options`, `Referrer-Policy: no-referrer`, `X-Frame-Options`, COOP/CORP.
  - `GET /health`: open, no token, no data: `{service:'forge', status:'ok'|'degraded'}`; `503` if the database does not answer (the database check is cached for one second). Owner, uptime and counters are deliberately not here (any local program can call it); `server.json` has pid, port, start time and version.
- Errors: `HttpError` and `ForgeError` families map to 400/401/403/404/409/413/415/429. Only an `HttpError` (written for the client) echoes its message; any other 4xx `ForgeError` answers with its family's fixed text, and anything else is a bare `500`, because such messages carry paths, refs and secret names.
- Shutdown on SIGINT/SIGTERM or `POST /admin/shutdown` (the same path): ask the tick to stop, drain (`services/drain.ts`: the hook handler refuses every new tool call with the deny reason `server_draining`, receipted like any denial, and shutdown waits until no live run has a tool call that was allowed but has no effect receipt yet, for at most `engine.shutdown_drain_ms` of the company settings (default 10 s, 0 = do not wait) and never more than half of the grace window; a run still mid-call at the timeout is interrupted anyway and its cut-off write still fails G1 closed; a crash has no drain), interrupt live runs (`engine.interruptRun`: each is marked `interrupted` with its harness session and its harness is stopped; a tick may be waiting on a run, so it is not awaited first), give the tick and the gate jobs what is left of one `FORGE_SHUTDOWN_GRACE_MS` window, interrupt runs a late tick started, end streams, close the port, remove the Director's temp directory, close the database, then remove `server.json` and `server.lock`. A second signal exits `130` immediately. Interrupted runs are resumed by the next start's first tick (d-0092, `packages/engine` `tick/restart.ts`); their run secrets stay in the SecretStore.
- Run secret lifecycle (d-0100; `services/secret-retirement.ts`): secrets are stored when a run is prepared and deleted when the run is over: at start (this also removes what a crash left, and secrets of runs the database does not know) and after every tick, any run that has stopped for good loses all its generations. A run that succeeded keeps its secrets until its ticket is `done` or `cancelled` (G1 judges it after it settles, and a later rework run of the ticket re-verifies its chain to count its edits as evidence), and a run that is alive or `interrupted` is never touched.
- Liveness (d-0033): the first `SessionStart` of a run stores `hook_registered_at` and a `hook_liveness` event (resume, compact and clear do not move it); a `PreToolUse` from a run whose hook never registered is denied `fail_closed_no_liveness` and leaves no receipt.
- Harness isolation: Worker and Director children get an allowlisted environment, not the server's (`FORGE_GH_*`, API keys and cloud credentials stay out). `FORGE_HARNESS_ENV_PASSTHROUGH` names extra variables (default none; credential variables are never passed through: `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` reach a child only from the harness's auth mode and its stored secret, d-0087). A missing or shim `claude` no longer stops startup (the owner may be about to set its path in Settings): preflight logs the issue and a run fails at its start with the install pointer.

Public API: none; it is an app.

Any folder can be a project (d-0124). `POST /projects/inspect` reports the folder's git state (`repo`, `none`, `inside_repo`), a snapshot count when there is no git, branches, ecosystems and checks (from the subfolder when inside a repository). `POST /projects` takes `git_setup` (`snapshot` or `init_only`, required when the folder has no git) and `scope` (`root` or `subfolder`, required when the folder is inside a repository); missing choices are a 400 (`git_setup_required`, `scope_required`), a too-large snapshot is `snapshot_too_large`, and the user's folder is only touched after every other check passed. With no `git_host` or GitHub connection the project registers a `local_repo` host and merges locally; a subfolder project stores `repo_root` + `subfolder` and is served from the repository top with the Worker in the subfolder. Services: `project-inspect`, `project-placement`, `project-host`, `worker-wiring`.

- **Escalations (S4a).** `POST /interactions/:id/act` settles a wait with an action it offers (answer, retry, replan, cancel, run_as_express, recheck) and returns `{escalation}`; `POST /tickets/:id/act` does Rework and Cancel for waits with no interaction (review, sign-off, scheduler holds) and returns `{ticket_id, action}`; `GET /cards/:id/escalations` lists a card's pending waits then the last 50 settled; `GET /tickets/:id` adds `escalations` and `wait_actions`; the Inbox `question` items cover all three kinds and carry the `escalation` view, owner stage only. Refusals: 400 `invalid_body` / `invalid_answer`, 404 `interaction_not_found` / `ticket_not_found` / `card_not_found`, 409 `not_pending` (with `settled`), `action_not_offered`, `ticket_has_dependents` (with `dependents`), `still_broken` (with `detail`), `stale`. `POST /interactions/:id/answer` stays and settles the same typed owner answer at any stage. Every ticket and interaction write also invalidates `["ticket", id]`.

Off by default. `FORGE_TRACE=1` (or `true`) writes everything that happens to a card as JSON lines, with secrets removed; no UI, files only (d-0163).

| ----------------------- | ----------------------- | ------------------------------------------------------------------------------ |
| `FORGE_TRACE`           | unset (off)             | `1` / `true` turns tracing on; off installs no decorator and creates no folder |

| `FORGE_TRACE_KEEP_DAYS` | `14`                    | files whose modification time is older are deleted at start-up and once a day  |

- **Files:** `forge-YYYY-MM-DD.jsonl` (everything, in order, one per server-local day) and `cards/<CARD-ID>.jsonl` (one card's story: creation, chat, Director steps, tickets, runs, escalations). If redaction throws the entry is dropped with one stderr warning.

## Why this approach

- `node:http` with a small router and hand-written SSE, no framework (d-0061). Rejected: Hono, Fastify.
- Hook auth is the run's bearer token compared in constant time in `@forge/hooks`; the route only extracts it. The token lives only in the registry's memory (the database holds its SHA-256); the HMAC secrets are in the SecretStore (DPAPI-encrypted on Windows) and never in the database (d-0100). A restart makes every old token unknown, so a dead Worker's hook calls are refused; a resume registers a new token and a new secret generation, and the hook handler refuses credentials of any other generation.
- Install token (d-0093; `services/auth/`): on first start the server creates `<dataHome>/install-token` (32 random bytes, base64url, 43 characters), mode 0600 where the OS has modes, and on Windows the ACL is cut to the current user with `icacls` (granted by the user's SID from `whoami /user`, so domain and Entra accounts work; inheritance removed, SYSTEM and Administrators removed; applied on every start, not only on creation; if that fails the server starts and logs a warning, never the token). A file that does not hold a well-formed token is replaced. The router asks the guard before every handler; a route is protected unless it declares `access: 'open'` (`/health`, and the hook route, which keeps its own per-run Bearer secret). The comparison hashes both sides and uses `timingSafeEqual`; a wrong or missing token is `401 {"error":{"code":"unauthorized","message":"unauthorized"}}` with `WWW-Authenticate: Bearer`, also for unknown paths. Host guard, loopback-only bind, JSON-only bodies and no CORS stay. The CLI reads the same file.
- Browser sessions (`services/auth/sessions.ts`, `cookies.ts`): the page never holds the token. `forge start` / `forge open` get a code from `POST /auth/open-code`, open `/auth/open?code=` and the browser trades it once for a cookie. A code lives 60 s, is spent by the first attempt that names it, at most 8 are outstanding, and a presented code is compared in constant time against every stored one. The session id is 256 random bits, only its SHA-256 is kept in memory; idle expiry is 12 h and slides on use, the hard limit is 7 days, at most 64 sessions (oldest dropped). Nothing is persisted, so a restart signs every browser out (the page shows its session-expired state, `forge open` fixes it). `Secure` is not set because the server speaks http on loopback. The cookie is sent by the browser on its own, so every request that carries it and is not GET or HEAD (the check is by exemption: OPTIONS or a method added later is checked too; it runs before routing, so open routes such as logout are covered) must carry an `Origin` equal to `http://<its Host>`, else `403 bad_origin`. That check, with no CORS headers, is what stops a page on another local port (it sends our Host, so the Host check cannot; `SameSite` cannot either because it ignores ports); the Host check stops DNS rebinding. A request with a valid bearer token needs no `Origin` (the dev proxy forwards the page's). Rejected: putting the token in `define`/`localStorage` (readable by page scripts) and a long-lived code in the URL.
- SSE tickets: `EventSource` cannot send headers and the token must not sit in a URL. `POST /auth/sse-ticket` (token) returns `<expiry-ms>.<hmac-sha256>` signed with a per-process random key over `sse:<runId>:<expiry>`; `GET /runs/:id/events?ticket=...` accepts it for that run id only, for 60 seconds, and on no other route. It is reusable until expiry because `EventSource` reconnects with the same URL; after expiry the page asks for a new one. A restart invalidates all tickets. A project ticket (`{project}`) is signed over `sse-project:<slug>:<expiry>` instead, so a run ticket never opens a project stream and a project ticket never opens a run or another project.
- Live project updates (d-0132): `assemble.ts` wraps the storage in `trackProjectWrites` (`services/tracked-storage.ts`): each committed write to cards, card events, relations, the reply queue, tickets, questions or inbox marks is resolved inside its transaction to the project slug and the query keys, and announced to the `ProjectEvents` hub (`services/project-events.ts`) after the commit; a rolled-back transaction announces nothing. The engine gets the same hub as the `ProjectEventSink` port for what is engine memory (the Director "thinking" flag). Streams subscribe to the hub per slug.
- Single instance and daemon files (d-0092): `services/instance/` holds the exclusive lock (`fs.open(..., 'wx')`, pid inside, stale when the pid is dead, an empty lock under 5 s old counts as held) and `server.json` (written atomically after the port is bound, removed only by the pid it names). `forge start | status | stop` (apps/cli) use them.
- SSE reads storage, not an in-process emitter, because `apps/mcp` is a separate process that also appends events.
- The Worker driver and the Director model arrive as ports (`ExternalPorts`): production passes the Claude adapters (`createClaudePorts`), the end-to-end test passes a fake harness that still goes through the real hook route, receipts, MCP tools and G1.
- Tool schema hashes: Forge MCP tools are hashed from the real MCP server. A harness-native tool is allowed only through an `approved` row of `harness_tool_schemas` for the installed build (`services/tool-policy.ts`, `services/harness-compat.ts`, d-0088). At start-up the build is read (`claude --version`); a build in the shipped known-good list is recorded as compatible with its tools approved by `forge-release` (ACP engine only), any other build is checked in the background by `@forge/drivers` `checkInstalled` (about a minute, no cost). A failed check sets the harness `paused` with a plain `status_note` and runs refuse to start on it (`auth` error); a passed check leaves every new or changed tool shape `pending`, and `admit()` denies a pending tool as `schema_pending` (a denied one as `schema_denied`) until `POST .../approve`. An unknown build or an unknown tool is denied. Approvals and catalogue edits apply to the next tool call; each run records `catalogue_hash`, the hash of the catalogue with the approved native hashes applied. The installed build is re-read at start-up and on `POST /harnesses/:id/test`, not on every run.
- Build guard (`services/build-check.ts`, `HarnessCompat.assertCurrent`): the installed `claude` build is read at boot and when Settings change, but the owner can upgrade it in place while Forge runs. Before every run starts, the run preparation reads the build again (a cached `--version`, one spawn per file state); a build that differs from the one whose tool approvals were loaded starts the first-sight check of the new build in the background and refuses that start with `HarnessChangedError`: the engine parks the ticket with a reason starting `harness_changed:` until the owner has approved the new build's tools and released it. The build that ran is written on the run row (`driver_version`).
- GitHub connections (`POST /github/connections`): the id is picked and the row inserted in one transaction (`insertIfAbsent`), and the private key is written to the SecretStore only after the insert, so two simultaneous adds for one account cannot share an id or overwrite each other's key; a failed key write deletes the row again.
- Grants: a run's project grant is `tool_grants` from the project's effective settings (`PUT /settings/projects/:slug` with `{doc:{tool_grants:{deny:["grep"]}}}`); ticket grants have no source yet.
- Tier C globs come from the project's settings (`tier_c_globs`, default `.forge/**`, `.claude/**`, `.github/**`), matched ignoring case; the engine reads them each tick, so an edit applies at once.
- Settings (d-0085, d-0090): the server no longer reads `forge.yaml`; engine limits and models are built-in defaults plus the company override in the database, project settings are the project override. The engine takes one snapshot per tick, so an edit saved through the API applies to the next tick with no restart (the tick timer period, `tick_interval_ms`, is read once at start and is the one dial that needs a restart). Each run row records `config_version` (`c<company>:p<project>`).
- Settings API (JSON only, loopback and Host guard as for every route): `GET /settings/company` returns `{config, version}` (version 0 = built-ins); `PUT /settings/company` takes `{doc, author, reason, expectedVersion}` and returns the saved version row, 409 `version_conflict` when someone saved first, 400 listing the keys when `doc` is not a valid override (unknown keys are refused); `GET /settings/company/history` returns `{versions}`; `GET`/`PUT /settings/projects/:slug` (`GET` returns `{config: {forge, project}, version: {company, project}}`) and `GET /settings/projects/:slug/history` work the same, 404 for an unregistered project. A saved `doc` is the whole override of the scope, not a patch on the previous version: send everything that should differ from the defaults.
- Harnesses (d-0087, d-0101): Workers and the Director run the user's installed `claude`. The `harnesses` table (migration 0012) holds, per harness id, the optional executable path, the auth mode and the last test result; `services/harness-source.ts` reads the row `claude` at the start of every run (absent row: PATH lookup, own login), so a save applies to the next run. `PUT /harnesses/:id` resets the stored test result; `PUT /harnesses/:id/secret` writes the pasted key or token to the SecretStore as `harness/<id>/api-key` or `harness/<id>/oauth-token` and answers `{id, kind, stored: true}`: the value is never returned by any route, and `GET /harnesses` only says per kind whether one is stored. `POST /harnesses/:id/test` answers `{binary_path, version, auth_mode, ok, account_kind?, live, error?, live_note?}` (resolve, `--version`, `claude auth status --json` with the credential injected); the one paid hello call runs only with `?live=1`, otherwise `live: 'skipped'` and a note says so. It records version, status and time on the row. The `claude setup-token` PTY flow is deferred to the UI phase; tokens are pasted for now.
- Many projects (d-0082, d-0094; `services/project-registry.ts`): the registry holds one runtime per served project: the project's identity, its `GitHost` (`services/git-host.ts`: `local` bare repo with a relative `remote_path` resolved against the clone, or a GitHub App whose App id and key name come from the project's connection, else from the settings), the G1 gate over the project's own worktrees, a `WorktreeManager` on `local_path` with its worktrees under `<dataHome>/worktrees/<slug>/<ticket>`, and the base branch. `load()` runs at start (a project with no clone path is skipped with a warning; one that cannot be built is skipped with an error and does not stop the others). The engine calls `registry.runtime(slug, settings)` with the settings it read for the tick; when the project's settings version moved and the `git_host` part changed, the runtime is rebuilt on that call (lazily, no restart, other projects untouched); an unrelated edit rebuilds nothing, and a failed rebuild throws (reported by the tick) and is retried on the next use. A project registered through the API is served from the next tick; an archived one is dropped, and unarchiving registers it again (no restart). `refresh()` runs before each tick: it re-reads every project's row and GitHub connection and rebuilds a runtime whose connection (or the link to it) changed since it was built; a project whose connection disappeared or cannot be built stops being served (its tickets park) and is retried on the next refresh. A project whose stored settings are in the old `profile` + `commands` format and lost a command to the conversion is logged at load with the reason. Settings are only served for registered projects: the config source the engine, routes and registry share is wrapped by `withKnownProjects`, so an unknown slug is a typed `ProjectNotFoundError`, not defaults at version 0.
- Drivers: `services/driver-registry.ts` keys the installed harness drivers by id (today the one Claude driver, `claude-code`). A ticket's harness is its project's effective `default_harness`; an id with no driver parks the ticket with that reason, it never runs on another harness. Shutdown cancels each live run on the driver that started it.
- Secrets: `ports.secrets` or a lazily created DPAPI store (`services/lazy-secrets.ts`), so a server with local-only projects, or off Windows, never builds it.
- Port implementations live in adapter packages, not here: the report store in `@forge/gates`, the run secret registry and liveness recorder in `@forge/hooks`, the receipt lookup in `@forge/drivers`, the id source and JSON logger in `@forge/engine`. What stays is wiring, plus `prepareRun`, which is this app's own port to the driver.
- Dependencies: workspace packages, `yaml@2.9.1` (config), `zod@4.6.7`. Dev: `@modelcontextprotocol/sdk@1.32.1` (the fake Worker calls the real MCP server in memory).

## Requirements

- Node 24, pnpm; `pnpm build` at the root, then `node apps/server/dist/main.js` from the project checkout (or set `FORGE_ROOT`). The hook client and the MCP server run from `dist/`.
- Env: `FORGE_ROOT` (the folder the yaml config is read from; default: current directory; it is not a project, projects are registered through the API), `FORGE_HOME` (data home override, an absolute folder, development and tests only), `FORGE_HOST` (only `127.0.0.1`), `FORGE_PORT` (default 4310, `0` = any), `FORGE_CLAUDE_BINARY` (a real `claude.exe` on Windows), `FORGE_ENGINE` (`acp` or `cli`), `FORGE_SHUTDOWN_GRACE_MS`, `FORGE_HARNESS_ENV_PASSTHROUGH` (comma-separated host variable names a harness child may inherit).
- Files: `.forge/` in the checkout holds only config (the tool catalogue is in the database; `.forge/tools/catalog.yaml` is only a readable mirror of the built-in seed); the data home (`%LOCALAPPDATA%\Forge` by default, or the folder in `forge-home.json` in the platform config directory) holds `forge.db`, `install-token`, `server.json`, `server.lock`, `logs/server.log` (written by `forge start`), `runs/`, `secrets/` (DPAPI blobs for a GitHub App key), `worktrees/<projectSlug>/<ticket>` (one checkout per ticket, outside the repository), `memory/<projectSlug>/` (one private repository per project: decisions, rejected, proposed, outcomes, `MEMORY.md`; this repository's own `.forge/memory/` is the dev team's memory and is never read), and reserved `backups/`; nothing is written into the checkout. Each registered project's clone must have its base branch, and `git` must be on PATH.
- Claude Code installed (`claude` on PATH, `FORGE_CLAUDE_BINARY`, or the path saved in Settings) and signed in, or an API key or OAuth token saved for the harness, for live runs; without it a run fails at start with `Install Claude Code: https://code.claude.com/docs/en/setup`. Tests: `pnpm test` (unit and the in-process end-to-end under `__tests__/e2e`, real git, SQLite and `npm`, no model; spawn-heavy files run in the `heavy` vitest project, two at a time, and temp directories are removed when each file ends). Live (billable, `FORGE_PROBES=1`, serial): `pnpm probes` runs every file under `__tests__/probes` (probe 8 Express end to end, probe 10 restart resume, probe 11 rework after a failed G1); `pnpm probes probe11` runs only the files whose path contains `probe11`. The probe fails at once when the ticket parks (`waiting_human`, `blocked`, `cancelled`), printing the blocked reason, each run's end, the last events and the denied decisions; it always writes its artefacts (ticket, runs, events, receipts, gate results and reports, interactions, server log) to `.forge/data/probes/8/` and keeps the temp fixture on failure.

## Extending

Add a ticket source as an adapter in `packages/triggers` and pass it in `ExternalPorts.triggers` (or add it to `services/triggers.ts`); the route and poller do not change.

Add a route as `src/routes/<name>.ts` returning a `Route`, list it in `routes/routes.ts`, parse its body with a schema in `src/schemas/`. Add a harness by writing a driver package and a ports factory next to `claude-ports.ts`; `assemble.ts` does not change. New settings go in `src/schemas/env.ts` and `config/load-settings.ts`.

## Limits

- Cards: a closed card with a question still pending stays in Needs you (d-0107: Needs you outranks Closed), and `PATCH /cards/:id` does not cancel it because the engine has no interaction cancel path to call; open question for the owner. `PATCH /cards/:id` closes a card without stopping its running tickets (d-0111 pauses them for the owner's call once the card chat exists), cannot reopen one, and a type change creates no tickets (conversion actions come with the card Director). There is no card Director chat or steer route yet, and the card-type registry is read-only here (the settings UI edits it later). The web Board's intake reply schema does not know `card_created` yet.
- Project memory: no API creates a decision or a proposal yet (the Director writes them once the chat flow exists), and the opt-in mirror of decisions to the user's repository (d-0086) is deferred. The server composes the memory writer but no Worker-facing route reaches it; the data-home floor denies Workers the folder.
- The install token is one shared secret in a user-only file: it keeps other accounts and browser pages out, not other processes of the same user (they can read the file too). A shared machine with several users on one account is out of scope.
- The session cookie is scoped to the loopback host, not the port (browsers ignore ports for cookies): any other local web server the user's browser visits on 127.0.0.1 receives it and could replay it. Writes still need a matching Origin from a browser, but a replaying process can forge headers. Closing this needs a per-tab secret the page holds outside cookies (open decision). Sessions are lost on restart. No start on login or tray (d-0092, later); `/health` no longer shows owner, uptime or counters, and no authenticated status route replaces them yet.
- A project row from before B4 has no `local_path` and is not served (warning at start); there is no API to set it yet, so such a project is registered again. A GitHub-connection project needs its `installation_id` typed in: the server does not look it up yet. A connection cannot be edited or disabled through the API yet, and `onboarding` projects are not created by anything yet (they simply run nothing). Archiving is one way. Candidates of several projects are scheduled by ticket number, not round-robin; global slots are shared.
- The polling cursor is in memory: after a restart a polled source is asked from the start and dedupe absorbs the repeats; no polled adapter exists yet (GitHub Issues is after release).
- Only the Claude driver is registered; a project naming another harness parks its tickets.
- Only the Express lane runs (engine limit); G1 is the only gate.
- A restart resumes interrupted runs from their harness session (d-0092); one that cannot be resumed is retried as a new run in the same worktree. A run's chain can be verified only while its secrets exist: once they are retired (the run is over and its ticket past the gates), G1 on that run fails with "Receipt chain unverifiable", so a ticket sent back to the gates after that is reworked on a fresh run.
- Liveness is enforced at the hook route (tool calls denied until `SessionStart` registered), not by killing the run; a Worker that never calls a tool is caught by the stall timer. The fingerprint is derived from run id and session id, not from the hook script.
- The run secret registry keeps the newest 5000 runs' tokens in memory (secrets stay readable from the store), so a run older than that cannot receive hook calls; none is expected to be alive that long.
- A tool call whose input alone exceeds the hook route's 2 MiB (a huge `Write`) is rejected with 413 and so blocked; only outputs are truncated by the hook client.
- Gate reports are written as `.md` under `<dataHome>/runs/<runId>/gates/<gate>-<head sha>.md` and never overwritten; nothing prunes old runs. The Director's `forge-director-*` working directory is one per process and removed at shutdown (a crash leaves it in the OS temp directory).
- Harness secrets and run secrets use DPAPI on Windows; elsewhere the DPAPI store refuses to exist, so a run cannot start (there is no plaintext fallback for run secrets), and tests pass a memory store.
- GitHub App host: wired from config but its live check is probe 9 (not part of this app's tests).
- `GET /runs/:id/events` polls storage every 500 ms per open stream.
- Stats, cost, overview and inbox are computed per request by reading the project's rows (no cache, no aggregate table): fine for one machine, to be revisited if a project holds tens of thousands of runs. A queued ticket has no run row yet, so Runs shows it only once dispatched (the ticket list shows it waiting). Memory proposals carry no timestamp, so they are dated at the epoch (the web shows no date for them), sort last and cannot resurface by change.
- Cost: a card's Director spend is what the engine stored on its planning state (`director_spend_usd`): planning steps, `card_chat` turns that succeeded, and escalation answer/recover steps. Not attributed to any card: triage and steering steps, and the cost of a model call that failed, so a card's total is a floor. Spend is stored as one running sum, so there is no per-step breakdown (no `by_step`). Ticket list rows look their card titles up per distinct card of the page (primary-key reads), the cost with one grouped read.
- Debug trace: files only (no UI); retention is by age, not size; Worker harness stderr and the MCP server's own logs are not captured, only what reaches the engine, the storage port, the config source, the Director's model and HTTP.
- Agents: one harness setup (`claude`) backs every driver id today, so readiness reads that row; agent writes are attributed to `owner` (no per-user identity yet).
