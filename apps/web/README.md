# @forge/web

The Forge control room: a React app for watching and steering a project's work. The shell, theme, motion system and data layer exist; the screens arrive one batch at a time.

## Why it exists

Forge runs work autonomously, but the user still decides what needs a human: answering a Worker's question, approving a review, reading what a run did. They need to see state at a glance and talk to the Director and Workers live. Without a control room the only view is logs and the database. The UI is built natively rather than embedding a third-party tracker (d-0010, r-0004).

There is no company-wide Home (d-0104). The user always works inside one project and switches project from a dropdown at the top of the left sidebar; everything about Forge itself (harnesses, GitHub, limits, general) lives in a separate "Forge settings" group.

## What it does

Built (batches W1 to W7, `docs/design/web-build-plan.md`):

- **Shell**: left sidebar (project switcher, project nav, Forge settings, theme toggle), a drawer on screens under 768 px, skip link, animated page transitions.
- **Project switcher**: dropdown of open projects from `GET /projects`, `Ctrl+K` / `Cmd+K` opens it, switching keeps the same screen under the new project. Loading, empty and error states.
- **Unsaved-changes guard**: any view calls `useUnsavedChanges(isDirty)`; while true, switching project or navigating shows an in-page "Keep editing / Discard changes" alert.
- **Theme**: "Instrument" tokens (graphite, one cobalt signal, amber only for what needs the user), light and dark, system by default with a toggle, fonts self-hosted.
- **Motion**: critically damped spring presets, shared-layout sidebar indicator, route transitions, `MotionConfig reducedMotion="user"`. Only `transform` and `opacity` animate.
- **Data layer** (`src/api/`): the `ForgeApi` port with the `http` adapter as its only implementation (no mock, d-0123), a validated SSE helper `watchRunEvents()` (used by the Ticket thread; it reports connecting, open and reconnecting).
- **Forge settings (W2)**, all on the real endpoints:
  - _Harnesses_ (`/settings/harnesses`, `/settings/harnesses/:id`): list with version, installed build, sign-in and status; per harness a sign-in form (signed-in account, API key, OAuth token), a write-only credential field, a test (optional paid live call), the compatibility check with live progress and a per-check result, and built-in tool approvals where every approve or deny goes through a confirm that records name and reason.
  - _GitHub_: connections list and an add form (App id and private key; the key is never shown). No one-click App creation (later).
  - _Limits_ and _General_: company settings as versioned, attributed saves. Edits are validated against core's `ForgeConfig` in the unit shown, saved as the previous override plus the change (so untouched settings keep following defaults), and a 409 offers "Reload latest" or "Keep my edits on top". History lists every version with what it changed.
- **Project settings** (`/p/:slug/settings`, W4): read-only project facts; every overridable setting (checks by role, default harness, Workers at once, fallback harnesses, ecosystems, Tier C paths, remote) shown as inherited (with where it comes from) or overridden, a switch to clear an override; versioned save with a required reason; if a newer version exists (409 or a background refresh) saving pauses and the banner offers a diff and a reload, never an overwrite; history list with plain-words diffs; archive behind a confirm. Keys the screen does not edit (git host, gate rules, tool grants) are carried through a save unchanged.
- **Memory** (`/p/:slug/memory`, W4): tabs Decisions, Rejected, Proposals, Outcomes with counts; text and tag filters; superseded decisions marked; a detail drawer (`?record=d-0003`) with source, author, dates and links along the supersede chain; Approve and Reject (reason required) behind a confirm, applied optimistically and rolled back on failure; the list windows past 100 rows.
- **Board, Tickets view** (batch W3): `/p/:slug/board`. One newest-first list of the project's tickets (`GET /projects/:slug/tickets`, cursor paging; the first 1,000 load on their own, then "Load older tickets"), grouped on the client into six columns (`src/domain/board-columns.ts`): Inbox and planned, In progress, Needs you (amber: waiting_human, review, needs_signoff), Verifying, Done, Blocked and cancelled. Cards show id, title, lane, run status, rework count and the needs-you marker, and are one link to the Ticket page. Lane, state and text filter; columns over 100 tickets are virtualised, shorter ones glide a card between columns with the shared-layout spring; refetch every 5 s and on focus; offline and refresh-failed banners; an "Ask the Director" box files a chat request (`POST /intake`, one dedupe key per message).
- **Board, Cards view** (W6, the default): `/p/:slug/board` opens on six columns of cards (New, Shaping, Needs you, In progress, Done, Closed) grouped on the client by the `column` the server rolled up (`GET /projects/:slug/cards`, cursor paging like the ticket list; `src/domain/card-columns.ts`). The UI never decides a column and a card cannot be dragged. A tile shows the type icon and label (from `GET /card-types`, icon names mapped to bundled lucide icons, a document icon for an unknown name), title, "N of M tickets done", amber "Needs you" only in that column, and is one link to the Card page. Type and text filters, Cards | Tickets switch; the view and both filters persist (`forge.ui.board`, version 2). Columns over 100 cards window; refetch every 5 s and on focus; offline and refresh-failed banners. A request the Director turns into a card (intake `card_created`) links to it from the Ask the Director box.
- **Card page** (W6): `/p/:slug/cards/:id`, tab in `?tab=`. Header: id, column pill, source, title, a type select (changing it asks first, then `PATCH /cards/:id {type}`; 409 `card_type_source` and `card_closed` are explained) and Close card (a confirm with a required reason, then `PATCH {closed_reason}`; a closed card shows its reason and takes no change). An amber banner lists questions waiting on the user with a link to each ticket. **Chat** tab: history from `GET /cards/:id/events` read in windows by `seq` (the newest 50 with `?order=desc&limit=50`, "Show earlier messages" with `?before=<oldest held>&limit=50`, each poll `?after=<newest held>` so a long history costs one small request); speech bubbles (user right, Director left), what the Director did as compact lines that say Done or Refused with the summary (under a `director_message` and as `director_action` lines), a Director close suggestion (`close_suggested`) with a "Close card" shortcut that opens the close dialog with its reason prefilled, and one quiet line per ticket event, type change, close or unknown kind (never a crash); follow-the-newest with "Jump to latest"; "The Director is thinking" while `director.state` says so, its error in words; a composer (Ctrl+Enter) that appends the message at once as "Sending…", swaps in the server's `user_message` event on 202, and on refusal (409 `card_closed`, 503 `server_draining`, offline) removes the unsent line and keeps the draft, which is saved per card (`forge.ui.drafts`, key `card:<id>`). A closed card keeps its history and disables the box with the reason. Polls every 5 s, every 3 s while the Director is thinking or the newest speech is the user's. **Tickets** tab: linked tickets in creation order with state, lane, run status, each a link. **Details** tab: source, creator, times, budget cap ("No cap" when absent), summary.
- **Message the Worker** (W6): on the Ticket page, under the live thread, when the shown run is the ticket's current run and live; `POST /runs/:id/steer {message, author}`. The message shows in the thread as the user's line when the run streams its `user_message` event; refusals read in words (409 `run_not_live`, 409 `steer_unsupported`, 503 `server_draining`) and keep the draft (`run:<id>`). Tickets link back to their card (`card_id`) from the Board tile and the Ticket header.
- **Ticket page** (batch W3): `/p/:slug/tickets/:id` from `GET /tickets/:id`: header (state, lane, PR link, blockers as links), gate strip (latest result per gate), runs list, and the **live Worker thread** of the chosen run from `watchRunEvents()`: messages, tool calls (collapsed, expandable), permission decisions and denials, finish and error lines, a connection state (connecting, live, reconnecting, ended, lost with Reconnect), follow-the-newest scrolling that pauses when you scroll up ("Jump to latest"), virtualised past 100 items. A pending question shows in amber above the thread with an answer form (`POST /interactions/:id/answer`): optimistic, the draft survives a refusal, a 409 says it was already answered.
- **UI state** (`src/state/`, d-0122): zustand stores built by `createPersistedStore()`, saved in `localStorage` as `forge.ui.<name>` (versioned, schema-checked on read, guarded storage). Persisted: `theme` (mode), `project` (last project slug), `board` (view, filter), `thread` (follow latest, expand tools), `drafts` (unsent answers by question id, dropped when sent), `memory` (tab, tags, hide-superseded; not the search text) and `author` (the name on settings saves). Hooks keep their names (`useBoardPrefs()`, `useThreadPrefs()`, `useAnswerDraft()`, `useMemoryPrefs()`, `useAuthorPrefs()`). Server data, tokens, secrets and run content are never persisted (a test pins the allowed fields).
- **Home** (`/p/:slug`, W5): a readout line (Workers running, tickets by state, spend today and over the range), "Waiting on you" (the newest five inbox items that need action, each linking to its source, with the true count), "In progress" (the Board's ticket list filtered to started work, each with a five-stage track and a "Needs you" mark), and "How it is going" for a 7, 30 or 90 day range: hand-drawn SVG charts of tickets done, runs and spend per day (named, described, with a hidden data table), and tiles for lead time (median, p90), rework rate, G1 pass rate and cost coverage. A figure the server sends as `null` reads "No data", never 0; spend is not drawn when no run reported a cost. The Director bar at the foot is the Board's composer. From `GET /projects/:slug/stats`, `/inbox`, `/inbox/counts` and the ticket list.
- **Inbox** (`/p/:slug/inbox`, W5): views Needs action, Unread, All, Archived with counts; each row names its kind and links to its source (ticket, run, memory record or harness). Read, unread and archive answer at once (every cached view and the counts move together), roll back with a plain message if the server refuses, and an archive offers Undo for eight seconds. Cursor paging with "Load more", windowed past 100 rows. The sidebar Inbox link shows the unread count, refreshed every 30 seconds and on window focus.
- **Runs** (`/p/:slug/runs`, W5): newest-first runs with status (a quota-parked run reads "Parked: quota"), ticket, harness, start, duration, cost ("no cost reported" when absent) and tokens; filter All, Active, Done, Problems (sent to the server as `status`), paging, windowed. While any run is live the list refetches every 5 seconds. A run opens in a drawer (`?run=<id>`, from `GET /runs/:id`) with gates, working folder, harness session, tokens per model and a link to its ticket.
- **Cost** (`/p/:slug/cost`, W5): spend reported, run count and tokens for the range, a per-day chart, the cost coverage sentence ("5 of 6 runs reported cost. Spend covers only those runs."), top tickets and runs, by harness, by model in tokens ("no price table yet"), and budgets (per-run cap, per-step budget; period budget "Not set").
- **First-run wizard** (`/welcome`, W7): full screen, outside the shell. `/` opens it when `GET /system` says setup is not finished (no project registered yet) and the user has not chosen "Finish later"; if `/system` cannot be read the project list decides alone. Four steps: 1 Data folder (read-only path from `/system` with how it is chosen), 2 Harnesses and logins (the Forge settings sign-in, credential and Test forms for `claude`; the real model call is an unticked, cost-labelled box), 3 Connect GitHub (optional; the settings add form, or "Skip: use local git only"), 4 First project. It opens at the first step the server shows as not done (a harness that passed its test opens it at step 3), Esc or Back goes one step back, any step is reachable from the step list, and "Finish later" remembers the choice (`localStorage`, UI preference) and lands in Forge settings; `/` then shows "No projects yet" with "Add project" and "Resume setup".
- **New project** (`/projects/new` inside the shell, and wizard step 4; one `ProjectForm`): repository folder, then "Check folder" (Enter) runs `POST /projects/inspect` and shows what was found (top-level repository, checked-out branch, branch count, languages, suggested checks). Only then the name, ticket prefix (prefilled, editable, checked against the server's patterns), base branch (select), git host (local bare remote, or a GitHub connection with `owner/name` and installation id), checks (the project-settings editor) and your name are offered; editing the folder hides them again. Create sends the strict `POST /projects` body and opens the new project's Home. Every server refusal code (`invalid_local_path`, `path_in_data_home`, `not_a_directory`, `not_a_repository`, `not_repository_root`, `base_branch_missing`, `project_exists`, `prefix_in_use`, `path_in_use`, `connection_*`, `invalid_settings`, `project_not_servable`) is shown beside its field with a fix. The project switcher menu ends with "Add project".
- **Placeholders** for the destinations later batches build.

Routes: `/` redirects to a project (or to `/welcome` on a fresh Forge); `/welcome`; `/projects/new`; `/p/:slug`, `/p/:slug/cards/:id`, `/p/:slug/tickets/:id` and `/p/:slug/{inbox,board,issues,chat,runs,cost,memory,settings}`; `/settings/{harnesses,harnesses/:id,github,limits,general}`.

Public API: none; it is an app. Entry is `src/main.tsx`.

## Why this approach

- Stack fixed by d-0103: Vite, React 19, React Router, TanStack Query, Tailwind 4, Radix primitives with our own styling (no shadcn), lucide icons, `motion`. assistant-ui is not used: the thread folds Forge's own run events (`src/domain/thread.ts`) and renders them as text, never HTML or markdown, because it is untrusted model output. Rejected for now: a chat-UI library, since the thread is read-and-answer, not a chat composer.
- **Types come from `@forge/core` zod schemas.** `src/schemas/projects.ts` derives the `/projects` response from core's `Project`; `src/schemas/http.ts` holds the two server envelopes core does not export (error body, SSE ticket reply), each documenting the server route it mirrors.
- **The real API only** (d-0123): there is no mock adapter, fixture data or `VITE_FORGE_*` switch in `src/`. `ForgeApi` stays one interface so a screen reads the API from context; a screen whose backend does not exist yet gets the endpoint built, not sample data. Component tests stub `fetch` (`__tests__/helpers/fetch-stub.ts`) so the real adapter, schemas and screens run unchanged.
- **zustand for UI state** (5.0.15): small, no provider, and its `persist` middleware gives versioning and migration. Rejected: hand-rolled `useSyncExternalStore` stores (what this replaced) and redux-style libraries (more than the problem needs).
- **The token never reaches the browser.** In production the Forge server serves `dist/web` and the browser carries an HttpOnly session cookie from a one-time link (`forge open`); the page calls the same `/api/*` paths. In development `vite.forge-proxy.ts` proxies `/api/*` to `127.0.0.1:4310`, strips any page-supplied `Authorization`, reads the install token from the data home on every request and adds the header itself. Rejected: `define` or `import.meta.env` for the token (readable by any script on the page).
- Springs are critically damped (damping = 2 * sqrt(stiffness * mass)): fast, no wobble. Animating only `transform` and `opacity` keeps 60 fps.
- **One list, grouped on the client, for the Board.** A ticket has one state, so a single newest-first list is one consistent snapshot: a ticket moving between columns can never appear twice or vanish between two requests, one refetch refreshes every column and paging has one cursor. Per-column paging would need six cursors that drift apart as tickets move. `@tanstack/react-virtual` windows long columns and threads (no Windows caveat).
- Radix for menus and dialogs gives focus trap, Escape, ARIA and typeahead for free; the look is ours.
- `Button`, `StatePanel` and the nav items carry every state (hover, focus-visible, active, disabled, loading, error, success where meaningful).

## Requirements

- Node 24.20, pnpm 12, and `pnpm install` at the repo root.
- Run it: start the server with `forge start` (default port 4310; `FORGE_PORT` changes it), then `pnpm --filter @forge/web dev` and open <http://127.0.0.1:5173>. There is no mock mode: the app always needs a server.
- The dev proxy needs `@forge/core` built once (`pnpm build` at the root) to find the data home; without it, `/api` calls go out without a token and the page shows its "Forge did not accept this session" state. It honours `FORGE_HOME` like the server.
- The install token is read from `<data home>/install-token` (Windows default `%LOCALAPPDATA%\Forge`). The server regenerates it on restart; the proxy follows with no reload.
- Scripts: `dev`, `build` (to `dist/web`), `preview`, `e2e`.
- Component tests (`web` project, jsdom, 70% line floor, part of the root `pnpm test`) need no server: `__tests__/helpers/fetch-stub.ts` stubs `fetch` with a route table (method and path to a response or a function; `stub.calls`, `stub.use()` to stage a refusal), `event-source-stub.ts` scripts run streams, and `fake-forge/` builds a stateful sample server from them with data in `forge-data/` parsed through core's schemas.
- Browser smoke (separate from `pnpm test`): `pnpm build` once at the root (the server runs from `dist/`), `pnpm --filter @forge/web exec playwright install chromium` once, then `pnpm --filter @forge/web e2e`. `e2e/global-setup.ts` starts the real server on a temporary data home and free port (`FORGE_HOME`, `FORGE_PORT`), seeds two repositories as projects and one chat request through the HTTP API, builds the app and serves it with `vite preview` whose `/api` proxy adds the install token; teardown stops both and deletes the temp folders. Allow about a minute to boot on Windows. Drives 375 px and 1280 px.
- Root `pnpm typecheck`, `pnpm lint` and `pnpm format:check` cover this app too.

## Extending

- **Add a screen**: its entry already exists in `PROJECT_NAV` or `SETTINGS_NAV` (`src/domain/nav-entries.ts`). Build the component under `src/routes/` and swap its `PlaceholderPage` in `src/routes/app-routes.tsx`. Read data with TanStack Query over `useForgeApi()`; give it loading, empty, error and offline states (`StatePanel`). Hold edits? Call `useUnsavedChanges(isDirty)`.
- **Add a resource**: add it to `ResourceApis` (`src/types/api.types.ts`) and implement it in `src/api/http/http-adapter.ts` (the compiler refuses an adapter that misses it), parsing responses with a schema from `@forge/core` (or a minimal one in `src/schemas/` that names the server route it mirrors). Build the server endpoint first; add its routes to `__tests__/helpers/fake-forge/` for component tests.
- **Add persisted UI state**: `createPersistedStore({ name, version, initial, schema })` in a `src/state/` file with a schema in `src/schemas/ui-state.ts`, wrap it in a `use<Feature>Prefs()` hook, and add its allowed fields to `__tests__/state/persisted-stores.test.tsx`. Bump `version` and give `migrate` when the shape changes.
- **Settings forms** hold their write in `useSubmit()` (component state, never a query cache) so pasted keys do not linger; versioned editing lives in `useCompanyDraft()`; the field lists are data in `src/domain/settings-fields.ts`.
- **Add a resource in its own file** (no fixtures, d-0123): add it to `ResourceApis` (`src/types/api.types.ts`), implement it in an `src/api/http/*-http.ts` file spread into `createHttpAdapter()`, and test screens with `renderWork()` and `createFetchStub()` (`__tests__/helpers/`), which stand in for the server at `fetch`.
- **Watch a run**: `watchRunEvents({ runId, baseUrl: '/api', onEvent, onEnd, onError })` gets a ticket, streams, validates frames and resumes with `?after=<seq>`.
- **Animate**: pick a preset from `src/theme/motion.ts`; never write raw stiffness numbers or animate layout properties.
- Every new screen records its Nielsen-10 coverage and a Hallmark pass before build.

## Limits

- Project destinations still placeholders: Chat, Issues W8.
- Cards (W6): history event kinds are read as open strings (the web schema is looser than core's `CardEvent`, so a kind newer than this UI shows as a note instead of failing the page). A card tile shows ticket progress only as counts (the summary carries no per-ticket states). An old close suggestion keeps its button for as long as the card is open.
- Work screens (W5): `stats`, `cost`, `inbox` and `runs` are served by the real server like every other resource. Charts show UTC calendar days as the server sends them. Cost has no per-model dollars (the server keeps tokens only) and no period budget. Inbox and Runs have no text search or date filter (the server's queries are view/status/cursor only). Run and Inbox links to a harness open the harness list when the item names only a build. Range, inbox view and run filter are plain React state that resets on reload (d-0122).
- Memory: the server's list omits outcomes and does not return `superseded_by`, so the Outcomes tab is empty against the real server and a superseded row links to its successor only in the drawer. A proposal answer cannot be undone (no API), so it is a confirm, not an undo window.
- Project settings: project name, repository, branch, folder and prefix are read-only (the API only archives). Archiving cannot be undone from the UI. Author is the fixed name `owner` until accounts exist.
- Production hand-off exists (W7b): `forge start` serves this build from the server at `/` and signs the browser in with a one-time link (`forge open` for a new one); the page holds no credential. The session lasts 12 h idle and ends when the server restarts; the 401 state then tells the user to run `forge open`.
- First run: the data folder is shown, not editable (it is chosen when Forge starts; no API changes it). "Finish later" is remembered per browser, not on the server. A local host needs a bare repository path typed by hand; Forge does not create one. The wizard's own tests run on `stubFetch`; the other screens' tests still use the mock adapter until it is removed.
- The bundle is one 700 kB chunk (all of `@forge/core`'s schemas are included); code-splitting waits for the first heavy screen.
- Archived projects are hidden from the switcher; there is no way to open one yet.
- The Playwright smoke is not part of `pnpm test`, needs a downloaded browser and a built server. With no Claude Code configured no Worker runs, so it asserts empty states for the live thread, memory proposals, harnesses and GitHub connections; screens with data are pinned by the component tests.
- Sidebar collapsed state is not persisted because the sidebar has no collapse control yet; the settings editors keep unsaved edits in the page (they guard leaving) rather than in storage.
- Settings gaps the server leaves: no profile call (the name on a save or decision is typed once and kept in `localStorage`, d-0122), no data-folder path, no edit or disable of a GitHub connection, no per-project cap here (project settings, W4), and the harness list has no delete. A by-state cap Forge ships with can be changed but not removed (overrides merge over defaults).
- Board: no drag-and-drop (a ticket changes column only when the server changes its state); the Cards view is W6. Past 1,000 tickets the older ones load on request.
- Ticket page: no steering message to a live run (W6b), no "Cancel run" or gate report viewer; the runs list needs `GET /tickets/:id` to include all runs (it does today, unpaged).
- Answers are sent as plain text; the server stores any JSON, so a structured answer for permission or plan kinds waits on a contract for those shapes.
